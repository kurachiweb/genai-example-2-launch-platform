# ADR-0001: D1のORMにDrizzle ORMを採用する(MikroORM+Kyselyから変更)

**日付**: 2026-09-30
**状態**: accepted
**決定者**: KurachiWeb(決定)、Claude(調査・推奨)

## 背景

- 本サービスのデータベースはCloudflare D1のみである(SW-003)。D1は`BEGIN`によるトランザクションを使えず、複数テーブルへの書き込みを一括で成功・失敗させる手段は`D1Database.batch()`に限られる。
- 当初の技術選定はMikroORM+Kyselyだった。MikroORM v7のD1対応は公式ドキュメント上で実験的扱いであり、保存処理がアトミックにならないため、複数テーブルへの書き込みはKyselyで行う規則にしていた。
- MikroORMはWorkersで使えない`new Function`を避けるため、起動前の事前コンパイル工程が必要だった。マイグレーションの既定出力はTSクラスで、Wranglerで適用できるSQLファイルを出力する公式手順は確認できなかった。
- 実装コードがまだ無く、ORMの変更で修正が要るのはドキュメントのみだった。

## 決定

ORMとしてDrizzle ORM(v1.0 RC)とdrizzle-kitを採用し、Kyselyは併用しない。

## 検討した代替案

### 案1: MikroORM+Kysely(従来の選定)

- **長所**: 開発が活発(7.2.2が2026-09-28公開)。変更追跡やリレーション管理が充実している。`nocase`を`columnType`の指定だけで書ける。
- **短所**: D1は実験的扱いで、保存処理がアトミックにならない。D1用ダイアレクトはコミュニティ製の`kysely-d1`(最終リリース2025-04)に頼る。事前コンパイル工程が要る。SQLマイグレーションの出力手段を自前で用意する必要がある。
- **採用しない理由**: D1では変更追跡と一括保存を安全に使えず、複数テーブルの書き込みはKysely頼みになる。ORMの利点を生かせないまま、回避策の規則だけが残る。

### 案2: Drizzle ORM 0.45.x(安定版)

- **長所**: `latest`タグが指す安定版である。
- **短所**: リレーション取得の仕組み(RQB v1)が1.0で廃止されるため、後から移行作業が要る。
- **採用しない理由**: 実装前のため、移行先である1.0を最初から採用できる。

### 案3: Drizzle ORM+Kysely併用

- **長所**: Kyselyの書き方に慣れている場合に移行しやすい。
- **短所**: スキーマの型定義が二重になる。クエリの書き方が2種類になる。依存パッケージが増える。
- **採用しない理由**: Drizzle単体で、JOIN・upsert・`db.batch()`・`sql`テンプレートによる生SQLまで足りる。

## 結果

### 良くなること

- 複数テーブルへの書き込みを、型付きの`db.batch()`でアトミックに書ける。
- 事前コンパイル工程が不要になる。
- マイグレーションがSQLファイルで出力され、Wranglerでそのまま適用できる。

### 悪くなること

- カラムの照合順序を指定するAPIが無く、`customType`による共通ヘルパー(`textNoCase`)で代用する。対象はASCIIの大文字小文字のみで、既存カラムへ後から付けるとテーブル再作成になる。
- FTS5の仮想テーブルとトリガーはスキーマ定義で表現できず、カスタムマイグレーションの生SQLで書く。
- マイグレーションの出力が入れ子構造のため、Wrangler設定に`migrations_pattern`の指定が要る。
- D1ではDrizzleの`db.transaction()`を使えない。

### リスク

- 1.0が正式リリース前のため、RC版を使う。
  - RC版から正式版への更新で、破壊的変更が入る可能性がある。更新時に変更点と生成SQLの差分を確認する。
- テーブル再作成のマイグレーションに`PRAGMA foreign_keys=OFF`が含まれ、D1の外部キーの扱い(`PRAGMA defer_foreign_keys`)と合わない可能性がある。適用前に生成SQLを人が確認する。
