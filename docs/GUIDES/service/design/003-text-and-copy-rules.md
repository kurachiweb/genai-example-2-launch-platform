# 文言・文字数規則

入力欄の文字数上限、UI文言の表記、通知メールの文面規則を定める。文体・語調の方針は[デザイン原則](001-design-principles.md)を参照。

## 入力欄の文字数上限

上限値・必須区分・文字種の制約は対応要件を正とし、本表はその索引である。

文字数は原則書記素(ユーザーが1文字と認識する単位)で数えるが、パスワードに限りコードポイント数で数える。全角・半角・絵文字を区別しない。上限はフロントエンドでフォーカスアウト時(UI-005)に検証し、サーバー側でも同じ値で検証する(NFR-SECUR-012)。

### 容量の単位

要件定義書とUIでファイルサイズの上限を`kB`・`MB`で書く場合、1,024を基数とする(1kB = 1,024バイト、1MB = 1,048,576バイト)。実装の定数とテストの境界値はこの換算で求めたバイト数にし、1,000を基数とする値(500,000バイト・20,000,000バイトなど)を使わない。UIの表記は要件定義書と同じ`kB`・`MB`のままとし、`KiB`・`MiB`と書かない。

| 表記  | バイト数   |
| ----- | ---------- |
| 500kB | 512,000    |
| 5MB   | 5,242,880  |
| 10MB  | 10,485,760 |
| 20MB  | 20,971,520 |

外部サービスが定める上限は、そのサービスの仕様のバイト数に従い、この規則の対象外とする。

マークダウンの入力欄の禁止文字・必須の未入力・文字数超過の文言は、「コメント」を欄の項目名に、「2,000」を欄の上限の3桁区切りの値に置き換える。必須の未入力には空白だけの入力を含む。禁止文字は、タブ・改行(LF・CR)を除く制御文字(C0制御文字U+0000〜U+001F・DEL U+007F・C1制御文字U+0080〜U+009F)と、対にならずに現れたサロゲート(文字として成り立たない符号)である。1つの入力に複数の違反があれば、禁止文字・必須の未入力・文字数超過の順に最初の1つだけを表示する。

アップロードの拒否の文言のうち、「アップロードしたファイルを読み込めない」は内容と申告した形式の不一致・壊れたSVG・テキストファイルの不正な文字・寸法を読めない画像に、「書き出し直しが必要なSVG」はSVG 1.0・1.1の標準の文書型宣言の他にDOCTYPE・ENTITYの宣言を含むSVGに、「画像の縦横の大きさの超過」は画素数・辺の長さの上限の超過に、「アップロードの送信の失敗」は送信の途中で長さが食い違った場合などに使う。「権限の無い操作」はアップロードできない種類の主体(利用者・管理者)の操作などに使い、停止中のアカウントとメールアドレスの未確認による拒否は「停止中アカウント(パスワード合致時)」「メール未確認」の文言を使う。

アカウントの文言のうち、「権限の無い操作」はアカウントの操作でも、利用者側でない呼び出し元の操作と運営者による退会の操作口への拒否に使う。「ログイン失敗」は未登録・退会済みのメールアドレスとパスワードの不一致を区別せずに使い、「停止中アカウント(パスワード合致時)」は停止中の利用者のメールアドレス変更・パスワード変更・多要素認証の操作の拒否にも使う。「認証コード・リカバリコードの誤り」はリカバリコードの誤りにも同じ文言を使う。「パスワードの文字数の違反」の下限と上限は[入力欄の文字数上限](#入力欄の文字数上限)のパスワードの値を示す。「アカウントの状態の変更の重なり」は、同じ利用者の退会・停止・停止解除が同時に行われ、後から確定しようとした操作を拒否する場合に使う。「認証コードとリカバリコードの両方の入力・どちらも無い入力」は画面のフォームでは起きず、APIサーバーが直接の呼び出しを拒否する場合に返す。

問い合わせの文言のうち、ニックネーム・メッセージ(問い合わせチャットのメッセージと管理者の返信の本文を含む)の禁止文字・必須の未入力・文字数超過は、マークダウンの入力欄と同じ順序と禁止文字で判定し、最初の1つだけを表示する。ニックネームの未入力と文字数超過は上の表の「ニックネームの未入力」「文字数超過」の文言を使い、上限は[入力欄の文字数上限](#入力欄の文字数上限)の値を示す。添付ファイルの件数と合計サイズの超過は「ファイル選択数超過」「ファイルの合計サイズ超過」の文言を使う。「問い合わせの添付ファイルに添付できないファイルがある」は、削除済み・他の利用者のもの・別のメッセージに紐付け済みのファイルなどを送った場合に添付の欄に表示し、該当のファイルの一覧の項目には「このファイルは添付できません。削除してから送信してください。」([状態・案内の文言](#状態案内の文言))を示す。「問い合わせのカテゴリの未選択・選択したカテゴリの削除」は、フォームを開いた後に管理者がカテゴリを削除した場合にも使う。未ログイン(停止中を含む)の送信の回数の上限は「レート制限(429)」の文言に、再度送信できる日時の案内を続ける。

決済の文言のうち、「決済サービスの障害(APIの応答)」は、APIサーバー・イベントサーバーが`payments_unavailable`(503)で返し、題名を伴わずに単独で読まれる文言である。画面の決済画面と決済後のランディングは、この文言ではなく[状態・案内の文言](#状態案内の文言)の「外部サービス障害による縮退運転」(共通部品の題名「現在ご利用いただけません。」と理由の文)を表示する。2つの文言は同じ理由の文を共用部品の定数から使い、意味を揃える。決済の開始の回数の上限は「レート制限(429)」の文言を、決済履歴の続きの位置の指定の誤り(`invalid_cursor`)は[管理画面のエラーメッセージ](#管理画面のエラーメッセージ)の「一覧のページの位置の指定の誤り」と同じ文言を使う。利用者の状態(未ログイン・メール未確認・停止中)による決済の開始と同意の記録の拒否は、上の表のアカウントの文言を使う。「決済履歴の表示する件数の指定の誤り」の上限は1回に読む件数の上限(50件)を示し、画面の操作では起きずAPIサーバーが直接の呼び出しを拒否する場合に返す。カードの拒否など支払いの確定の失敗は、決済サービス(Stripe)が返す利用者向けの文言をそのまま入力欄の近くに表示する。

### 共通のエラー応答の文言

フロントエンドサーバーとAPIサーバーの間の中継・通信で起きる失敗は、エラーコードごとに次の文言を返し、画面にもそのまま表示する。問い合わせの導線が無い管理者側の画面にもそのまま出るため、どの文言も問い合わせを促す文を含めない。

| 状況                                      | エラーコード(状態コード)                                 | 文言                                                                           |
| ----------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------ |
| CSRF対策による操作の拒否                  | `csrf_rejected`(403)                                     | この操作を受け付けられませんでした。ページを再読み込みして再度お試しください。 |
| 受け付けない操作の方法・形式              | `method_not_allowed`(405)・`unsupported_media_type`(415) | この操作を受け付けられませんでした。ページを再読み込みして再度お試しください。 |
| 中継先(APIサーバー)の障害・応答の時間切れ | `upstream_unavailable`(503)・`upstream_timeout`(503)     | 現在ご利用いただけません。時間をおいて再度お試しください。                     |
| 中継先からの応答の形式が不正              | `invalid_response`                                       | 現在ご利用いただけません。時間をおいて再度お試しください。                     |
| ブラウザからの通信の失敗                  | `network_error`                                          | 通信に失敗しました。時間をおいて再度お試しください。                           |
| 中継の対象に無い要求                      | `not_found`(404)                                         | お探しの内容は見つかりませんでした。                                           |
| サーバー内部の失敗                        | `internal_error`(500)                                    | 問題が発生しました。時間をおいて再度お試しください。                           |
| 要求の集中                                | `rate_limit_exceeded`(429)                               | 操作が集中しています。しばらく待ってから再度お試しください。                   |

ページの要求が集中した場合の画面(429)は`rate_limit_exceeded`と同じ文言を表示する。フロントエンドサーバーの設定の不備や想定外の例外でページを描画できない場合の画面(500)は、[想定外のエラーの画面](#状態案内の文言)の見出しと案内をつなげた文言を表示する。

アップロードの欄も、この表の文言をそのまま欄に表示する。ただし中継の`unsupported_media_type`(415)は、利用者にとって用途ごとの形式の拒否と同じ意味のため「ファイル形式違反」の文言に代え、保存先の一時的な障害は「アップロード・画像配信の一時的な障害(503)」の文言にする。応答の本文が共通のエラー形式でない・文言が空の場合は「エラーコードを持たない想定外の失敗」の文言を表示する。ただし503と429は、本文に文言が無くてもそれぞれ「アップロード・画像配信の一時的な障害(503)」「レート制限(429)」の文言を表示する。

| 画面                                 | 静的な500の画面の文言                                                                                |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| 問い合わせの導線がある画面(利用者側) | ページを表示できませんでした。時間をおいて再度お試しください。解決しない場合はお問い合わせください。 |
| 問い合わせの導線が無い画面(管理者側) | ページを表示できませんでした。時間をおいて再度お試しください。                                       |

- 予選勝利の結果通知にはWeekトーナメントの決済期限を明記する
- Weekトーナメント決勝勝利の結果通知にはYearトーナメントの決済期限を明記する

### 決済のメールの本文

購入確認メールと自動返金の通知メールは、[本文の構成](#本文の構成)の宛名・本文・ボタンの順に、次の要点を書く。どちらも配信停止リンクを付けない。購入確認メールは購入の権利の付与が確定するごとに1通送り、Ultrasの毎月の更新の請求では送らない。自動返金の通知メールは、反映の期限切れ・権利を付与できない・二重決済で自動の全額返金が成功したときだけ送る。

| 通知種別       | 宛先                               | 本文の要点                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | ボタン         |
| -------------- | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- |
| 購入確認       | 購入者の登録しているメールアドレス | 「ご購入ありがとうございます。お支払いを確認し、購入が確定しました。このメールは購入の控えです。大切に保管してください。」、見出し「購入の内容」の箇条(購入・分量・お支払い金額・購入日時・役務の提供時期)、最終確認画面の追加事項があれば見出し「購入の条件」の箇条、見出し「役務の即時提供への同意」(「<日時>に、購入の画面で次の内容に同意いただきました。」と、かぎ括弧で囲んだ同意の文言)、見出し「返金ポリシー」(返金ポリシーの要旨)、「購入と返金の記録は、下のボタンから決済履歴で確認できます。」 | 決済履歴を見る |
| 自動返金の通知 | 購入者の登録しているメールアドレス | 「購入を確定できなかったため、お支払いいただいた金額の全額を返金しました。」、「返金の理由: <理由の文>」、見出し「返金の内容」の箇条(購入・分量・返金した金額・お支払いの日時・返金の日時)、「返金は、お支払いに使った支払い方法へ戻ります。お手元に反映されるまでの日数は、カード会社などにより異なります。」、「返金の記録は、下のボタンから決済履歴で確認できます。」                                                                                                                                   | 決済履歴を見る |

- プレビューは、購入確認メールを「ご購入ありがとうございます。購入の内容と、同意いただいた条件をお知らせします。」、自動返金の通知メールを「購入を確定できなかったため、お支払いいただいた金額の全額を返金しました。」とする
- 日時は[本文の構成](#本文の構成)のとおりUTCで、年を付けて表記する。例: 「2026年11月2日07:40(UTC)」
- 金額はロケールによらず、通貨の記号と通貨のコードを付けてセント単位まで表記する。例: 「$1,234.50 USD」。購入確認メールのお支払い金額には「(税込)」を添える
- 最終確認画面の追加事項(Ultrasの自動更新である旨・毎月の請求額・解約の方法など)は、最終確認画面に表示した文をそのまま箇条にする。追加事項の無い購入では見出し「購入の条件」も置かない
- 同意の文言は、購入者が同意した版の文言をそのまま載せる。返金ポリシーの要旨は最終確認画面と同じ文とする
- 返金の理由の文は次のとおりとする

| 理由               | 理由の文                                                                         |
| ------------------ | -------------------------------------------------------------------------------- |
| 反映の期限切れ     | お支払いの確認が、購入を反映できる期限に間に合いませんでした。                   |
| 権利を付与できない | お支払いを確認した時点で、購入の対象が購入できない状態になっていました。         |
| 二重決済           | 同じ購入の対象へのお支払いが既に確定していたため、重ねてのお支払いとなりました。 |

- ボタンのリンクは利用者側の[決済履歴](002-page-layouts.md#決済履歴settingsbilling)の画面(`/settings/billing`)へのリンクで、有効期限を持たない
