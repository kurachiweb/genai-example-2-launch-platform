# 日次・週次・年次タイムライン

サービスの定期処理と時刻に依存する仕様を、基準時刻(UTC-08:00)の1日の流れに沿って整理する。各処理の規則は対応要件を正とし、本書は時刻の一覧と処理順序を定める。
基準時刻は夏時間を持たない固定オフセットであり、日境界はUTCの8:00である。日時データの保持はI18N-002を、表示形式はI18N-004を正とする。

### 日次バッチ(4:21)の内容

対象データと条件は[データ保持期間の一覧](../legal/001-compliance-policy.md#データ保持期間の一覧)のうち削除方法が「日次バッチ」のものを正とする。退会ユーザーのデータ、及びプロダクト・コメント・画像の個別削除(FR-PRDCT-013・FR-COMNT-006・FR-FILEU-024)によるデータは、それぞれの論理削除から14日が経過する直前(論理削除から13日後)のバッチで処理し、画像ファイルの物理削除時は[エッジキャッシュを無効化](../features/002-image-variants.md#キャッシュとパージ)する(FR-FILEU-021)。削除のほかに、使い捨てメールアドレスの判定のやり直し(FR-USER-014)、画像の自動判定の再依頼と保存先の照合(FR-FILEU-013・016)、外部APIでのキーワード抽出のやり直し(FR-FTS-007)を行う。

日次バッチは次の表のジョブを順序の小さいものから1つずつ実行する。前のジョブが終わるまで次のジョブを始めず、1つのジョブが失敗しても後続のジョブを実行する。利用者のアカウントのジョブ(順序100〜120)は、退会ユーザーの物理削除の開始→期限切れの認証情報の削除→使い捨てメールアドレスの判定のやり直しの順に、他のドメインのジョブより前に置く。管理者のアカウントのジョブ(順序200〜210)は、利用者のアカウントのジョブの後に、期限切れの認証情報の削除→監査ログの物理削除の順に置く。問い合わせのジョブ(順序300)は、管理者のアカウントのジョブの後に置く。決済のジョブ(順序400〜410)は、問い合わせのジョブの後に、未完了の購入と依頼待ちの返金・メールの確認→決済履歴の物理削除の順に置く。Ultrasのジョブ(順序500)は決済のジョブの後に置く。送り直す知らせと依頼待ちのメールの行は決済の反映が作るためである。利用者のプロフィールのジョブ(順序600)は、Ultrasのジョブの後、メディアのジョブ(順序810)の前に置く。検索のキーワードの再抽出は各ドメインの削除の処理より後(順序2300)に置き、削除済みのデータの再抽出を要求しない。

### 参加費決済の突合(23:40)

23:40のジョブも日次バッチと同じく、順序の小さいものから1つずつ実行する。参加費決済の突合は、同時刻のマッチの確定より先に動かすため順序10とし、23:40に置く他のジョブは順序を10より大きくする。

| 順序 | ジョブの名前                       | 処理                                                                                                                                                                                                                                                                                                                                                                                                                                                           | 対応要件     |
| ---- | ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| 10   | `payments.checkout-reconciliation` | 決済期限が実行時刻以前かつ24時間以内の未反映の購入(月曜日のWeekトーナメント参加費とYearトーナメント決勝日の6日前の参加費)を、200件までStripeの決済セッションの状態と1件ずつ突合する。支払い済みなら反映し、失効・未払いなら失効にする。Stripeに到達できなかった購入は他の購入の突合を続けたうえで運用者へ通知し、200件を超えた分は翌日4:21の確認が拾う。23:45の組み合わせ決定に間に合わせるため、起動から4分を過ぎたら残りを止めて残った件数を運用者へ通知する | FR-PYMNT-013 |

| D − 6日(月)23:35 | D − 5日(火)7:35 | 参加費決済期限、ただしUIには35分前の23:00が締切と表示する。対象はこの日の前日までのWeek優勝プロダクト |

## 同時刻に走る処理の順序

毎週月曜日の23:35の決済期限から23:45の組み合わせ決定までの10分間に複数の処理が連鎖する。実装上は以下の順序を守る。

```mermaid
sequenceDiagram
    participant S as Stripe(23:35)
    participant C as Cron(23:40)
    participant M as マッチ確定
    participant P as ペアリング(23:45)
    participant N as 通知(Queue)
    S->>S: 決済期限(23:35)
    C->>C: 未反映の参加費決済を突合(月曜日・D−6日)
    C->>M: 当日マッチのUpvote数・最終Upvote時間を確定
    M->>M: 勝敗判定、ディレクトリ掲載、賞の授与
    M->>M: 翌日の不戦勝を判定(隣接マッチ両者敗北)
    P->>P: 翌日予選のペアリング
    P->>P: 月曜日ならWeekトーナメント組み合わせ、D−6日ならYearトーナメント組み合わせ
    P->>N: 勝敗結果通知・開始予告通知をenqueue
```

- マッチ確定(23:40)が完了してからペアリング(23:45)を行う。翌日のトーナメントマッチの対戦相手は当日の勝敗に依存するため
- 参加費決済の突合(23:40)はペアリング(23:45)の前に完了させる([理由](002-pricing-and-plans.md#決済期限を組み合わせ決定よりも10分早める理由))
- 決済期限(23:35)をマッチ終了より早め、UIにより早い時間を表示する理由は[料金及びプラン体系](002-pricing-and-plans.md#ui表示において決済期限を35分早める理由)を参照
- 準決勝以前でトーナメントマッチに勝利した投稿者への通知は、勝敗結果と翌日の開始予告を1通に統合する(FR-NOTIF-004)
