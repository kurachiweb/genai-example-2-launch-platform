# 日次・週次・年次タイムライン

サービスの定期処理と時刻に依存する仕様を、基準時刻(UTC-08:00)の1日の流れに沿って整理する。各処理の規則は対応要件を正とし、本書は時刻の一覧と処理順序を定める。
基準時刻は夏時間を持たない固定オフセットであり、日境界はUTCの8:00である。日時データの保持はI18N-002を、表示形式はI18N-004を正とする。

### 日次バッチ(4:21)の内容

対象データと条件は[データ保持期間の一覧](../legal/001-compliance-policy.md#データ保持期間の一覧)のうち削除方法が「日次バッチ」のものを正とする。退会ユーザーのデータ、及びプロダクト・コメント・画像の個別削除(FR-PRDCT-013・FR-COMNT-006・FR-FILEU-024)によるデータは、それぞれの論理削除から14日が経過する直前(論理削除から13日後)のバッチで処理し、画像ファイルの物理削除時は[エッジキャッシュを無効化](../features/002-image-variants.md#キャッシュとパージ)する(FR-FILEU-021)。削除のほかに、使い捨てメールアドレスの判定のやり直し(FR-USER-014)、画像の自動判定の再依頼と保存先の照合(FR-FILEU-013・016)、外部APIでのキーワード抽出のやり直し(FR-FTS-007)、通知メールの送り出しの遅れの回復(FR-NOTIF-021)、措置の通知メールの送り直し(FR-ADMUG-030)、通報の対応結果の通知の送り直し(FR-ADMUG-031・039)を行う。

日次バッチは次の表のジョブを順序の小さいものから1つずつ実行する。前のジョブが終わるまで次のジョブを始めず、1つのジョブが失敗しても後続のジョブを実行する。利用者のアカウントのジョブ(順序100〜120)は、退会ユーザーの物理削除の開始→期限切れの認証情報の削除→使い捨てメールアドレスの判定のやり直しの順に、他のドメインのジョブより前に置く。管理者のアカウントのジョブ(順序200〜210)は、利用者のアカウントのジョブの後に、期限切れの認証情報の削除→監査ログの物理削除の順に置く。問い合わせのジョブ(順序300)は、管理者のアカウントのジョブの後に置く。決済のジョブ(順序400〜410)は、問い合わせのジョブの後に、未完了の購入と依頼待ちの返金・メールの確認→決済履歴の物理削除の順に置く。Ultrasのジョブ(順序500)は決済のジョブの後に置く。送り直す知らせと依頼待ちのメールの行は決済の反映が作るためである。利用者のプロフィールのジョブ(順序600)は、Ultrasのジョブの後、メディアのジョブ(順序810)の前に置く。プロダクトのジョブ(順序1000〜1010)は、メールの後始末のジョブ(順序900)の後に、論理削除したプロダクトの物理削除の開始→未完了の後続処理の再実行の順に置く。プロダクトの後続処理の再実行は、利用者の後続処理の再実行(16:21)と異なりメールの後始末と重なる処理を持たないため、日次バッチに含める。マッチのジョブ(順序1100〜1110)は、プロダクトのジョブの後に、滞ったマッチイベントの送り直し→完了したマッチイベントの記録の削除の順に置く。通知のジョブ(順序1300)は、マッチのジョブの後に置き、送信枠の送り出しの回復→作成から30日を過ぎても展開していない通知イベントの削除→滞った通知イベントの展開のやり直し→送っていない通知の期限切れ→保持期間を過ぎた記録の削除を1つのジョブで行う。コメントのジョブ(順序1400)は、通知のジョブの後に置く。前に動く必要のある他のドメインのジョブは無く、同じ日に再び実行しても匿名化していないコメントだけを処理するため結果は変わらない。Weekトーナメントのジョブ(順序1500)は、コメントのジョブの後、検索のキーワードの再抽出の前に置く。Yearトーナメントのジョブ(順序1700)は、Weekトーナメントのジョブの後、検索のキーワードの再抽出(順序2300)の前に置く。UGC管理のジョブ(順序1900〜1910)は、Yearトーナメントのジョブの後に、週ごとの統計の集計→措置の通知の送り直しと記録の削除の順に置く。統計の集計は各機能の照会を読んで週ごとの統計だけを書き、前に動く必要のある他のドメインのジョブは無い。週の終わりの時点の総数は、その時点で退会・論理削除していない利用者・プロダクトを数え、物理削除は退会・論理削除から13日後に始まるため、週が終わってから13日以内に確定すれば同じ日次バッチの物理削除(順序100・1000)が先に動いても変わらない。保守のジョブも前に動く必要のある他のドメインのジョブは無く、措置の記録だけを読み書きし、通知の宛先は送る時点で確かめ直す。返金の依頼は決済の機能の部品が受け付け、Stripeへの返金はイベントサーバーが非同期に行うため、決済のジョブ(順序400)の後に置いても返金は翌日まで遅れない。同じ日に再び実行しても、依頼済み・知らせ済みの枠は対象にならず結果は変わらない。通報のジョブ(順序2000〜2010)は、UGC管理のジョブの後、検索のキーワードの再抽出の前に、通報の対応結果の通知の送り直し→保持期間を過ぎた通報の削除の順に置く。送り直しを削除より先に動かし、削除の前に最後の送信を試みる。どちらも通報の記録だけを読み書きし、通知の宛先は送る時点で確かめ直すため、前に動く必要のある他のドメインのジョブは無い。対象への参照の消去は利用者・プロダクトの物理削除の後続処理が行い、日次バッチのジョブではない。検索のキーワードの再抽出は各ドメインの削除の処理より後(順序2300)に置き、削除済みのデータの再抽出を要求しない。

### 23:40・23:45・0:00・0:07のジョブ

23:40・23:45・0:00・0:07のジョブも日次バッチと同じく、時刻ごとに順序の小さいものから1つずつ実行する。参加費決済の突合は、同時刻のマッチの確定より先に動かすため順序10とし、23:40に置く他のジョブは順序を10より大きくする。マッチのジョブは、どの時刻も順序1100に置く。23:40のマッチの確定は、23:45のペアリングに間に合わせるため起動から4分50秒を過ぎたら残りを止め、残りは23:45のジョブがペアリングの前に確定する。23:40・23:45・0:00のマッチのジョブは、それぞれ先頭で、確定の日時から2日以内で確定のイベントが無いマッチにイベントを作って送る。通知のジョブは、23:45・0:00とも順序1300に置き、同じ時刻のマッチのジョブ(順序1100)の後に動く。23:45の通知のジョブは夜の送信枠を開くだけで、送り出しはトーナメントのジョブ(順序1500番台・1700番台)の準備の完了を待って始まる(「[同時刻に走る処理の順序](#同時刻に走る処理の順序)」)。Weekトーナメントのジョブは、23:45に順序1500で通知のジョブの後に動き、組み合わせ決定・追いつき・進行・通知イベントの発行を全て終えてから、最後に準備の完了を伝える。Yearトーナメントのジョブは、23:45に順序1700でWeekトーナメントのジョブの後に動き、Week優勝の取り込み・組み合わせ決定・進行・通知イベントの発行を全て終えてから、最後に準備の完了を伝える。Weekトーナメントの決勝で確定したWeek優勝を同じ夜のうちに参加の枠にし、Week優勝の結果通知へYearトーナメントの決済期限を追記するためである。夜の送り出しは、前提として登録された全ての機能が準備の完了を伝えた時点、遅くとも23:55に始まる。送り出しが23:50などの決まった時刻に始まることを前提にしない。

## 同時刻に走る処理の順序

毎週月曜日の23:35の決済期限から、23:45の組み合わせ決定と通知メールの送り出し(遅くとも23:55)までに、複数の処理が連鎖する。実装上は以下の順序を守る。

```mermaid
sequenceDiagram
    participant S as Stripe(23:35)
    participant C as Cron(23:40)
    participant M as マッチ確定
    participant P as ペアリング(23:45・1100)
    participant J as 夜の送信枠を開くジョブ(23:45・1300)
    participant T as トーナメントの組み合わせ(23:45・1500番台・1700番台)
    participant G as 送り出しの入口
    participant N as 通知(Queue)
    S->>S: 決済期限(23:35)
    C->>C: 未反映の参加費決済を突合(月曜日・D−6日)
    C->>M: 当日マッチのUpvote数・最終Upvote時間を確定
    M->>M: 勝敗判定、ディレクトリ掲載、賞の授与
    M->>M: 翌日の不戦勝を判定(隣接マッチ両者敗北)
    P->>P: 翌日予選のペアリング
    J->>G: 夜の送信枠を開き、送り出しの前提の一覧を確定
    G->>N: 23:55を期限とする送り出しを予約
    T->>T: 月曜日ならWeekトーナメント組み合わせ、D−6日ならYearトーナメント組み合わせ
    T->>T: 当日に確定したマッチに追いつき、次ラウンドの予定と受賞を記録
    T->>G: 通知イベントを発行し、準備の完了を伝える
    G->>N: 全ての前提がそろえば送り出しを依頼(勝敗結果通知・開始予告通知)
```

- マッチ確定(23:40)が完了してからペアリング(23:45)を行う。翌日のトーナメントマッチの対戦相手は当日の勝敗に依存するため。23:40の確定が時間の上限で残りを止めた場合も、23:45のジョブがペアリングの前に残りを確定する
- 参加費決済の突合(23:40)はペアリング(23:45)の前に完了させる([理由](002-pricing-and-plans.md#決済期限を組み合わせ決定よりも10分早める理由))
- 決済期限(23:35)をマッチ終了より早め、UIにより早い時間を表示する理由は[料金及びプラン体系](002-pricing-and-plans.md#ui表示において決済期限を35分早める理由)を参照
- 準決勝以前でトーナメントマッチに勝利した投稿者への通知は、勝敗結果と翌日の開始予告を1通に統合する(FR-NOTIF-004)
- 夜の送信枠の送り出しは、同じ23:45のペアリング(順序1100)と通知のジョブ(順序1300)の後、送り出しの前提として登録された機能(tournament-weekの順序1500番台・tournament-yearの順序1700番台の23:45のジョブ)が処理の最後に送り出しの入口へ準備の完了を伝え、全ての機能が伝えた時点で始める。同じ日に同じ機能が繰り返し伝えても、複数の機能が伝えても、送り出しは1回だけ始まる。23:55までに伝えない機能があれば23:55に送り出しを始め、運用者へ通知する(notificationsの仮2、FR-NOTIF-014・015)。送り出しの前提を登録した機能が無い間は、23:45の通知のジョブが直ちに送り出しを依頼する
- Weekトーナメントの23:45のジョブ`tournament-week.evening-bracket`(順序1500)は、組み合わせ決定→その日に確定した予選の勝利の枠の追いつき→全トーナメントの進行(次ラウンドの予定と受賞)→その夜の通知イベント(結果・翌日の開始予告・受賞)の発行の順に行い、最後に準備の完了を伝える。トーナメントマッチの確定の直後にもイベントサーバーが同じ進行と発行を行うが、23:45のジョブがそれに追いつくため、どちらが先でも翌日0:00の開始と夜の送り出しに間に合う。いずれかが失敗した日は準備の完了を伝えず、送り出しは23:55の期限に任せる
- Yearトーナメントの23:45のジョブ`tournament-year.evening-bracket`(順序1700)は、Weekトーナメントのジョブの後に、Week優勝の取り込み→組み合わせ決定(決勝日の6日前の夜)→全トーナメントの進行(次ラウンドの予定と受賞)→その夜の通知イベント(結果・翌日の開始予告・受賞)の発行の順に行い、最後に準備の完了を伝える。Yearトーナメントの処理が無い夜も準備の完了を伝える。トーナメントマッチの確定の直後にもイベントサーバーが同じ進行と発行を行うが、23:45のジョブがそれに追いつく。いずれかが失敗した日は準備の完了を伝えず、送り出しは23:55の期限に任せる
- トーナメントのマッチ開始予告メールは、マッチ前日の23:45(その日のペアリングと組み合わせの後)の送信枠で送る。Yearトーナメントの1回戦のように組み合わせ決定がそれより前でも、前日の23:45まで送らずに保留する(notificationsの仮1、FR-NOTIF-002)
- 0:00の開催通知メールは、同じ0:00のマッチの開始(順序1100)の後に送る。開始の日時を過ぎても開始していない当日のマッチが残る間は送り出しを待つため、マッチの開始が失敗した日は、運用者が0:00のジョブを起こし直してマッチが開始した後に送られる。終了の日時まで開始しなかったマッチは待たず、開始したマッチの分だけを送る
