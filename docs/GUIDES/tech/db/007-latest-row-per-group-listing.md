# グループごとの最新の行で並べる一覧

1つのグループ(商品・記事など)に記録の行が何度も加わるデータで、グループごとに1行の基準の行(期間内で最も新しい記録など)を問い合わせの中で選び、その値で並べ替え・絞り込み・全文検索・オフセット方式のページ分けをする一覧の問い合わせの規約を定める。窓関数による基準の行の選択、窓関数の前に掛ける条件と外側に掛ける条件の分け方、並びの一意と同順位の決まった順、全文検索の副問い合わせとの結合、一覧と件数の一括の読み取り、絞り込みの選択肢の件数との一致、オフセット方式の読み取りの費用と上限、写しのテーブルへ移る判断の目安、及びテストを扱う。

## 前提と用語

ORMにDrizzle、データベースにCloudflare D1を使う構成を前提とする。テーブル定義と接続は「[データベースのスキーマ規約](003-schema-conventions.md)」に、一括の読み取りとバインド変数の上限は「[Cloudflare D1の制約と対処](002-d1-constraints.md#d1の制約と対処)」に、検索式と関連度のSQL断片は「[全文検索の索引(SQLite FTS5)](004-full-text-search.md)」に従う。画面の側の条件の持ち方は「[URLのクエリで条件を持つ一覧](../frontend/014-url-state-listing.md)」に従う。

| 用語               | 意味                                                                                                                                           |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| グループ           | 一覧の1項目になる行。記録のテーブルから外部キーで参照される側(商品・記事など)                                                                  |
| 記録               | グループに属し、何度も加わる行(評価・受賞・販売など)。1つのグループに0行以上ある                                                               |
| 基準の行           | グループごとに記録から1行だけ選び、一覧の並びと表示の値に使う行(期間内で最も新しい記録など)                                                    |
| 基準の候補         | 基準の行に選ばれ得る記録。記録の種類・期間などの、記録ごとの条件で絞る                                                                         |
| 掲載の条件         | 一覧に並べるグループの条件(公開中である・論理削除されていない・投稿者が可視である・カテゴリが一致するなど)。グループの側の現在の状態で判定する |
| 同順位の決まった順 | 並びのキーが同じ行の順を決めるため、並びの末尾に置く一意な列までの並び                                                                         |
| オフセット方式     | ページ番号から`LIMIT`・`OFFSET`で読む位置を決めるページ分け                                                                                    |
| 写しのテーブル     | 基準の行の値をグループごとに1行へ前もって写しておくテーブル。並べ替えの索引を張るために使う                                                    |

以下の例のテーブル名は、グループを`articles`、記録を`article_reviews`(記録の日付`reviewed_on`・評価`rating`)とする。本プロジェクトのテーブル名と1ページの件数は、技術ドキュメントに写さず、プロジェクト固有の値の文書「[本プロジェクト固有の値](../../../onboardings/project-values.md)」に置く。

## 問い合わせの形

一覧の1ページは、基準の候補に窓関数で順位を付ける`WITH`句と、順位が1の行をグループに結合する外側の問い合わせの1文で読む。

```sql
WITH base_reviews AS (
  SELECT r.article_id, r.id AS review_id, r.reviewed_on, r.rating,
         row_number() OVER (
           PARTITION BY r.article_id
           ORDER BY r.reviewed_on DESC, r.id DESC
         ) AS base_rank
  FROM article_reviews AS r
  WHERE r.reviewed_on >= ? AND r.reviewed_on <= ?
)
SELECT a.id, b.review_id, b.reviewed_on, b.rating
FROM articles AS a
JOIN base_reviews AS b ON b.article_id = a.id AND b.base_rank = 1
JOIN (<検索のSQL断片>) AS m ON m.source_id = a.id
WHERE <掲載の条件> AND a.category_id = ?
ORDER BY <並び順>
LIMIT ? OFFSET ?
```

- `WITH`句の期間の条件、検索の副問い合わせの結合、カテゴリの条件は、指定があるときだけ加える。
- 件数は、同じ`WITH`句と結合と条件の`COUNT(*)`の文で読み、一覧の文と1回の一括の読み取りにする(「[一覧と件数の一括の読み取り](#一覧と件数の一括の読み取り)」)。

Drizzleでは、`WITH`句を`db.$with()`で作り、一覧と件数の両方の文に`.with()`で渡す。条件で結合を加える文は`$dynamic()`にする。

```typescript
const BASE_RANK = 1;

function baseReviewsOf(db: Database, from?: string, to?: string) {
  return db.$with('base_reviews').as(
    db
      .select({
        articleId: articleReviews.articleId,
        reviewId: sql<string>`${articleReviews.id}`.as('review_id'),
        reviewedOn: articleReviews.reviewedOn,
        rating: articleReviews.rating,
        rank: sql<number>`row_number() over (partition by ${articleReviews.articleId} order by ${articleReviews.reviewedOn} desc, ${articleReviews.id} desc)`.as(
          'base_rank',
        ),
      })
      .from(articleReviews)
      .where(
        and(
          from === undefined ? undefined : gte(articleReviews.reviewedOn, from),
          to === undefined ? undefined : lte(articleReviews.reviewedOn, to),
        ),
      ),
  );
}

const baseReviews = baseReviewsOf(db, input.from, input.to);
const joinsBaseReview = and(
  eq(baseReviews.articleId, articles.id),
  eq(baseReviews.rank, BASE_RANK),
);
const pageQuery = db
  .with(baseReviews)
  .select({
    articleId: articles.id,
    reviewId: baseReviews.reviewId,
    reviewedOn: baseReviews.reviewedOn,
    rating: baseReviews.rating,
  })
  .from(articles)
  .innerJoin(baseReviews, joinsBaseReview)
  .$dynamic();
```

- 基準の候補を別の部品の副問い合わせ(`.as('<別名>')`で別名を付けたもの)から読む場合は、部品を呼んだ戻り値を変数に受け、その変数の列で参照する(`const reviews = publishedReviews(); reviews.articleId`)。部品の関数そのものの属性としては参照できない。
- `WITH`句の名前と順位の列の別名(`base_reviews`・`base_rank`)は、一覧の問い合わせごとに決め、他の問い合わせの列の名前と重ねない。

## 基準の行の選択

基準の行は、窓関数`row_number()`で基準の候補に順位を付け、順位が1の行をグループに内部結合して選ぶ。

- `PARTITION BY`にグループの列、`ORDER BY`に基準を決める列(記録の日付など)を置く。
- `ORDER BY`の末尾に記録の一意な列(主キー)を加え、並びを一意にする。並びが一意でないと、同じ値の記録のどれが1位になるかが実行ごとに変わり得て、同じ条件の一覧で表示の値やページの境界が変わる。
  - 一意索引などの制約で、同じグループに同じ値の記録が無いことが保証される場合(1つのグループの記録が1日に1行までで、日付で並べるなど)は、一意な列を省いてよい。省いた場合は、保証する制約をコードのコメントに書く。
- 外側の問い合わせは`base_rank = 1`を結合の条件に含めて内部結合する。基準の候補が無いグループは結合で除かれる。
- `GROUP BY`と`MAX()`でグループごとの最新の値を求める書き方は使わない。最新の値は求まるが、その行の他の列(記録のID・評価)を同じ行から取り出すには、SQLiteだけの集約しない列の扱い(集約関数が`MAX()`・`MIN()`の1つだけのとき、その行の値を返す)に頼るか、同じ値で結合し直す必要がある。

## 条件の掛け方

### 窓関数の前に掛ける条件

どの記録を基準の候補にするかの条件(記録の種類・期間)は、`WITH`句の中、窓関数の前に掛ける。

| 期間の条件の位置                                     | 期間内に古い記録と、期間の後に新しい記録を持つグループ             |
| ---------------------------------------------------- | ------------------------------------------------------------------ |
| 窓関数の前(`WITH`句の`WHERE`)                        | 期間内の古い記録が基準の行になり、一覧に並ぶ                       |
| 窓関数の後(外側の`WHERE`で`base_rank = 1`の行を絞る) | 期間の後の新しい記録が基準の行になって期間で除かれ、一覧に並ばない |

- 期間の条件は、指定があるときだけ加える。`? IS NULL OR reviewed_on >= ?`のように値によらない1つの文にすると、意味は同じでも、記録の日付の索引を範囲の読み取りに使えない場合がある。
- 期間の両端は、記録の日付と同じ表現(業務日付の文字列など)で比べ、開始日と終了日の当日の記録を含める(`>=`・`<=`)。
- 基準の候補の条件に使う列(記録の種類・記録の日付)に索引を張り、`WITH`句が期間の範囲だけを読むようにする。

### 外側に掛ける条件

どのグループを並べるかの条件(掲載の条件・カテゴリ)は、外側の問い合わせのグループの側に掛ける。

- 掲載の条件は、グループと関連する行(投稿者など)の現在の状態から読み取りの時点で判定する。写しを持たないため、非公開化・論理削除・投稿者の停止と退会・カテゴリの変更が、次の読み取りから反映される。
- グループの条件は窓関数の順位を変えないため、`WITH`句の中に入れない。`WITH`句に入れると、記録の行ごとにグループと関連する行を結合して判定することになる。
- カテゴリの絞り込みは、掲載の条件に`a.category_id = ?`を加えて掛け、一覧と件数の両方に同じ条件を渡す。

## 並び順と同順位の決まった順

並び順の選択肢ごとに、基準の行の値のキーの後に同順位の決まった順を置き、最後はグループの一意な列(主キー)にする。

| 並び順         | `ORDER BY`                                     |
| -------------- | ---------------------------------------------- |
| 新しい順       | `b.reviewed_on DESC, a.id DESC`                |
| 古い順         | `b.reviewed_on ASC, a.id ASC`                  |
| 評価の高い順   | `b.rating DESC, b.reviewed_on DESC, a.id DESC` |
| 関連度の高い順 | `m.rank ASC, b.reviewed_on DESC, a.id DESC`    |

- オフセット方式は、ページごとに並びを作り直す。並びが一意でないと、同順位の行の順がページごとに変わり、ページをまたいで同じ項目が重複し、別の項目が欠ける。
- 逆向きの並び(古い順)は、全てのキーの向きを逆にする。新しい順をちょうど逆にした順になる。
- 関連度の`rank`は`bm25()`の値で、小さいほど関連度が高いため昇順にする(「[検索のSQL断片](004-full-text-search.md#検索のsql断片)」)。
- 検索語が無いときの関連度の高い順は、関連度の値が無いため、既定の並び(新しい順)と同じ並びにする。並び順の選択肢を画面で選べなくしても、APIが受け付けた値で失敗させない。
- 並び順の組み立ては、並び順の値から`ORDER BY`の式の配列を返す関数にまとめ、`switch`で全ての値を扱う。値を足したときに型検査で漏れが分かる。

## 全文検索との結合

検索語があるときは、`ftsRankedSources`の副問い合わせをグループと`source_id`で内部結合する(「[検索のSQL断片](004-full-text-search.md#検索のsql断片)」)。

```typescript
const SEARCH_MATCHES = sql.raw('article_search_matches');

const search =
  matchExpression === undefined
    ? undefined
    : {
        source: sql`(${ftsRankedSources(ARTICLE_SEARCH_INDEX, matchExpression)}) AS ${SEARCH_MATCHES}`,
        joinsArticle: sql`${SEARCH_MATCHES}.source_id = ${articles.id}`,
        rank: sql<number>`${SEARCH_MATCHES}.rank`,
      };

const searchedPage =
  search === undefined
    ? pageQuery
    : pageQuery.innerJoin(search.source, search.joinsArticle);
```

- 一覧と件数の両方に同じ副問い合わせを結合する(件数の文も同じ形で`searchedCount`にする)。件数だけ結合しないと、検索で絞った一覧と検索前の総件数が並ぶ。
- 検索の副問い合わせは一致したグループの絞り込みと関連度だけに使い、掲載の条件は外側でグループの側から判定する。索引文書は索引の更新の遅れで元データより古いことがあり、非公開化したグループの索引文書が残っていても一覧に並べない。
- 検索式は、呼び出し側が共用部品の`normalizeSearchTerms`と`buildFtsMatchExpression`で作って渡す(「[検索式](004-full-text-search.md#検索式)」)。検索式が無い(語が無い)ときは副問い合わせを結合しない。検索の問い合わせの部品は検索式だけを受け、利用者の入力を受けない。
- 副問い合わせの別名は`sql.raw()`の固定の文字列にし、利用者の入力を含めない。

## 一覧と件数の一括の読み取り

一覧の1ページと総件数は、同じ`WITH`句・結合・条件の2つの文にし、1回の`db.batch()`で読む。

```typescript
const [rows, totals] = await db.batch([
  searchedPage
    .where(listedCondition)
    .orderBy(...orderOf(input.sort, baseReviews, search))
    .limit(PAGE_SIZE)
    .offset((input.page - 1) * PAGE_SIZE),
  searchedCount.where(listedCondition),
]);
const totalCount = totals[0]?.total ?? 0;
```

- 一括の読み取りは、1回の呼び出しとして数えられ、1つのトランザクションとして実行される(「[複数テーブルへの書き込みをまとめる](002-d1-constraints.md#複数テーブルへの書き込みをまとめる)」)。2回に分けて読むと、間に入った書き込みで総件数と一覧が食い違い得る。
- 件数の文も`base_rank = 1`で結合するため、記録の数ではなくグループの数を数える。件数の文には`ORDER BY`・`LIMIT`を付けない。
- 一覧の文と件数の文は、同じ関数で作った`WITH`句と条件の値を共有し、片方だけに条件を加えない。
- 総ページ数は`ceil(総件数 / 1ページの件数)`とし、0件なら0にする。総ページ数を超えるページ番号は失敗にせず、空の一覧と総件数を返す。画面はこの組み合わせ(空の一覧で総件数が1以上)を範囲外のページとして示す。
- 1ページの件数は定数にし、利用者の入力から受け取らない。
- 結合したテーブルに同じ名前の列がある場合は、一括の読み取りの結果が列の名前で写されるため別名を付ける(「[複数テーブルへの書き込みをまとめる](002-d1-constraints.md#複数テーブルへの書き込みをまとめる)」)。

## 絞り込みの選択肢の件数

絞り込みの選択肢に添える件数(カテゴリごとの件数など)は、窓関数を使わず、カテゴリの条件を含まない掲載の条件(`listedWithoutCategory`)だけで`GROUP BY`で数えてよい。

```typescript
const rows = await db
  .select({ categoryId: articles.categoryId, listed: count(articles.id) })
  .from(articles)
  .where(listedWithoutCategory)
  .groupBy(articles.categoryId);
```

- この件数は、検索語と期間を指定しない一覧の、そのカテゴリの総件数と一致しなければならない。掲載の条件が「基準の候補の記録を1行以上持つ」ことを含み、掲載の条件を満たすグループが必ず基準の行を持つことを前提にする。前提が崩れる変更(基準の候補の条件を狭める・掲載の条件から記録の有無を外す)では、件数の数え方も見直す。
- 一致はWorkers統合テストで確かめる(「[テスト](#テスト)」)。
- 件数の無いカテゴリは結果に含まれないため、呼び出し側は0として扱う。

## オフセット方式の費用と上限

- `OFFSET`は読み飛ばす行も読むため、後ろのページほど読み取りが増える。加えて、窓関数は期間内の基準の候補を全て読んでから順位を付けるため、1ページの読み取りは基準の候補の数に比例する。件数の文も同じ`WITH`句を読む。
- ページ番号は、安全な整数の範囲の2以上の値だけを受け、それ以外は1ページ目として扱う。範囲外の大きな値は、空の一覧を返すだけで失敗にしない。
- URLでページ番号を共有でき、総件数と総ページ数を示す一覧にはオフセット方式を使う。続きを後ろに加える一覧や、総件数を示さない一覧には、並びのキーの組を位置にしたカーソルによる一覧を使う(「[利用者間の関係の保存と一覧](006-user-relationship-lists.md#一覧)」)。
- 1文で使うバインド変数は、期間の両端・検索式・カテゴリ・件数・オフセットの数個で、上限(「[バインド変数の上限](002-d1-constraints.md#バインド変数の上限)」)に近づかない。

## 写しのテーブルへ移る判断の目安

写しのテーブルを持たずに、毎回の読み取りで基準の行を選ぶ形を既定にする。掲載の条件の変化(非公開化・論理削除・投稿者の停止と退会・カテゴリの変更)が次の読み取りから反映され、写しを直す処理と、写しと元データの食い違いが無い。

写しのテーブルへ移るのは、次の全てに当てはまる場合とする。

- 想定する最大の記録の数で合成したデータの性能の検証で、一覧の応答時間がプロジェクトの目標を超える。
- 期間の条件を窓関数の前に掛け、記録の種類と日付の索引を張っても、目標に届かない。
- 写しを直す処理を、掲載の条件を変える全ての経路(記録の追加・グループの状態の変化・関連する行の状態の変化)に足せる。

写しのテーブルは、期間を指定しない基準の行(全期間で最新の記録)しか前もって持てない。利用者が期間を自由に選べる一覧では、期間を指定した読み取りに窓関数の形が残るため、写しは期間を指定しない一覧の並べ替えにだけ使う。

## テスト

一覧の問い合わせは、Workers統合テストで実物のD1に記録とグループを書いて確かめる。

- 基準の行: 記録を複数持つグループが1項目になり、最新の記録の値を持つこと。基準の候補でない記録(別の種類の記録)が後にあっても基準の行にならないこと。
- 期間: 開始日・終了日と同じ日の記録を含むこと、期間外の記録だけを持つグループを除くこと、期間内の古い記録が基準の行になること、開始日だけ・終了日だけの期間。記録の日付を業務日付で持つ場合は、基準の時刻の0時の直前と直後の記録の日付。
- 掲載の条件: 条件ごとに外れるグループ(非公開・論理削除・投稿者の停止と退会・基準の候補が無い)を一覧と件数の両方から除くこと、停止の解除・非公開の解除で再び並ぶこと。
- 並び順: 並び順の選択肢ごとに、同じ値のグループが同順位の決まった順に並ぶこと。
- ページ分け: 1ページの件数の境目(最後の項目と次のページの最初の項目)が重複も欠落もしないこと、総ページ数を超えるページが空の一覧と総件数を返すこと。
- 一括の読み取り: D1の`prepare`と`batch`を数える包みで接続を作り、1回の一覧の読み取りが2つの文の1回の一括の読み取りであることを確かめる。
- 全文検索: 検索で絞った件数が総件数になること、関連度が同じ項目が同順位の決まった順に並ぶこと、索引文書が残っていても掲載の条件を外れたグループを並べないこと。
- 絞り込み: カテゴリと期間・検索・並び順の組み合わせ、選択肢の件数とカテゴリの絞り込みの総件数の一致。
- テストの種別と命名は「[テストの種別と命名](../testing/001-test-strategy.md#テストの種別と命名)」に従う。
