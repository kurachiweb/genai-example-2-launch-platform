# 最初の最上位管理者の用意

管理者が1人もいない環境で最初の最上位管理者を用意する、招待の発行コマンドの目的・実行者・引数・環境ごとの手順・出力とリンクの扱い・失敗の扱いを定める。最後の最上位管理者が認証の手段を失って締め出された場合の手順も扱う。

## 前提と用語

管理者の状態・ロール・最後の最上位管理者の保護は「[管理者の認可の設計](../security/007-admin-authorization.md)」に、トークンのハッシュ化は「[秘密情報のハッシュ化](../security/002-keyed-hashing.md)」に、Infisicalの環境種別は「[シークレット管理の環境種別](../infra/002-environments.md#シークレット管理の環境種別)」に、ローカルのD1の操作は「[ローカル状態の永続化と共有](../infra/001-wrangler-conventions.md#ローカル状態の永続化と共有)」に従う。

| 用語                             | 意味                                                                                                                                       |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 招待の発行コマンド               | 最上位管理者ロールの招待中の管理者と招待の認証系トークンを、指定した環境のデータベースへ直接書き込み、招待のリンクを端末に表示するコマンド |
| `<招待の発行コマンド>`           | 招待の発行コマンドを起動するパッケージのスクリプト。`<APIサーバーのアプリ>`のディレクトリで実行する                                        |
| 対象の環境                       | コマンドの`--target`で指定する書き込み先。`local`(ローカル環境)・`staging`(デプロイ先検証環境)・`prod`(本番環境)                           |
| 締め出し                         | 最後の有効な最上位管理者が、認証アプリとリカバリコードを両方失い、ログインも本人確認もできなくなった状態                                   |
| `<ペッパーのシークレットのキー>` | 「[秘密情報のハッシュ化](../security/002-keyed-hashing.md#前提と用語)」と同じ                                                              |
| `<ローカル状態の保存先>`         | 「[ローカル状態の永続化と共有](../infra/001-wrangler-conventions.md#ローカル状態の永続化と共有)」と同じ                                    |

- `<招待の発行コマンド>`の本プロジェクトでの名前と引数、`<ペッパーのシークレットのキー>`の名前は、技術ドキュメントに写さず、プロジェクト固有の値の文書(「[本プロジェクト固有の値](../../../onboardings/project-values.md)」)に置く。

## 目的と実行者

- 招待の発行コマンドは、管理画面の招待(最上位管理者以外のロールで招待し、招待のメールを送る)を使える管理者がいない環境で、最初の最上位管理者を用意するために使う。既に最上位管理者がいる環境でも実行でき、締め出しからの復旧にも使う(「[最上位管理者が締め出された場合](#最上位管理者が締め出された場合)」)。
- コマンドは管理画面とAPIサーバーに公開された入口を持たない。対象の環境のデータベースへ書き込める資格情報と、`<ペッパーのシークレットのキー>`の値を持つ開発者だけが実行できる。
- 招待のメールを送らず、操作者となる管理者がいないため監査ログにも記録しない。

| 対象の環境        | 実行者                            | 用途                                                     |
| ----------------- | --------------------------------- | -------------------------------------------------------- |
| `local`           | 開発者・AIエージェント・E2Eテスト | ローカル環境の管理者の用意、管理画面のE2Eテストの補助    |
| `staging`・`prod` | 開発者だけ                        | デプロイ先の最初の最上位管理者の用意と締め出しからの復旧 |

- `staging`・`prod`を対象にした実行は、AIエージェントの設定の拒否の一覧(Claude Codeでは`permissions.deny`)に載せ、技術的にも拒否する(「[AIエージェントが実行しない操作](001-deployment.md#aiエージェントが実行しない操作)」)。コマンドは子のプロセスとしてWranglerを起動するため、`--remote`を付けた`wrangler d1`のコマンドの拒否の規則には一致しない。`<招待の発行コマンド>`に`--target staging`・`--target prod`を付けた形を、初回の準備で開発者が拒否の一覧に加える(「[初回の準備](001-deployment.md#初回の準備)」)。引数は`--target=staging`のように`=`で繋いでも受け付けるため、どちらの形にも一致する規則にする。加えるまでは、AIエージェントが実行できてしまうリスクが残る。

## 引数

```sh
<招待の発行コマンド> -- --target <対象の環境> --email <メールアドレス>
```

| 引数       | 規則                                                                                                      |
| ---------- | --------------------------------------------------------------------------------------------------------- |
| `--target` | 必須。`local`・`staging`・`prod`のいずれか                                                                |
| `--email`  | 必須。前後の空白を除き、メールアドレスの長さの上限以内で、HTML5の`type="email"`の形式に合うメールアドレス |

- 引数の誤り(不明な引数・位置引数・指定の無い環境・形式の誤ったメールアドレス)は、何も書き込まずに理由と使い方を表示して失敗する。
- メールアドレスは大文字小文字を区別せずに既存の管理者と照合する。

| 指定したメールアドレスの管理者 | 書き込み                                                                                                       |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| いない                         | 最上位管理者ロールの招待中の管理者と、招待のトークンを作る                                                     |
| 招待中(ロールを問わない)       | その管理者を最上位管理者ロールにして招待の期限を延ばし、未使用の招待のトークンを消してから新しいトークンを作る |
| 有効                           | 何も書き込まず、既に有効な管理者がいる旨を表示して失敗する                                                     |

## 環境ごとの手順

コマンドは`<ペッパーのシークレットのキー>`を環境変数から読み、トークンのハッシュを作る。対象の環境と同じ環境のペッパーをInfisicalで注入して、`<APIサーバーのアプリ>`のディレクトリで実行する。別の環境のペッパーで作ったハッシュはアプリのハッシュと一致せず、リンクが無効になる。

| 対象の環境 | Infisicalの環境種別 | Wranglerの書き込み先                                        |
| ---------- | ------------------- | ----------------------------------------------------------- |
| `local`    | `dev`               | `--local --persist-to <ローカル状態の保存先>`のローカルのD1 |
| `staging`  | `staging`           | `--remote --env staging`のデプロイ先のD1                    |
| `prod`     | `prod`              | `--remote --env prod`のデプロイ先のD1                       |

### ローカル環境

```sh
infisical run --env dev -- <招待の発行コマンド> -- --target local --email admin@test.example
```

- ローカルのD1にマイグレーションを適用してから実行する。APIサーバーを起動していなくても書き込める。
- 表示されたリンクを、起動した管理者側のフロントエンドで開いて招待を完了する。

### デプロイ先(staging・prod)

1. 対象の環境のデータベースにマイグレーションが適用され、管理者側のフロントエンドがデプロイ済みであることを確かめる。
2. Wranglerがデプロイ先のD1へ書き込める資格情報(その環境の`/ci/cloudflare`のCloudflareのAPIトークン。「[ロールバックと復旧の実行者](002-rollback-and-recovery.md#実行者)」と同じ)と、その環境のペッパーを注入して実行する。

```sh
infisical run --env <環境種別> --path /ci/cloudflare -- \
  infisical run --env <環境種別> -- \
  <招待の発行コマンド> -- --target <環境種別> --email <メールアドレス>
```

3. 表示されたリンクを、招待する本人にだけ安全な経路で渡す。本人がリンクを開き、ニックネーム・パスワード・認証アプリの登録・リカバリコードの保存を済ませると、最上位管理者として有効になる。
4. 2人目以降の管理者は、最上位管理者が管理画面から招待する。招待の発行コマンドを日常の招待に使わない。

- ペッパーはコマンドだけが使い、子のプロセスのWranglerには渡さない。
- prodでの実行は、本番環境の公開を担う開発者が行う。

## 出力とリンクの扱い

成功すると、標準出力に次の行を表示して終了コード0で終わる。

```text
最上位管理者の招待を発行しました(環境: <対象の環境>)。招待のメールは送っていません。
招待のリンク: <招待の完了の画面のURL>#token=<トークン>
有効期限: <UTCの日時> [<ISO 8601の日時>]
このリンクは再表示できません。招待する本人にだけ渡してください。
```

- 招待中の管理者を最上位管理者にした場合は、その旨と、未使用の招待のリンクを無効にした旨の行が加わる。
- トークンはアプリのメールのリンクと同じく、サーバーへ送られないフラグメントに置く。招待の完了の画面のオリジンは、対象の環境の管理者側のフロントエンドのオリジンで、Wrangler設定の値と一致することをコマンドの単体テストで確かめる。
- リンクの有効期限は24時間で、招待中の管理者の招待の期限も同じ時刻になる。
- トークンの平文は端末への表示にだけ使い、データベース・一時ファイル・ログに残さない。端末のログや共有の画面にリンクを残さない。リンクを失った・期限が切れたときは、同じメールアドレスで実行し直して新しいリンクを発行する。前のリンクは無効になる。
- 書き込みのSQLは、OSの一時ディレクトリの中に作るディレクトリへ、所有者だけが読み書きできる権限(0600)のファイルとして書き、トークンのハッシュだけを含める。実行の後に削除する。

## 失敗の扱い

失敗すると、標準エラー出力に理由を表示して終了コード1で終わる。

| 状況                                                 | 書き込み                       | 対処                                                                                                 |
| ---------------------------------------------------- | ------------------------------ | ---------------------------------------------------------------------------------------------------- |
| 引数の誤り                                           | しない                         | 表示された使い方に従って引数を直す                                                                   |
| ペッパーが注入されていない                           | しない                         | 表示された注入付きのコマンドで実行し直す                                                             |
| 指定したメールアドレスの管理者が有効                 | しない                         | 別のメールアドレスを使う。既存の管理者のパスワードを忘れた場合は、管理画面のパスワードリセットを使う |
| 管理者の照会の失敗(Wranglerの失敗・結果の形式の誤り) | しない                         | Wranglerの出力を確かめ、資格情報・マイグレーションを直して実行し直す                                 |
| 書き込みの失敗                                       | ローカルのD1では全体を取り消す | Wranglerの出力を確かめて実行し直す                                                                   |
| 一時ファイルの削除の失敗                             | 済んでいる場合がある           | 表示されたパスのファイルを手作業で削除する。書き込みの失敗が重なった場合はその理由も表示される       |

- 照会の後、書き込みまでの間に同じメールアドレスの管理者が有効になると、トークンの挿入が招待中の管理者を見つけられずにNOT NULLの違反で失敗し、書き込み全体が取り消される。
- ローカルのD1では、ファイルの書き込みが1つでも失敗すると全体が取り消される。デプロイ先のD1で書き込みが失敗した場合も、同じメールアドレスで実行し直せば、作られた招待中の管理者を最上位管理者にしてトークンを置き換えるため、重複した管理者は作られない。

## 最上位管理者が締め出された場合

管理者の認証の手段を回復する機能は設けない。リカバリコードが認証アプリを失ったときの唯一の予備の手段である。

| 失ったもの                                        | 手順                                                                                                                                                                                                                         |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| パスワードだけ                                    | ログイン画面のパスワードリセットで再設定する。多要素認証の設定は変わらない                                                                                                                                                   |
| 認証アプリだけ(リカバリコードが2つ以上残っている) | リカバリコードでログインし、自分のアカウントのページで多要素認証を再設定する。ログインで1つ、再設定の開始の本人確認でもう1つを使うため、残りが1つだけなら、認証アプリとリカバリコードの両方を失った場合(下の2行)の手順になる |
| 認証アプリとリカバリコードの両方                  | 他に有効な最上位管理者がいれば、その管理者が締め出されたアカウントを削除し、必要なら管理画面から招待し直す                                                                                                                   |
| 最後の最上位管理者の、認証アプリとリカバリコード  | 次の手順で、招待の発行コマンドで新しい最上位管理者を用意する                                                                                                                                                                 |

1. 締め出された管理者とは別のメールアドレスで、招待の発行コマンドを実行する。締め出された管理者のメールアドレスは有効な管理者のものなので、コマンドは何も書き込まずに失敗する。
2. 新しい最上位管理者が招待を完了してログインする。
3. 有効な最上位管理者が2人になるため、新しい最上位管理者が管理者アカウントの一覧から、締め出された管理者を削除する。削除は監査ログに記録される。
4. 元の担当者が引き続き管理者を務めるときは、削除の後に、元のメールアドレスで管理画面から招待し直すか、招待の発行コマンドを実行する。

- データベースを直接編集して認証の手段を消したり、ロールを書き換えたりしない。監査ログに残らない変更になり、管理者のテーブルの不変条件(有効な管理者は有効なTOTPを持つ)を壊す。
- 管理者は自分自身を削除できない。最後の最上位管理者は、降格も削除もできない(「[最後の最上位管理者の保護](../security/007-admin-authorization.md#最後の最上位管理者の保護)」)。

## テスト

- 引数の検証・照会の結果による分岐・SQLの組み立て・出力の行・失敗の表示・一時ファイルの削除は、Wrangler・一時ファイル・トークンの生成・時刻・IDを差し替えた単体テストで確かめる。
- SQLは、全てのマイグレーションをメモリ上のSQLiteに適用して実行し、作られる行と、照会の後に有効になった管理者での失敗を確かめる。
- 文字列のリテラルは、`'`を二重にして囲み、制御文字を拒否する部品で作る。E2Eテストでローカルのデータベースを操作する補助も同じ部品を使う。
- E2Eテストは`--target local`だけを使い、コマンドの出力のリンクから画面で招待を完了させて管理者を用意する。ペッパーを要するため、E2EテストをInfisicalの注入の下で実行する。
