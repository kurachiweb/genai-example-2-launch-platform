# 入力値バリデーション

利用者の入力を、画面のフォームとAPIサーバーの両方で同じ規則で検証する方式を定める。規則の置き場所と共有の仕方、サーバーの検証を正とする分担、文字数の数え方、使用できない文字、前後の空白の扱い、違反の順序と文言、エラーの詳細の欄名とフォームの欄の対応を扱う。フォームの部品の使い方は「[共通化の対象のフォーム](../frontend/005-shared-components.md#フォーム)」に、GraphQLのリゾルバでの引数の検証は「[引数の検証](../backend/004-graphql-server.md#引数の検証)」に、マークダウンの項目の検証規則は「[マークダウンの検証規則](../frontend/008-markdown-editor-and-content.md#検証規則)」に従う。

## 前提と用語

検証にZod、画面のフォームにReact Hook Form、APIサーバーとの通信にGraphQLを使う構成を前提とする。共用部品・画面の共通部品・`<共用部品の配置先>`・`<共通部品の配置先>`は「[共有ディレクトリの配置方式](003-shared-directories.md#用語)」の用語に従う。本文書では、さらに次の用語を使う。

| 用語             | 意味                                                                                                                              |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 入力規則         | 1つの項目の上限の定数と、値を受け取って違反の種類を返す判定の関数の組。Zodに依存しない                                            |
| 検証規則         | 入力規則に違反の文言を対応させたZodのスキーマ。画面のフォームとAPIサーバーの引数の検証に渡す                                      |
| 欄の詳細         | 検証の失敗の項目ごとの詳細(`field`・`code`・`message`)。APIサーバーは共通のエラー形式の`details`に入れて返す                      |
| 書記素           | 利用者が1文字と認識する単位。結合文字・異体字セレクタ・ZWJで結合した絵文字・国旗の絵文字は、複数のコードポイントでも1書記素である |
| 空白             | Unicodeの`White_Space`の性質を持つ文字(`\p{White_Space}`)。半角空白・全角空白・タブ・改行・ノーブレークスペースなどを含む         |
| 使用できない文字 | 対になっていないサロゲート、タブ・LF・CR以外のC0制御文字、DEL、C1制御文字                                                         |

## 規則の置き場所

入力規則と検証規則は、画面とAPIサーバーの両方が読み込める共用部品(`<共用部品の配置先>`)に置き、両方で同じものを使う。画面とAPIサーバーで別々に書くと、上限や空白の扱いが食い違い、画面では通った入力がサーバーで拒まれる(またはその逆が起きる)。

| 置き方                                            | 共用部品に置くもの                                                                    | 各アプリが書くもの                                      | 向いている項目                                                                                                      |
| ------------------------------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 検証規則ごと共有する                              | 項目名と上限を引数に取り、文言を含むZodのスキーマを返す関数                           | スキーマを組み合わせた入力の全体の形                    | 文言が項目名と上限だけで決まり、同じ形の項目が多い(マークダウンの本文など)                                          |
| 入力規則と文言を共有し、Zodのスキーマは各側で包む | 上限の定数・判定の関数と、違反の種類から文言への対応                                  | 判定と文言の対応を包んだZodのスキーマ                   | 文言が項目名と上限だけで決まるが、各側で検証の置き場所が異なる(画面はフォームの規則、APIサーバーはユースケースなど) |
| 入力規則を共有し文言は各側で持つ                  | 上限の定数と、違反の種類(`'empty' \| 'too-long'`など)か違反の無いことを返す判定の関数 | 違反の種類から文言への対応と、判定を包んだZodのスキーマ | 項目ごとに文言が異なる、複数の項目の組で判定する、上限を文言に入れる書き方が項目ごとに違う                          |

- 共用部品の検証規則は、モジュールの読み込み時にスキーマを作らず、呼ばれた時に作る関数にする。画面のアプリはZodの実行時のコード生成の試行を止める設定を済ませてからスキーマを作る必要があり(「[実行時のコード生成を試すライブラリ](../frontend/003-frontend-server-security.md#実行時のコード生成を試すライブラリ)」)、関数にすると設定より先に作られることが無い。
- 画面のアプリでは、Zodの値を画面の共通部品の`utilities/validation/zod.ts`から読み込む。共用部品の検証規則は`zod`を直接読み込むが、同じZodの実体を使うため設定が効く。
- 入力規則を共有し文言を各側で持つ場合は、画面とAPIサーバーの文言を同じにする(文言規則の文言)。文言に上限を入れる時は、文字列に書き写さず入力規則の定数から組み立てる。
- 入力規則と文言を共有する場合は、判定の関数と同じファイルに、違反の種類から文言への対応(`<項目名>_MESSAGES`)を置く。同じ形の項目が複数あれば、項目名と上限から対応を作る関数で組み立てる。各側は判定の結果で対応を引き、Zodのスキーマ(画面のフォーム・APIサーバーの引数の検証)やユースケースの違反のエラーの文言に使う。文言を書き写さないため、画面とAPIサーバーの文言が必ず一致する。共用部品はZodのスキーマを持たないため、モジュールの読み込み時にスキーマを作る心配も無い。
- 入力規則の判定は、Zodに依存しない関数にする。同じ判定を、Zodのスキーマの外(ドメインの規則の中で入力規則の上限を使う場合など)でも使えるためである。
- 違反の無いことは、`'ok'`のような値でも`undefined`でも表してよい。`'ok'`は文言の対応に`ok: undefined`の行を置いて全ての戻り値を引けるようにし、`undefined`は違反の種類だけを文言の対応に置いて、引く前に`undefined`を除く。同じ機能の判定の関数どうしは、どちらかに揃える。
- 共用部品は画面の部品・Workersの実行環境・データベースに依存できない(「[共有ディレクトリの配置方式](003-shared-directories.md#用語)」の共用部品)。項目の判定にデータベースの照会(重複の確認など)が要る規則は、共用部品に置かずAPIサーバーのユースケースで行う。

```typescript
// <共用部品の配置先>/<機能>/<機能>-input-rules.ts
import { countGraphemes } from '../text/graphemes.ts';
import { trimWhiteSpace } from '../text/white-space.ts';

export const DISPLAY_NAME_MAX_GRAPHEMES = 25;

export type DisplayNameCheck = 'ok' | 'empty' | 'too-long';

export const checkDisplayName = (value: string): DisplayNameCheck => {
  const graphemes = countGraphemes(trimWhiteSpace(value));
  if (graphemes === 0) {
    return 'empty';
  }
  return graphemes > DISPLAY_NAME_MAX_GRAPHEMES ? 'too-long' : 'ok';
};
```

```typescript
// 画面のフォームとAPIサーバーの引数の検証のそれぞれで、入力規則をZodのスキーマに包む
const DISPLAY_NAME_MESSAGES = Object.freeze({
  ok: undefined,
  empty: '表示名を入力してください。',
  'too-long': `表示名は${String(DISPLAY_NAME_MAX_GRAPHEMES)}文字以内で入力してください。`,
});

const displayName = z
  .string()
  .superRefine((value, context) => {
    const message = DISPLAY_NAME_MESSAGES[checkDisplayName(value)];
    if (message !== undefined) {
      context.addIssue({ code: 'custom', message });
    }
  })
  .transform(trimWhiteSpace);
```

## サーバーの検証を正とする

画面の検証は、送信の前に利用者へ誤りを示すためのもので、入力を守る役目はAPIサーバーの検証が負う。画面の検証を通らない要求も、APIサーバーへは直接送れるためである。

- APIサーバーは、画面で検証した項目も含め、全ての入力を検証し直す。GraphQLのリゾルバでは`withValidatedArgs`に検証規則を渡す(「[引数の検証](../backend/004-graphql-server.md#引数の検証)」)。
- データベースの照会や外部サービスが要る判定(重複・漏洩の照合など)は、APIサーバーのユースケースだけで行い、違反は欄の詳細を持つ`AppError`で返す。画面はその詳細を欄のエラーとして示す(「[エラーの詳細の欄名とフォームの欄の対応](#エラーの詳細の欄名とフォームの欄の対応)」)。
- 照合の対象になるだけで形式に意味の無い値(メールのリンクのトークン・セッションの識別子など)は、形式の誤りを検証で細かく拒まず、ユースケースが「照合できない」として扱う。引数の検証では、長すぎる値で処理量が増えないよう、長さの上限だけを確かめる。
  - 例外として、外部サービスが戻り先のURLに付けて渡す識別子のように、利用者が入力しない値で、形式の誤りを示しても存在の有無が漏れないものは、照合の前に形式を確かめ、形式の誤りを欄の詳細を持つ検証の誤りとして返してよい。
- 画面の検証の文言とAPIサーバーの文言は同じにする。画面の検証をすり抜けた入力でも、利用者に同じ文言が欄のエラーとして示される。

## 文字数の数え方

文字数の上限は、項目の性質に合わせて数え方を選び、選んだ数え方を入力規則に1か所だけ書く。画面のカウンターと検証規則は同じ数え方を使う。

| 数え方                 | 関数                                            | 使う項目                                                                                         |
| ---------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 書記素                 | 共用部品の`text/graphemes.ts`の`countGraphemes` | 利用者が読み書きする文字列(名前・本文・説明など)。上限の文言の「文字」と利用者の数え方が一致する |
| コードポイント         | 項目の入力規則の中の関数                        | 表示しない秘密の値(パスワードなど)。ハッシュの計算量の上限をコードポイントで抑える               |
| UTF-16の単位(`length`) | 文字列の`length`                                | 規格で長さが決まる値(メールアドレスなど)のうち、許す文字がASCIIだけで単位の違いが出ない値        |

- `countGraphemes`は`Intl.Segmenter`の書記素の区切りで数える。UTF-16の単位やコードポイントで数えると、絵文字や結合文字を含む入力が見た目より多く数えられ、上限ちょうどに見える入力が拒まれる。
- 書記素で数える前の入力の大きさは、APIサーバーの要求本文の上限(「[GraphQLサーバーの基盤](../backend/004-graphql-server.md#前提と用語)」の`<GraphQLの本文の上限>`)で抑えられる。書記素の区切りは入力の長さに比例する時間で済むため、項目ごとにUTF-16の単位の上限を重ねて設けなくてよい。
- 前後の空白を除いて保存する項目は、除いた後の値で数える。

## 使用できない文字

利用者が書く文字列(特に複数行の本文)は、使用できない文字を含む入力を拒む。判定は共用部品の`text/text-safety.ts`の`hasForbiddenCharacters`で行う。

- 対になっていないサロゲート(`String.prototype.isWellFormed`が偽の文字列)は、UTF-8へ変換できず、保存や表示の途中で置換文字に化ける。
- タブ・LF・CR以外のC0制御文字、DEL、C1制御文字は、表示されずに文字列の比較や検索の結果を変え、ログや端末の表示を崩す。
- 置き換えて受け付けず、違反として利用者に示す。黙って置き換えると、利用者の入力と保存された値が食い違う。
- 1行の項目で改行を許さない規則や、文字種を限る規則(ハンドルの英数字など)は、項目の入力規則に加える。

## 前後の空白

前後の空白の扱いは、共用部品の`text/white-space.ts`の`trimWhiteSpace`で行い、空白の集合を`\p{White_Space}`にそろえる。

- `String.prototype.trim`は空白の集合が`\p{White_Space}`と異なる(`trim`はBOM(U+FEFF)を除いてNEL(U+0085)を除かず、`\p{White_Space}`はその逆である)。画面とAPIサーバー、判定と保存で別の集合を使うと、空白だけの入力が一方では空、他方では空でないと判定される。
- 1行の項目(名前・メールアドレスなど)は、前後の空白を除いた値で判定し、同じ値を保存する。検証規則に`.transform(trimWhiteSpace)`を付け、判定した値と保存する値を食い違わせない。
- 必須の判定は、前後の空白を除いて空になる入力を未入力として扱う。空白だけの入力を受け付けない。
- 本文のように空白や改行に意味がある項目は、値を変えずにそのまま保存し、必須の判定でだけ空白だけかを調べる。
- パスワードなどの秘密の値は、前後の空白を除かない。利用者が意図して入れた空白を黙って変えると、同じ値で照合できなくなる。
- 前後の空白を正規表現の量指定子(`/^\p{White_Space}+|\p{White_Space}+$/u`など)で除かない。途中に長い空白の並びがある入力で、処理時間が入力の長さの2乗になる(「[サニタイズの後の変換の限定](../security/004-markdown-sanitization.md#サニタイズの後の変換の限定)」)。

## 違反の順序と文言

- 1つの欄には、最初の1つの違反だけを示す。複数の違反を並べると、利用者がどれから直すかを迷い、1つを直しても他の文言が残る。検証規則は、判定の関数が最初の違反の種類だけを返し、`superRefine`で1つの問題だけを加える形にする。
- 判定の順序は、使用できない文字→必須→上限→形式とする。使用できない文字を含む入力は、他の判定の結果によらず直す必要があるため、最初に示す。空白だけの入力は、上限を超えていても必須の違反だけを示す。
- 利用者へ出る全ての規則に、日本語の文言を指定する。指定しないとZodの既定の英語の文言が出る。画面のフォームは文言の無い規則の違反を共通の既定の文言で示すが、APIサーバーの欄の詳細には既定の英語の文言が出る。
- 文言の上限の数は、入力規則の定数から組み立てる。4桁以上の上限は3桁区切りで示す。

## エラーの詳細の欄名とフォームの欄の対応

APIサーバーが返す欄の詳細を、画面のフォームの欄のエラーとして示す。詳細の`field`とフォームの欄の名前がそろうように、フォームの入力の形と経路を決める。

| 段階                     | `field`の値                                                                                           |
| ------------------------ | ----------------------------------------------------------------------------------------------------- |
| 引数の検証の失敗         | 引数のパスを`.`で連結した値(`input.displayName`・`input.links.0.url`など)。コードは`validation_error` |
| ユースケースが返す違反   | ユースケースの入力からの相対の経路。リゾルバが引数の名前(`input.`など)を前に付けてから返す            |
| フォームが欄に付ける経路 | `AppForm`の`serverFieldPrefix`に引数の名前を渡し、`field`の先頭の`<引数の名前>.`を外した経路          |

- フォームの検証規則の入力の形は、GraphQLの入力の型と同じ形(同じ項目名・同じ入れ子)にする。形が同じなら、引数の名前を外した`field`がそのままフォームの欄の名前になる。
- ユースケースは、GraphQLの引数の名前を知らないため、詳細の欄を自身の入力からの相対の経路で返す。リゾルバは、ユースケースの例外の詳細の欄に引数の名前を前に付けて投げ直す。入力の中の入れ子の値(本人確認の入力など)を別のユースケースに渡す場合は、その入れ子の経路も前に付ける。
- 欄に対応しない詳細(描かれていない欄・無効の欄・欄をまとめた値への詳細)は、フォームが`onSubmitError`へ渡し、フォーム全体の失敗として示す(「[フォーム](../frontend/005-shared-components.md#フォーム)」)。サーバーが詳細を返し得る値を、入力欄を描かずにフォームの入力に含めない。
- 1つの欄に複数の詳細が返った場合、フォームは最初の詳細だけを示す。
- 詳細の`code`は、引数の検証ではZodの問題のコード、ユースケースの違反では違反の種類を表すコードである。画面は`code`で分岐せず、`message`を示す。

## テスト

- 入力規則は共用部品の単体テストで、上限ちょうどと1つ超えた値、結合した絵文字・異体字セレクタを含む値、空白だけの値(半角・全角・タブ・改行)、使用できない文字を含む値を確かめる。
- 画面のフォームの検証規則とAPIサーバーの検証規則は、それぞれのテストで、違反ごとの文言と、前後の空白を除いた値が出力になることを確かめる。
- 前後の空白を除く処理は、入力の上限の長さの空白の連続で処理時間が伸びないことを回帰テストで確かめる。
