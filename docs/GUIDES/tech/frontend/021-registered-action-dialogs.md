# 登録口に登録する操作のダイアログ

後から加わる機能が、他の機能の画面の登録口(ページの区画・「…」メニュー)へ同じ操作(通報など)のダイアログを登録する形と、管理画面で1つの案件に複数の種類の操作(措置・措置なしの完了・却下など)を確認のダイアログから行う一覧の単位のダイアログの置き場所、及び確定の後と失敗の後の照会の取り直しの規約を定める。複数の登録口で1つのダイアログを共有する部品の分け方、ダイアログの開閉と入力の破棄とフォーカス、置き場所への操作の受け渡し、詳細のページの取り直しの遅らせ方、完了済み・競合・案件の不在の失敗でも一覧を取り直す場合の扱い、他の機能の措置の影響する照会の無効化、及びテストを扱う。

メニューの登録口の項目とダイアログの分け方は「[メニューの登録口の項目とダイアログ](015-star-rating-and-threaded-composer.md#メニューの登録口の項目とダイアログ)」に、措置の確認のダイアログ・一覧の単位の置き場所・対象の不在の失敗の取り直しは「[管理画面の検索と措置の操作](020-admin-search-and-moderation-actions.md)」(特に「[一覧の単位の置き場所](020-admin-search-and-moderation-actions.md#一覧の単位の置き場所)」と「[確定の後の反映](020-admin-search-and-moderation-actions.md#確定の後の反映)」)に、監査ログの照会の無効化とロールによる出し分けは「[管理画面のシェルと区画](009-admin-console-shell.md)」に、閉じた後のフォーカスは「[処理の後のフォーカス](004-accessibility-rules.md#処理の後のフォーカス)」に従い、この文書はそれらとの差分だけを書く。APIサーバーの側の案件の規則は「[投稿の集約と案件の完了・再開](../backend/022-submission-aggregation-and-case-resolution.md)」に従う。

## 前提と用語

TanStack Router・TanStack Query v5・TanStack Startと、shadcn/uiの`Dialog`・`DropdownMenu`を前提とする。部品の置き場所は、利用者側・管理者側のアプリの`src/`からのパスで示す。`<ドメイン>`は操作を登録する機能のディレクトリの名前、`<所有する機能>`は措置の操作と影響する照会の表を持つ機能のディレクトリの名前に置き換える。

| 部品                                                            | 置き場所                                                                                    | 役割                                                                                             |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 共有のダイアログ(`<操作>Dialog`)                                | 利用者側の`components/<ドメイン>/<操作>-dialog.tsx`                                         | 対象の種類と参照を受け取り、入力・送信・閉じた後のフォーカスを受け持つ                           |
| 登録口ごとの部品(`<登録口><操作>Item`・`…Dialog`・区画)         | 利用者側の`components/<ドメイン>/`(1ファイル1部品)                                          | 登録口の文脈を共有のダイアログの対象と開閉に写す薄い部品                                         |
| 登録                                                            | 利用者側の`composition/`の各登録口の一覧                                                    | 区画・メニューの項目とダイアログを登録口へ追記する                                               |
| 案件の操作の起点(`<案件>Actions`)                               | 管理者側の`components/<ドメイン>/shared/`                                                   | 操作のボタンだけを描き、選んだ操作と案件と起点のボタンを置き場所へ渡す                           |
| 置き場所(`<案件>DialogHost`)と文脈                              | 管理者側の`components/<ドメイン>/shared/<案件>-dialog-host.tsx`・`<案件>-dialog-context.ts` | 一覧・詳細のページの単位に確認のダイアログを1つ置き、開く関数を文脈で渡す                        |
| 操作の実行のフック(`use<案件>Mutation`)                         | 管理者側の`components/<ドメイン>/shared/`                                                   | 操作を実行し、成功と失敗の種類ごとに照会を無効にして、失敗を投げ直す                             |
| 影響する照会の無効化(`invalidate<所有する機能>AffectedQueries`) | `<所有する機能>`の`components/<所有する機能>/shared/`                                       | 措置の種類ごとに影響する照会を無効にする関数。措置の機能のフックと、措置を呼ぶ他の機能が共有する |

| 用語             | 意味                                                                                                          |
| ---------------- | ------------------------------------------------------------------------------------------------------------- |
| 登録口           | 他の機能が部品を追記する一覧(ページの区画・メニューの項目など)。登録の形(`component`か`Item`と`Dialog`)を持つ |
| 共有のダイアログ | 複数の登録口から同じ操作を開くための、登録口に依らないダイアログの部品                                        |
| 案件             | 管理画面の一覧の1行が表す、状態を持つ対応の単位。行の操作で状態が変わり、絞り込みから外れ得る                 |
| 起点のボタン     | 確認のダイアログを開いたボタン。閉じた後のフォーカスの戻り先の候補                                            |
| 取り直す失敗     | 表示中の一覧・詳細が古いことを示す失敗。照会を無効にしてから投げ直す                                          |

本プロジェクトの登録口・登録の名前と順・操作の名前と文言は、技術ドキュメントに写さず、プロジェクト固有の値の文書「[本プロジェクト固有の値](../../../onboardings/project-values.md)」とサービスの文言規則に置く。

## 複数の登録口で同じダイアログを共有する

同じ操作を、登録の形の異なる複数の登録口(ページの区画と、別々のメニュー)へ登録する場合は、ダイアログの中身を1つの共有のダイアログに置き、登録口ごとの部品は文脈の写しだけを持つ。

```typescript
export interface SharedActionDialogProps {
  readonly targetKind: TargetKind;
  // 対象を指す値(IDやハンドル)。登録口ごとの部品が文脈から選ぶ
  readonly targetRef: string;
  readonly open: boolean;
  readonly onOpenChange: (open: boolean) => void;
  // 閉じた後のフォーカスの戻り先(メニューのボタン・区画のボタン)
  readonly returnFocusRef: RefObject<HTMLButtonElement | null>;
}
```

| 登録口の形                 | 登録口ごとの部品                                                                                                                                                         |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| メニュー(`Item`と`Dialog`) | `Item`は`DropdownMenuItem`を描いて`onSelect`を呼ぶ。`Dialog`は登録口から受けた`open`・`onOpenChange`・`returnFocusRef`をそのまま渡し、文脈から対象の種類と参照を足す     |
| ページの区画(`component`)  | 区画が操作のボタンと開閉の状態を持ち、自分のボタンを`returnFocusRef`にして共有のダイアログを描く。ページの移動ではないため、見た目が控えめなリンクでも`button`要素にする |

- 共有のダイアログは開閉を外から受ける(制御された`open`)だけにし、自分でボタンを描かない。開く元をダイアログの引き金(`DialogTrigger`)にしないため、閉じる時は`onCloseAutoFocus`で`preventDefault()`して`returnFocusRef`へ戻す。
- 本人のコンテンツなど、操作を出さない条件は登録口ごとの部品(項目・区画)が文脈で判定してnullを描く。共有のダイアログは条件を判定し直さない。サーバーも同じ条件を確かめる。
- 登録口ごとの部品は1ファイル1部品にする(項目とダイアログを1つのファイルから2つexportしない)。登録の値(`id`・`order`・部品)は登録口の一覧のファイルに書く。
- 共有のダイアログは操作の機能のディレクトリに置く。他の機能の登録口に登録するが、使うのは1つの機能のため共通部品にしない(「[共通化の対象](005-shared-components.md#共通化の対象)」)。

### 開閉と入力

- 閉じると入力を破棄する。ダイアログの中身(フォーム)は開いている間だけ描き、次に開いた時に前の入力・誤り・bot判定のトークンを残さない。
- ダイアログが開いて初めて要る取得(選択肢の一覧など)は、開いた時に行う(`enabled: open`)。閉じた登録口ごとに取得しない。取得の失敗はダイアログの中の部分の失敗と再試行で示し、ダイアログを閉じない。
- 送信の成功で通知を出してダイアログを閉じる。失敗はダイアログを開いたままフォームの上部や欄に示し、入力を保つ。

## 一覧の単位のダイアログの置き場所

管理画面の一覧と詳細の行の操作で、案件に複数の種類の操作(措置・措置なしの完了・却下)を行う場合は、「[一覧の単位の置き場所](020-admin-search-and-moderation-actions.md#一覧の単位の置き場所)」の形を、案件の操作の置き場所として置く。差分は次のとおりである。

- 起点の部品はダイアログを持たず、選んだ操作の種類・案件・起点のボタンを置き場所の開く関数へ渡す。操作の種類ごとの確認の文言(措置の影響・通知が送られること・送った通知は取り消せないこと・理由が通知に載ること)は置き場所が操作の種類から選ぶ。確認のダイアログが理由の欄へ注記を足す引数を持たなければ、注記も`description`の文で示す。
- 置き場所は一覧のページでは表の外に、詳細のページでは詳細の区画の外に1つずつ置く。状態で絞った一覧で確定して行が消えてもダイアログを残し、確定の後は一覧の見出しへフォーカスを移す。
- 失敗の後は、起点のボタンが残っていれば(`isConnected`)そこへ、取り直しで消えていれば一覧の見出しへフォーカスを移す。
- 操作が既に目的の状態だった失敗(措置済みなど)は取り直さず、ダイアログの中に別の操作(措置なしの完了など)へ切り替える案内を示す。

### 詳細のページの取り直し

詳細のページでは、取り直す失敗の全て(対象の不在に限らない)の取り直しを、確認のダイアログを閉じるまで遅らせる(操作の実行のフックの`deferRefresh`、置き場所の同名の指定)。

- 案件の不在の取り直しは詳細を見つからない表示に替え、処理中のダイアログも外す。他の取り直す失敗も確認の説明の前提(対象と状態)を変えるため、失敗の文言を読み終えて閉じてから画面を更新する。
- 閉じずに画面を離れてダイアログが外れた時も、外れる時に同じ照会を無効にする。
- 取り直しを遅らせた失敗の後は、閉じた時点で起点のボタンが残っていても、閉じた後の取り直しで案件が完了になると起点が消えてフォーカスが`<body>`へ落ちるため、起点ではなく置き場所の見出し(確定の後と同じ移り先)へフォーカスを移す。案件の不在で詳細が見つからない表示に替わる時は、フォーカスが`<body>`へ落ちていれば見つからない表示の区画へ移す。
- 置き場所を通さない詳細のページの独自のダイアログ(状態の変更・照会など)も、取り直す失敗の取り直しを閉じるまで遅らせ、取り直しで開いたボタンが消え得るものは区画の見出しへフォーカスを移す。

## 取り直す失敗

「[確定の後の反映](020-admin-search-and-moderation-actions.md#確定の後の反映)」は対象の不在の失敗だけで影響する照会を無効にし、競合などの他の失敗では無効にしない。案件の一覧では、行ごとに状態と行える操作を示すため、完了済み・競合・案件の不在の失敗でも表示中の行が古い。取り直さないと、管理者は古い行から同じ失敗の操作を繰り返すため、次の失敗も取り直す失敗にする。

| 失敗                           | 意味                                     | 照会の無効化                                             |
| ------------------------------ | ---------------------------------------- | -------------------------------------------------------- |
| 対象の不在                     | 措置の対象が消えた・対象への参照を消した | 案件の一覧・詳細・件数と、`<所有する機能>`の影響する照会 |
| 完了済み                       | 他の管理者が先に完了した                 | 案件の一覧・詳細・件数                                   |
| 競合                           | 同時の別の操作で状態が変わった           | 案件の一覧・詳細・件数                                   |
| 案件の不在                     | 読んだ後に案件が物理削除された           | 案件の一覧・詳細・件数                                   |
| 措置済み・入力の誤り・権限など | 表示中の行は古くない                     | 無効にしない                                             |

- 取り直す失敗は、`GraphQLClientError`のコードが取り直す失敗のコードの一覧にあるもので判定する。`_not_found`の接尾辞では判定しない。照会を無効にしてから失敗を投げ直し、確認のダイアログの中に文言を示して理由の入力を保つ。
- 取り直す失敗の後も、監査ログの照会は無効にしない(記録が残らないため。「[監査ログを残す操作の後の照会の無効化](009-admin-console-shell.md#監査ログを残す操作の後の照会の無効化)」)。
- 規約と異なる扱いにした失敗の一覧は、操作の実行のフックの定数として1か所に置き、なぜ取り直すかをコメントに書く。

## 他の機能の措置の影響する照会

案件の操作が他の機能(`<所有する機能>`)の措置を呼ぶと、措置はその機能の一覧(停止で投稿・コメント・画像の表示が変わるなど)も変える。

- 成功の後は、自分の案件の照会と監査ログの照会に加えて、`invalidate<所有する機能>AffectedQueries(queryClient, <対象の種類>)`で措置の影響する照会を無効にする。
- 影響する照会の表は措置の機能が持ち、関数として公開させて使う。表を写すと、措置の機能が影響の範囲を変えた時に食い違う。公開する関数は措置の機能自身のフックも呼ぶようにし、振る舞いを変えずに切り出す。
- 表示していない照会は古い印が付くだけで取り直さない。

## テスト

- 共有のダイアログ(ブラウザテスト): 開閉と閉じた後の入力の破棄、開いた時だけの取得と失敗の再試行、閉じるとフォーカスが`returnFocusRef`へ戻ること、送信の成功で閉じ失敗で入力を保つこと、自動のアクセシビリティ検査。
- 登録口ごとの部品(ブラウザテスト): 各登録口が正しい対象の種類と参照でダイアログを開くこと、操作を出さない条件でnullを描くこと、メニューから開いたダイアログがメニューを閉じても残ること、区画の操作が`button`要素であること。登録口の一覧を固定する上流のテストは、登録の後の並びと件数に改める。
- 置き場所と実行のフック(ブラウザテスト): 絞った一覧で確定して行が消えてもダイアログが残り見出しへフォーカスが移ること、失敗の後のフォーカスの戻り先(起点が残る・消えた)、取り直す失敗の全てで照会を無効にし他の失敗では無効にしないこと、措置済みで取り直さず切り替えの案内を示すこと、成功の後だけの監査ログの照会の無効化、措置の後の影響する照会の無効化、詳細のページで閉じるまで取り直さないこと。ダイアログを開いている間は背後の一覧が支援技術から隠れるため、行が消えたことは隠れた要素も含める照会(`includeHidden: true`)で確かめる。
- 影響する照会の無効化を切り出した措置の機能は、既存のブラウザテストが変わらず成功することで確かめる。
- テストの種別と命名は「[テストの種別と命名](../testing/001-test-strategy.md#テストの種別と命名)」に従う。
