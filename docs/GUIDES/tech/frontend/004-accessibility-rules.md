# アクセシビリティ規則

React・TanStack Start・shadcn/ui(Radix UI)・Tailwind CSSで作る画面を、WCAG 2.2のレベルAAに沿わせるための規則を定める。キーボード操作、フォーカス、ランドマーク、スキップリンク、画面遷移の通知、状態とエラーの伝え方、コントラスト、視差効果の軽減、演出の停止手段の義務、自動検査と手動で確かめる項目を扱う。

## 前提と用語

部品の使い方は「[共通化する部品](005-shared-components.md)」、日時の要素は「[マークアップの規約](001-markup-conventions.md)」に従う。部品の置き場所は、共通部品のディレクトリからのパスで示す。

| 部品                                                    | 置き場所(共通部品内)                       | 役割                                                                           |
| ------------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------ |
| `AppDocument`                                           | `components/app-shell/app-document.tsx`    | `<html>`から描画する文書の外枠。スキップリンク・トースト・画面遷移の通知を置く |
| `SkipLink`                                              | `components/app-shell/skip-link.tsx`       | 本文へ移動するリンク                                                           |
| `MAIN_CONTENT_ID`                                       | `components/app-shell/main-content.ts`     | スキップリンクの移動先の`id`。画面シェルの`<main>`に付ける                     |

| `FormField`                                             | `components/form/form-field.tsx`           | ラベル・説明・エラーを入力欄に関連付ける欄                                     |

| `pressKeyUntilFocusMoves`                               | `test/keyboard.ts`                         | Radix UIの矢印キーの操作をテストで再現する補助                                 |

| ---------- | --------------------------------------------------------------------------------------------------------------------------------------- |

## キーボード操作

すべての操作をキーボードだけで行えるようにする(2.1.1)。

- 操作には意味に合った要素を使う。押して処理を行うものは`<button>`、移動するものは`<a href>`にする。`<div>`・`<span>`にクリックの処理を付けない。`eslint-plugin-jsx-a11y-x`の推奨規則(「[画面を持つアプリの静的解析](../coding/001-javascript-typescript-conventions.md#画面を持つアプリの静的解析)」)が、キー操作の無いクリックの処理や正の`tabIndex`を検出する。
- ボタンの見た目のリンクは`<Button asChild><a href="…">…</a></Button>`で作る。要素は`<a>`のまま残る。
- ラジオボタンの組・タブ・メニューの項目の間の移動は、Radix UIの部品が矢印キー・`Home`・`End`で提供する。同じ操作を独自に作らない。
- Tabでの移動の順序は文書の順序に従わせる。`tabIndex`に正の値を使わない。

### 操作できない状態

| 状態                                   | 指定                                     | 理由                                                                                                       |
| -------------------------------------- | ---------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 条件を満たすまで押せない(未入力など)   | `disabled`                               | Tabの停止位置から外し、押せないことを支援技術へ伝える                                                      |
| 処理中で押せない(送信中・再確認中など) | `aria-disabled`と`aria-busy`、文言の変更 | フォーカスのあるボタンを`disabled`にすると、Chromiumはフォーカスを`<body>`へ移して戻さず、操作の位置を失う |

- `aria-disabled`はクリックやEnterを止めない。処理を受ける側で処理中の操作を無視する(共通部品の`AppForm`・`SystemStatusView`はそうしている)。
- `Button`は`aria-disabled`の間、`pointer-events: none`と半透明の見た目になる。このため、`aria-disabled`の`Button`を直接`TooltipTrigger asChild`にすると、ポインターを重ねてもツールチップが開かない。押せない理由をツールチップで示す場合は、別の要素をトリガーにするなどしてブラウザテストで確かめる。
- `asChild`のリンクに`aria-disabled`を付けても、クリックは止まるがEnterでは移動する。移動させたくないリンクは`<a href>`として描画しない。

## フォーカス

### フォーカスの輪郭

フォーカスの位置を常に見えるようにする(2.4.7)。`styles/base.css`がベースのレイヤーで、`:focus-visible`のすべての要素に`var(--ring)`の2pxの実線の輪郭を付ける。部品は加えて半透明のリング(`focus-visible:ring-3 focus-visible:ring-ring/50`など)を付け、輪郭とリングが重なって表示される。

- 部品とページに、輪郭を消す・上書きするクラス(`outline-none`・`outline-hidden`・`focus-visible:outline-1`など)を付けない。Tailwind CSS v4のユーティリティはユーティリティのレイヤーにあり、ベースのレイヤーの輪郭に勝つ。shadcn/uiの部品のコードを取り込む時は、これらのクラスを取り除く。
- どのレイヤーにも属さないCSSを差し込むライブラリ(例:トーストのライブラリの`outline: 0`)は、レイヤー内の規則に勝って輪郭を消す。その部品にだけ`!important`付きのユーティリティ(`focus-visible:outline-2! focus-visible:outline-offset-2! focus-visible:outline-ring! focus-visible:outline-solid!`)で同じ輪郭を付け直す。
- 固定表示のヘッダーなどが、フォーカスした要素を完全に隠さないようにする(2.4.11)。自動検査では確かめられないため、手動で確かめる。

### 重ねて表示する部品

ダイアログ・シート・メニューを開いたら、フォーカスを中へ移して外へ出さず、閉じたら開いた元の要素へ戻す(2.4.3)。Radix UIの部品(`Dialog`・`Sheet`・`DropdownMenu`)がこれを行う。

- `Popover`は`modal`を指定しないとフォーカスを閉じ込めない。中で入力を完結させる場合は`modal`を指定する。
- `Sheet`は開いた時、中のリンクを飛ばして最初のリンク以外の操作へフォーカスを移す。
- `DialogContent`・`SheetContent`には`DialogTitle`・`SheetTitle`を必ず置き、題名を支援技術へ伝える。右上の「閉じる」ボタンは画面に見えない名前を持つ。

### 処理の後のフォーカス

- サーバーが入力の不正を欄ごとに返した時は、最初のエラーの欄へフォーカスを移す(`AppForm`が行う)。欄の部品に`FormField`が渡す`ref`を付けないとフォーカスが移らない。
- ブラウザ内の画面遷移では、フォーカスを移さない。移動の通知は「[画面遷移の通知](#画面遷移の通知)」で行う。

## ランドマークとページの構成

画面シェルは、ページの言語と、ヘッダー・ナビゲーション・本文・フッターのランドマークを持つ(1.3.1・3.1.1)。

- `AppDocument`が`<html>`の`lang`属性でページの言語を示す。
- レイアウトは`<header>`・`<nav>`・`<main>`・`<footer>`で組み立てる。`<nav>`が複数あるときは、`aria-label`でそれぞれに異なる名前を付ける。
- `<main>`はページに1つだけ置き、`id={MAIN_CONTENT_ID}`を付ける。
- 区画を後から差し込むレイアウトは、区画が空ならランドマークの要素ごと描画しない(名前だけの空の`<nav>`を残さない)。
- ページの見出しは`<h1>`1つから始める。`NotFoundView`・`UnexpectedErrorView`・`SystemStatusView`は自身で`<h1>`を持つため、それらを置くルートは`<h1>`を足さない。`EmptyState`は`headingLevel`を指定すると見出し付きの`<section>`になり、省略すると見出しを持たない。
- ページごとにタイトルを設定する(2.4.2)。ルートの`head`で`buildPageHead({ title, siteName })`(`start/page-head.ts`)を返し、`<ページ名> | <サイト名>`にする。ページ名はページごとに異ならせる。

## スキップリンク

`AppDocument`は`<body>`の最初の操作として`SkipLink`を置く(2.4.1)。

- 普段は画面に見えず、フォーカスした時だけ左上に表示する。
- クリック・Enterで、`id={MAIN_CONTENT_ID}`の要素へ直接フォーカスを移す。URLのフラグメントを変えるとルーターが画面遷移として扱い履歴も増えるため、リンクの既定の移動を止める。フォーカスできない要素には`tabindex="-1"`を付けてから移す。
- 本文の要素が無いページでは、リンクの既定の移動に任せる。スクリプトが動く前も既定の移動で本文へ移る。
- レイアウトを作るアプリは、ブラウザテストで`<main>`に`id={MAIN_CONTENT_ID}`があることと、スキップリンクで移ったフォーカスの輪郭の出方を確かめる。

## 画面遷移の通知

ブラウザ内の画面遷移では、支援技術がページの移動に気付かない。`AppDocument`が置く`RouteAnnouncer`が、移動先のページのタイトルを伝える(4.1.3)。

- 画面に見えない`aria-live="polite"`・`aria-atomic="true"`の領域を最初の表示から置いておき、ルーターの`onRendered`の後に`document.title`を書き込む。
- 最初の表示はブラウザが通知するため伝えない。検索パラメータやフラグメントだけが変わった時は、ページの移動として伝えない。
- 同じタイトルが続く遷移は、領域の内容が変わらないため伝わらない。ページごとに異なるタイトルを付ける。

## 状態とエラーの伝え方

状態とエラーは、色だけでなく文言で示し(1.4.1)、支援技術へ伝える(4.1.3)。

| 伝える内容                       | 部品                                               | 支援技術への伝え方                                               |
| -------------------------------- | -------------------------------------------------- | ---------------------------------------------------------------- |
| 読み込み中                       | `LoadingSkeleton`                                  | `role="status"`の中の見えない文言。スケルトンの形は`aria-hidden` |
| 区画またはページの読み込みの失敗 | `ErrorState`・`PartialErrorState`                  | `role="alert"`の文言                                             |
| 縮退運転中                       | `UnavailableNotice`                                | `role="status"`の題と理由                                        |
| 想定外のエラーの画面             | `UnexpectedErrorView`                              | `role="alert"`の見出しと案内                                     |
| 入力のエラー                     | `FormField`                                        | 欄の`aria-invalid`と、`aria-describedby`で関連付けた文言         |
| bot判定の失敗                    | `TurnstileWidget`                                  | `role="alert"`の文言                                             |
| 操作の結果                       | `notify`(トースト)                                 | 名前付きの領域の丁寧な通知(`role`を持たない)                     |
| 処理中のボタン                   | `SubmitButton`・`SystemStatusView`の再確認のボタン | `aria-busy`と、送信中などを示すボタンの文言への変更              |

- `Skeleton`自体は`aria`を持たない。読み込み中の表示には`Skeleton`を直接置かず、`LoadingSkeleton`で包む。
- トーストは一定の時間で消え、丁寧な通知で伝える。利用者の対応が要る失敗はトーストだけで伝えず、`ErrorState`・`PartialErrorState`か、フォームの`role="alert"`の表示で示す。トーストは操作の結果の通知に使う。
- アイコンには`aria-hidden="true"`を付け、意味は文言で伝える。アイコンだけのボタンは、`aria-label`か画面に見えない文言で名前を付ける。
- 破壊的な操作は、色ではなく文言(「削除する」など)で示す。破壊的なメニュー項目は、フォーカス中は文字色を通常の色にしている。

### エラーの関連付け

入力のエラーは、該当する入力欄と支援技術上で関連付ける(1.3.1・3.3.1)。`FormField`が次を行う。

- `<label for>`で入力欄に名前を付ける。名前を付けられる要素(`input`・`textarea`・`button`)を描く部品に使う。
- 説明とエラーの文言の`id`を`aria-describedby`で入力欄に関連付け、エラーのある間は`aria-invalid`を付ける。エラーは文言とアイコンで示す。
- 最初にフォーカスを外した時に検証し、以降は入力のたびに検証し直す(`useAppForm`の`mode: 'onTouched'`)。
- 必須の印は自動で付けない。必須の欄は、ラベルか説明の文言で必須であることを示し、入力欄に`aria-required`を渡す。

## コントラスト

文字と背景のコントラスト比を、ライト・ダークの両方でWCAG 2.2のAAの基準以上にする。

| 対象                                         | 基準      | 達成基準 |
| -------------------------------------------- | --------- | -------- |
| 文字(大きな文字を除く)                       | 4.5:1以上 | 1.4.3    |
| 大きな文字(18pt以上、または14pt以上の太字)   | 3:1以上   | 1.4.3    |
| 操作の境界・フォーカスの輪郭・状態を示す図形 | 3:1以上   | 1.4.11   |

- 色は`styles/tokens.css`のトークンのクラス(`bg-primary`・`text-muted-foreground`など)だけで指定する。色の値を直接書かない。
- 文字色を、本文の色の透明度を下げて(`text-foreground/60`など)作らない。背景によって比が変わり基準を割りやすい。控えめな文字には`text-muted-foreground`を使う。
- 通常・ホバー・フォーカス・選択中の各状態の色を測る。ホバーやフォーカスで背景を着色する部品は、その状態の文字の比も基準以上にする。
- デザイン案からトークンの値を移植するときも、ライト・ダークの両方で測り、基準に届かない値はデザイン案と離れても直す。直したトークンと理由はデザインの文書に記す。トークンを明るくしたときは、そのトークンを背景に使う部品のホバーの背景の濃さも合わせて見直し、各状態の比を測り直す。
- `axe-core`は、半透明の重なり・グラデーション・画像の上の文字の比を測れないことがある。その場合は手動で測る。

## 視差効果の軽減

OSの「視差効果を減らす」設定(`prefers-reduced-motion: reduce`)が有効な間は、アニメーションと遷移の動きを止めるか最小にする(2.3.3。レベルAAAだが本規則では必須とする)。`styles/base.css`がすべての要素と疑似要素に次の規則を`!important`で掛ける。

| プロパティ                  | 値       |
| --------------------------- | -------- |
| `animation-duration`        | `0.01ms` |
| `animation-iteration-count` | `1`      |
| `transition-duration`       | `0.01ms` |
| `scroll-behavior`           | `auto`   |

- `animate-spin`などの無限のアニメーションも1回で止まる。読み込み中・送信中であることを動きだけで示さず、文言か`aria`属性(`aria-busy`など)で示す。スケルトンの明滅も止まるため、`LoadingSkeleton`は文言で読み込み中を伝える。
- スクリプトで動かす演出にはCSSの規則が効かない。`matchMedia('(prefers-reduced-motion: reduce)')`か、アニメーションのライブラリの同等の仕組みで設定を読み、動きを止める。
- 共通部品は演出の切替のUIを持たず、OSの設定に従う。
- 1秒間に3回を超えて点滅する表示を作らない(2.3.1)。

## 演出の停止手段の義務

共通部品と画面シェルは、自動で動き続ける演出を持たない。演出を持つ区画を追加する機能は、WCAG 2.2の達成基準2.2.2(一時停止、停止、非表示)に従い、次を満たす。

- 自動で始まり、5秒を超えて続き、他の内容と並べて表示する動き・点滅・自動スクロールを持つ区画には、利用者がその演出を一時停止・停止・非表示にできる手段を、その区画の近くに用意する。
- 自動で始まり、他の内容と並べて表示する、自動で更新される情報(数値や一覧の自動更新など)には、一時停止・停止・非表示にできる手段か、更新の頻度を利用者が選べる手段を用意する。
- 手段はキーボードで操作でき、名前を持ち、現在の状態(停止中など)を支援技術へ伝える。
- OSの「視差効果を減らす」設定に従うだけでは、この義務を満たさない。設定を有効にしていない利用者も止められるようにする。
- この規約を変える場合、または共通部品に演出の切替のUIを加える場合は、演出を持つ機能を確かめ直す。

## 自動検査

### 静的解析

`createFrontendLintConfig`が`eslint-plugin-jsx-a11y-x`の推奨規則を有効にする(「[画面を持つアプリの静的解析](../coding/001-javascript-typescript-conventions.md#画面を持つアプリの静的解析)」)。代替テキスト・ラベル・キー操作・役割の誤りを検出する。

### ブラウザテスト

部品ごとのブラウザテスト(`*.browser.test.tsx`、「[テストの種別と命名](../testing/001-test-strategy.md#テストの種別と命名)」)で、キーボード操作・フォーカスの移動と戻り・`aria-*`の関連付け・文言を確かめ、`axe-core`の自動検査の違反が0件であることを、ライト・ダークの両方で確かめる。次は共通部品の`components/state/`に置いたテストの例である。

```tsx
import { describe, expect, test } from 'vitest';
import { render } from 'vitest-browser-react';

import '../../styles/base.css';
import { runAxe } from '../../test/a11y.ts';
import { applyColorScheme, COLOR_SCHEMES } from '../../test/computed-style.ts';
import { LoadingSkeleton } from './loading-skeleton.tsx';

describe.each(COLOR_SCHEMES)('配色が%sのとき', (scheme) => {
  test('アクセシビリティの検査の違反が0件', async () => {
    applyColorScheme(scheme);
    const { container } = await render(<LoadingSkeleton />);

    expect(await runAxe(container)).toStrictEqual([]);
  });
});
```

- `runAxe(element)`は、WCAG 2.2のAAのタグ(`WCAG_22_AA_TAGS`:`wcag2a`・`wcag2aa`・`wcag21a`・`wcag21aa`・`wcag22aa`)の規則だけで検査し、違反の要約の配列を返す。検査の前に、終わりのある動き(開閉や配色の切り替え)の終了を待つ。動きの途中の中間の色でコントラストを誤って測らないためである。
- `<html>`から描画する部品(`AppDocument`など)は、`runAxeOnDocument(document)`で文書全体(言語・タイトル・ランドマーク)を検査する。
- 重ねて表示する部品は、開いた状態を描画して検査する。モーダルなメニューを開くと、外側の`aria-hidden`の要素の中の開いた元のボタンを`axe-core`が`aria-hidden-focus`の違反と数える。メニューは、閉じた状態の`container`と、開いたメニューごと(開いたメニューが0件なら失敗にする)に分けて検査する。
- 自動検査のテストでは、視差効果を減らす設定を真似ない。Chromiumで配色の切り替えの途中の色が残り、コントラストを誤って測る。視差効果の軽減は、別のテストで`emulateReducedMotion('reduce')`の後に計算済みのスタイルを確かめる。
- Radix UIの矢印キーの操作は、押している間に移ったフォーカスで項目を選ぶ。テストの操作は押下と解放を間を置かずに送るため、`pressKeyUntilFocusMoves(key)`でフォーカスが移るまで押したままにする。

### カタログ

部品のカタログ(Storybook)の`@storybook/addon-a11y`が、ストーリーごとに同じWCAG 2.2のAAのタグで検査し、結果をパネルに表示する(「[カタログの書き方](005-shared-components.md#カタログの書き方)」)。アドオンは自身が依存する`axe-core`を使うため、ブラウザテストの`axe-core`と版が異なることがある。合否はブラウザテストで判定する。

E2Eテストでは自動検査を行わない。

## 手動で確かめる項目

自動検査は違反の一部しか検出しない。画面シェル・新しい部品・演出を持つ区画を追加・変更した時は、次を手動で確かめる。

| 項目                                                                                                      | 達成基準            |
| --------------------------------------------------------------------------------------------------------- | ------------------- |
| キーボードだけですべての操作ができ、Tabの順序が見た目の順序と合う                                         | 2.1.1・2.4.3        |
| 重ねて表示する部品でフォーカスが閉じ込められ、閉じると開いた元の要素へ戻る。どこにも閉じ込められない      | 2.1.2・2.4.3        |
| フォーカスの輪郭が見え、固定表示のヘッダーなどに隠れない                                                  | 2.4.7・2.4.11       |
| スクリーンリーダー(VoiceOver・NVDAなど)で、名前・役割・状態・エラー・状態の通知・画面遷移の通知が読まれる | 1.3.1・4.1.2・4.1.3 |
| 幅320pxで横スクロールが出ず、文字を200%に拡大しても内容と操作が欠けない                                   | 1.4.4・1.4.10       |
| 操作の大きさが24×24 CSSピクセル以上か、隣の操作と十分に離れている                                         | 2.5.8               |
| ライト・ダークの両方で、自動検査が測れない箇所のコントラストが基準以上                                    | 1.4.3・1.4.11       |
| 視差効果を減らす設定で、動きが止まり、状態が文言で分かる                                                  | 2.3.3               |
| 演出を持つ区画に停止の手段があり、キーボードで操作できる                                                  | 2.2.2               |
| ブラウザの翻訳を有効にしても崩れない(「[翻訳への耐性](005-shared-components.md#翻訳への耐性)」)           | 1.4.10              |
