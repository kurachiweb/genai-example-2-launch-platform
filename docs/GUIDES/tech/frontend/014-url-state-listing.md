# URLのクエリで条件を持つ一覧

検索語・絞り込み・並び順・ページ番号の条件をURLのクエリで持ち、URLを共有・ブックマークすると同じ一覧を開ける画面の規約を定める。クエリの正規化を共有の関数にすること、条件の変更とURLの作り方、送信でだけ検索する入力欄、ルートの`loader`と直前の結果を残す再読み込み、サーバーが解決した条件へのURLの合わせ込み、オフセット方式のページ送りのリンク、ページの移動のスクロールとフォーカス、及びテストを扱う。

一覧の問い合わせは「[グループごとの最新の行で並べる一覧](../db/007-latest-row-per-group-listing.md)」に、取得の補助と`loader`は「[データ取得](006-data-fetching.md)」(特に「[失敗を画面の中で表示する取得](006-data-fetching.md#失敗を画面の中で表示する取得)」)に、入力の規則の置き場所は「[入力値バリデーション](../coding/005-input-validation.md#規則の置き場所)」に、フォーカスと状態の伝え方は「[アクセシビリティ規則](004-accessibility-rules.md)」に従う。区画を登録口から並べる場合は「[区画の登録とページの構成](013-live-scoreboard.md#区画の登録とページの構成)」に従う。

## 前提と用語

TanStack Router・TanStack Query v5・TanStack Startを前提とする。部品の置き場所は、共用部品(フロントエンドとバックエンドが共に使う共有ディレクトリ)と、画面のアプリの`src/`からのパスで示す。`<一覧>`は一覧の画面ごとに置き換え、コードの例では`List`・`list`と書く。

| 部品                                                     | 置き場所                                                      | 役割                                                                          |
| -------------------------------------------------------- | ------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 条件の型と正規化・条件の変更(`normalize<一覧>Query`など) | 共用部品の`<一覧>/<一覧>-query-rules.ts`                      | URLのクエリとAPIの入力を条件にそろえる規則と、条件の変更で1ページ目に戻す関数 |
| 一覧のURL                                                | 画面のアプリの`components/<一覧>/<一覧>-href.ts`              | 条件とページ番号からURLを作る                                                 |
| 取得の設定と`loader`                                     | 画面のアプリの`graphql/<一覧>.ts`                             | 条件からAPIの入力と取得のキーを作り、ルートの`loader`で取得を始める           |
| 遷移のフック                                             | 画面のアプリの`components/<一覧>/use-<一覧>-navigation.ts`    | 条件の変更とページの移動の遷移、ページの移動の後のスクロールとフォーカス      |
| 解決した条件への置き換えのフック                         | 画面のアプリの`components/<一覧>/use-applied-<一覧>-query.ts` | サーバーが解決した条件とURLが食い違うときに、URLを置き換える                  |
| 印を付けないリンク                                       | 画面のアプリの`components/<一覧>/unmarked-path-link.tsx`      | ルーターの現在のページの印を外し、呼び出し元が決めた印だけを付けるリンク      |

| 用語           | 意味                                                                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 条件           | 検索語・絞り込み(カテゴリ・期間など)・並び順・ページ番号の組。URLのクエリの1項目が条件の1項目になる                                              |
| 正規化         | URLのクエリやAPIの入力の値を条件の型の値にそろえること。不正な値は既定の値に戻し、既定の値はURLに書かない                                        |
| 既定の値       | 指定が無いときの値。条件では`undefined`で表す                                                                                                    |
| 条件の変更     | ページ番号以外の条件を変えること。常に1ページ目に戻る                                                                                            |
| ページの移動   | ページ番号以外の条件を保ったまま、ページ番号だけを変えること                                                                                     |
| 解決した条件   | サーバーが条件を解決した結果(存在しない絞り込みを外し、識別子を保存済みの表記にしたもの)。一覧の応答に含める                                     |
| 再読み込みの間 | 条件の変更やページの移動の後、新しい条件の結果が届くまでの間                                                                                     |
| オフセット方式 | ページ番号から読む位置を決めるページ分け(「[オフセット方式の費用と上限](../db/007-latest-row-per-group-listing.md#オフセット方式の費用と上限)」) |

本プロジェクトの一覧の名前・1ページの件数・検索語の上限の文字数は、技術ドキュメントに写さず、プロジェクト固有の値の文書「[本プロジェクト固有の値](../../../onboardings/project-values.md)」に置く。

## クエリの正規化

URLのクエリを条件にそろえる関数は共用部品に1つだけ置き、ルートの`validateSearch`、APIサーバーの入力の解釈、画面のリンクの組み立ての全てで使う。画面とAPIで規則が分かれると、画面のURLとAPIが返す結果の条件が食い違う。

```typescript
// ルーターは検証の結果をURLの元の値に重ねるため、元の値を残さないよう既定の項目もundefinedとして返す
export const normalizeListQuery = (
  raw: Readonly<Record<string, unknown>>,
): ListQuery => {
  const q = normalizeSearchText(raw.q);
  return {
    q,
    category: normalizeCategory(raw.category),
    ...normalizeRange(raw.from, raw.to),
    sort: normalizeSort(raw.sort, q),
    page: normalizePage(raw.page),
  };
};
```

| 項目       | 正規化                                                                                                                                                            |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 検索語     | 前後の空白を除き、上限の書記素数で切り詰めて、もう一度前後の空白を除く。空になれば既定の値                                                                        |
| 識別子     | 識別子の形式の規則に合わなければ既定の値。存在するかはサーバーが判定する(「[サーバーが解決した条件へのURLの置き換え](#サーバーが解決した条件へのurlの置き換え)」) |
| 期間       | 日付の形式に合わない端は既定の値。両端があって開始が終了より後なら、両端とも既定の値                                                                              |
| 並び順     | 選択肢に無い値と、その時の既定の並び順と同じ値は既定の値。他の条件が無いと意味の無い並び順(検索語の無い関連度の順)も既定の値                                      |
| ページ番号 | 2以上の安全な整数だけを残し、1と不正な値は既定の値(1ページ目)                                                                                                     |

- 不正な値は、エラーの表示にせず黙って既定の値に戻す。URLは手で書き換えられ、古いリンクや共有されたURLから届く。一覧を表示できないより、条件を外した一覧を表示する。
- 既定の値はURLに書かない。同じ一覧が、既定の値を書いたURLと書かないURLの2つにならない。
- 既定の並び順が他の条件で変わる(検索語があれば関連度の順など)場合、条件には利用者が既定から変えた並び順だけを持ち、実際の並び順は別の関数(`effectiveSort(query)`)で求める。
- 戻り値は全ての項目を`undefined`を含めて持つ。ルーターは`validateSearch`の戻り値をURLの元の値に重ねて検索パラメータにするため、項目を省くと元の不正な値が残る。
- APIサーバーは、受け取った入力を同じ関数で正規化してから使う。APIの入力のページ番号は、型の検査で拒否されずに同じ規則で既定の値へ戻るよう、10進の整数の文字列でも受ける。

### ルーターの既定のクエリの解析

TanStack Routerの既定の`parseSearch`は、クエリの値をJSONとして読めれば読む。数の形の値は数に、`true`・`false`・`null`は真偽値と`null`になる。

- 検索語や識別子のように文字列の条件は、数として届いた値を文字列へ戻して受ける。数として読まれた時点で表記が変わる(`1.50`は`1.5`、`1e3`は`1000`)ため、正規化した値への置き換えで手入力のURLの表記が変わることがある。`true`・`null`のような値は検索語として受けず、既定の値になる。
- アプリが作るリンクは、ルーターの既定の`stringifySearch`(`defaultStringifySearch`)で作る。数として読める文字列は引用符で囲んだJSONとして書かれ(`q=%22123%22`)、読み戻しても文字列のままである。
- `parseSearch`・`stringifySearch`はルーター全体の設定で、他の画面の検索パラメータの読み方も変えるため、一覧のために変えない。

## 条件の変更とURL

```typescript
export const withListConditions = (
  query: ListQuery,
  patch: Partial<Omit<ListQuery, 'page'>>,
): ListQuery => normalizeListQuery({ ...query, ...patch, page: undefined });

export const listHref = (query: ListQuery): string =>
  `${LIST_PATH}${defaultStringifySearch({ ...query })}`;

export const listPageHref = (query: ListQuery, page: number): string =>
  listHref(normalizeListQuery({ ...query, page }));
```

- 条件の変更は、変える項目を重ねてページ番号を外し、もう一度正規化する。条件を変えた後の一覧は、件数もページ数も変わるため、常に1ページ目から示す。
- URLは、ルーターが遷移の時に作るURLと同じ表記になるよう、ルーターの既定の書き出しで作る。アプリが作ったURLとルーターが正規化したURLを文字列で比べられ、余分な置き換えが起きない。
- 1ページ目のURLは`page`を書かない(`listPageHref(query, 1)`は条件だけのURLになる)。
- 条件の変更は`router.navigate({ href, resetScroll: false })`で、履歴に加える遷移にする。ブラウザの戻る操作で前の条件の一覧へ戻れる。スクロールを先頭へ戻さず、利用者が操作した検索欄・絞り込み欄の位置に留める。フォーカスも移さない。
- 一覧の項目の中のリンクで一覧そのものの条件を変える場合(項目のカテゴリで絞り込むリンクなど)も、`with<一覧>Conditions`で作ったURLの`<a href>`にする。

### 送信でだけ検索する入力欄

- 検索欄は`<form role="search">`にし、名前を付ける。入力のたびには検索せず、Enterキーと検索のボタンでだけ条件を変える。IMEの変換中の確定前の文字で検索せず、全文検索への問い合わせを入力の回数だけ増やさない。
- 上限の書記素数を超えた語は送信で遷移せず、エラーの文言を`aria-describedby`で関連付けて入力欄へフォーカスを戻す。上限に近づいたら(上限の手前の文字数から)文字数を示し、入力欄に`aria-describedby`で関連付ける。文字数は前後の空白を除いた語の書記素数で数え、正規化と同じ数え方にする。
- URLの検索語が外から変わったとき(条件の解除・ブラウザの戻る操作)は、入力欄の値をURLの値に戻す。部品を作り直すと入力欄のフォーカスが失われるため、描画中に前の値と比べて状態を差し替える。
- 消去のボタンは入力欄を空にしてフォーカスを入力欄へ戻し、適用中の検索語があるときだけ検索語を外す条件の変更を行う。

## loaderと再読み込みの間

```typescript
export const Route = createFileRoute('/<一覧のパス>/')({
  validateSearch: normalizeListQuery,
  loaderDeps: ({ search }) => search,
  loader: loadList,
  component: ListRoute,
});

export async function loadList({ context, deps, cause }: ListLoaderArgs) {
  const loading = Promise.all([
    context.queryClient
      .query({ ...listQueryOptions(deps, context.viewer), staleTime: 'static' })
      .catch(() => undefined),
    context.queryClient
      .query({ ...listOptionsQueryOptions(), staleTime: 'static' })
      .catch(() => undefined),
  ]);
  if (cause !== 'stay') {
    await loading;
  }
}
```

- `loader`は一覧と絞り込みの選択肢を同時に取得し始め、失敗は例外にせずキャッシュに残す。一覧の失敗は一覧の位置に再試行とともに示し、検索欄と絞り込み欄は操作できるまま残す(「[失敗を画面の中で表示する取得](006-data-fetching.md#失敗を画面の中で表示する取得)」)。
- 同じ画面の中の条件の変更とページの移動(`cause === 'stay'`)では、取得を始めるだけで待たない。待つと、ルーターは前の条件の画面を保ったまま待ち、部品が新しい条件を受け取れないため、直前の一覧を残した再読み込みの表示を出せない(待つ時間が長ければ`pendingComponent`に替わる)。
- サーバーでの描画、他のルートからの遷移(`'enter'`)、先読み(`'preload'`)では待つ。最初の表示に一覧が入り、先読みした結果で遷移の直後から一覧を示せる。
- 部品は`useQuery`に`placeholderData: keepPreviousData`を付けて読み、`isPlaceholderData`の間を再読み込みの間とする。

### 再読み込みの間の表示

| 対象                   | 再読み込みの間の表示                                                                                                                                                                     |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 検索欄・絞り込み欄     | 操作できるまま残す。続けて条件を変えられる                                                                                                                                               |
| 直前の一覧とページ送り | 薄く残し、`inert`で操作とフォーカスを止める。囲む要素に`aria-busy`を付ける                                                                                                               |
| 進捗の表示             | 一覧の上端に`aria-hidden`の進捗のバーを出す。動きは視差効果を減らす設定でない時だけ付け、設定がある時は静止した帯にする(「[視差効果の軽減](004-accessibility-rules.md#視差効果の軽減)」) |
| 件数                   | `aria-live="polite"`・`aria-atomic="true"`の件数の欄を「読み込み中」の文言に替え、結果が届いたら新しい件数に戻す。支援技術に条件の変更の結果が伝わる                                     |

- 最初の読み込み(キャッシュに値が無い間)は、直前の一覧が無いため、一覧の形を保ったスケルトン(「[状態とエラーの伝え方](004-accessibility-rules.md#状態とエラーの伝え方)」)にする。検索欄と絞り込み欄はURLの条件から描き、選択肢を取得する欄(カテゴリなど)だけを無効にする。
- 取得し直している間(`isFetching`)は前の失敗を示さず読み込み中として描く。再試行のボタンは押した時に一覧の見出しへフォーカスを移す(「[処理の後のフォーカス](004-accessibility-rules.md#処理の後のフォーカス)」)。
- 絞り込みの選択肢の取得に失敗しても、一覧は表示し、その絞り込み欄は「全て」だけで操作できるようにする。
- 結果が閲覧者で変わる一覧(閲覧者自身の項目に印を付けるなど)は、取得のキーの末尾に閲覧者の識別子(未ログインは固定の印)を加える。同じタブでのログインとログアウトの後に前の閲覧者の結果を示さない。先頭の要素は操作の識別子のままにする(「[loaderとの組み合わせ](010-live-refresh-queries.md#loaderとの組み合わせ)」)。
- APIの入力は指定された項目だけで作る。既定の項目を`undefined`のまま入れると、同じ条件が別の取得のキーになり得る。

## サーバーが解決した条件へのURLの置き換え

存在しないカテゴリや、大文字小文字を同一視する識別子の表記の違いは、画面の正規化では分からない。サーバーは条件を解決した結果を一覧の応答に含め、画面はURLと食い違えばURLを解決した条件へ置き換える。

```typescript
export function useAppliedListQuery(query: ListQuery, viewer: Viewer | null) {
  const router = useRouter();
  const queryClient = useQueryClient();
  const { data: appliedHref } = useQuery({
    ...listQueryOptions(query, viewer),
    select: ({ list }) => listHref(listQueryOfApplied(list.applied)),
  });
  const currentHref = listHref(query);

  useEffect(() => {
    if (appliedHref === undefined || appliedHref === currentHref) {
      return;
    }
    const data = queryClient.getQueryData(
      listQueryOptions(query, viewer).queryKey,
    );
    if (data !== undefined) {
      queryClient.setQueryData(
        listQueryOptions(listQueryOfApplied(data.list.applied), viewer)
          .queryKey,
        data,
      );
    }
    void router.navigate({
      href: appliedHref,
      replace: true,
      resetScroll: false,
    });
  }, [appliedHref, currentHref, query, viewer, queryClient, router]);
}
```

- 解決した条件は、URLの条件と同じ関数で正規化してから比べる。比較はどちらも`<一覧>Href`で作ったURLの文字列で行う。
- 置き換えは`replace: true`にし、履歴を増やさない。戻る操作で食い違ったURLへ戻り、また置き換わることを繰り返さない。
- 置き換える前に、取得済みの結果を解決した条件の取得のキーへ写す。解決した条件の結果は取得済みの結果と同じであり、写さないと置き換えの後に同じ結果を取得し直し、再読み込みの表示が一瞬出る。
- 形式の不正な値はサーバーへ送る前にルーターの正規化で外れ、ルーターがURLを置き換える(ブラウザ内の遷移では置き換え、サーバーでの描画では転送の応答になる)。このフックが扱うのは、形式は正しいがサーバーでしか判定できない食い違いだけである。

## ページ送り

ページ送りの各ページは`<a href>`のリンクにする(「[キーボード操作](004-accessibility-rules.md#キーボード操作)」)。スクリプトの読み込み前・新しいタブで開く操作・検索エンジンのクローラーでも、URLでページを辿れる。

- リンクのURLは`<一覧>PageHref(query, page)`で作り、ページ番号以外の条件を保つ。1ページ目へのリンクは`page`を書かない。
- `<nav>`に一覧の名前を含めた名前(「<一覧の名前>のページ送り」)を付ける。ページ番号のリンクの名前は見えている番号を含め(「5ページ目」)、「前へ」「次へ」は見えている文言をそのまま名前にする(達成基準2.5.3)。
- 現在のページは、リンクに`aria-current="page"`を付けて示す。ルーターのリンクは、表示中のURLに一致すると判定したリンクに`aria-current="page"`と`data-status="active"`を付ける。既定では検索パラメータを部分一致で判定するため、条件の少ないURL(1ページ目など)へのリンクにも付く。`activeOptions`の`exact: true`で絞っても、表示中のURLと同じURLを指すリンク(絞り込み中の項目へのリンクなど)には必ず付き、止める指定が無い。ページ送りと、一覧の中で一覧そのものを指すリンクは、`createLink`で作った印を付けないリンクで描き、呼び出し元が現在のページと判断したリンクにだけ`aria-current="page"`を付ける。
- 先頭のページの「前へ」と末尾のページの「次へ」は、移る先が無いためリンクにせず、`disabled`のボタンにする。`aria-disabled`のリンクはEnterで移動する(「[操作できない状態](004-accessibility-rules.md#操作できない状態)」)。ページの移動の後はフォーカスを一覧の見出しへ移す(「[ページの移動のスクロールとフォーカス](#ページの移動のスクロールとフォーカス)」)ため、押したボタンにフォーカスを残す必要は無い。
- 総ページ数が1以下ならページ送りを描かない。
- ページ番号の省略(先頭・末尾・現在のページの前後を残して間を省く)は、ページ番号と総ページ数から項目の並びを返す純粋な関数にし、単体テストで確かめる。省略の記号は`aria-hidden`にする。
- 範囲外のページ(空の一覧で総件数が1以上)では、ページ送りと件数を描かず、全ページ数と1ページ目へのリンクを示す空の状態にする。
- 再読み込みの間に直前のページ送りを操作できないよう、一覧の側の`inert`の中に置く。

## ページの移動のスクロールとフォーカス

ページの移動では、新しいページを一覧の先頭から読めるよう、一覧の先頭へスクロールして一覧の見出しへフォーカスを移す。検索パラメータだけが変わる遷移は画面遷移の通知の対象外(「[画面遷移の通知](004-accessibility-rules.md#画面遷移の通知)」)のため、見出しへのフォーカスがページの移動を支援技術に伝える。条件の変更では、スクロールもフォーカスの移動もしない。

```typescript
const moveToList = (list: HTMLElement | null, heading: HTMLElement | null) => {
  list?.scrollIntoView({
    block: 'start',
    behavior: prefersReducedMotion() ? 'auto' : 'smooth',
  });
  // 見出しへのフォーカスで即座にスクロールすると、上の滑らかなスクロールが打ち消されるため止める
  heading?.focus({ preventScroll: true });
};

const onPageNavigate = () => {
  pendingRef.current?.();
  const unsubscribe = router.subscribe('onRendered', () => {
    unsubscribe();
    pendingRef.current = null;
    moveToList(listRef.current, headingRef.current);
  });
  pendingRef.current = unsubscribe;
};
```

- ページ送りのリンクの`onClick`で、ルーターの`onRendered`を1回だけ購読し、描画の後に移す。ルーターは描画の後にスクロールを先頭へ戻すため、遷移の前や描画の前に移すと戻される。購読はルーターのスクロールの復元の後に呼ばれる。
- 修飾キー付きのクリックと中ボタンの押下は、新しいタブなどで開くため、移動として扱わない(`event.button === 0`で修飾キーが無いときだけ呼ぶ)。現在のページのリンクの押下も扱わない。
- 一覧の見出しは見えない見出し(`sr-only`)でもよく、`tabIndex={-1}`を付けてプログラムからだけフォーカスできるようにする。再試行の後のフォーカスの移り先も同じ見出しにする。
- スクロールは視差効果を減らす設定では即座に、それ以外は滑らかにする。固定表示のヘッダーに隠れないよう、一覧の領域に`scroll-margin-top`(`scroll-mt-*`)を付ける。
- 続けて押したときとアンマウントでは、前の購読を解除する。

## テスト

- 正規化は単体テストで、項目ごとの不正な値が既定の値になること、既定の値が`undefined`になること、全ての項目を返すこと、ページ番号の規則(1・0・負・小数・安全な整数の範囲外・10進の文字列)、数として届いた検索語と識別子を文字列へ戻すこと、条件の変更でページ番号が外れることを確かめる。
- URLの組み立ては単体テストで、既定の値の項目を省くこと、1ページ目で`page`を外すこと、数として読める検索語が引用符付きで書かれることを確かめる。
- `loader`は単体テストで、最初の表示では一覧と選択肢を部品と同じ設定で同時に取得して待つこと、取得の失敗を例外にしないこと、`cause === 'stay'`では待たないことを確かめる。
- 画面はブラウザテストで、条件の変更でページ番号を外して1ページ目を取得すること、条件の変更でスクロールとフォーカスが動かないこと、ページの移動で一覧の先頭へスクロールして見出しへフォーカスが移ること(視差効果を減らす設定の有無の両方)、再読み込みの間に直前の一覧が`inert`・`aria-busy`で残り件数の欄が読み込み中の文言になること、取得の失敗と再試行の後のフォーカス、範囲外のページの表示を確かめる。
- ページ送りはブラウザテストで、各リンクの`href`と現在のページの`aria-current`、先頭と末尾の無効のボタン、修飾キー付きのクリックで移動の知らせを呼ばないことを確かめる。
- 解決した条件への置き換えは、ルートを含むブラウザテストかE2Eテストで、URLが履歴を増やさずに置き換わり、同じ結果を取得し直さないことを確かめる。
- 自動検査(`axe-core`)の違反が0件であることを、表示・再読み込みの間・取得の失敗について、ライト・ダークの両方で確かめる。
- E2Eテストで、URLを直接開くと条件とページが復元されること、ブラウザの戻る操作で前の条件の一覧へ戻ることを確かめる。
- テストの種別と命名は「[テストの種別と命名](../testing/001-test-strategy.md#テストの種別と命名)」に従う。
