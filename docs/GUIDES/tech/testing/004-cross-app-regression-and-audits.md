# 回帰テストと監査

複数のアプリにまたがる通しのE2Eテスト、定期実行の時刻を指定した進行、全経路のアクセシビリティの自動の検査と手動の確認、セキュリティの基線、外部サービスを止めた起動での読み取りの検証、指摘の記録と担当の機能への依頼の流れを定める。テストの種別と命名は[テスト戦略](001-test-strategy.md)に従い、性能の計測は[性能の検証](003-performance-verification.md)に従う。流れの名前や件数などの本プロジェクトの値は[本プロジェクト固有の値](../../../onboardings/project-values.md)に置く。

## 前提と用語

| 用語                 | 意味                                                                                                                                                                                                                                                                         |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 通しのE2E            | 利用者側・管理者側・APIサーバーにまたがる主要な流れを、1つのE2Eテストとして最初から最後まで確かめるテスト                                                                                                                                                                    |
| 業務日付             | 定期実行と業務の判定で使う日付。定期実行の起動の時刻から決まるため、起動の時刻を指定して進める。業務日付の定義は[定期実行](../infra/003-async-processing.md#定期実行)に従う                                                                                                  |
| 業務日付の切り替わり | 業務日付が変わる時刻の前後の時間帯。実際の時刻で判定する受け付けがこの時間帯に当たると、結果が時刻で揺れるため、テストの対象外にする                                                                                                                                         |
| 全経路の一覧         | 利用者側・管理者側の全てのページの経路を、代表の状態と用意の方法とともに並べた表。アプリの生成されたルートの木と照合する                                                                                                                                                     |
| 代表の状態           | 経路を確かめるときの画面の状態。データがある・空である・誤りがある、の3つを基本とする                                                                                                                                                                                        |
| 縮退の起動           | 外部サービスの鍵や宛先を無効な値にして、そのサービスを使えない状態でアプリを起動すること。外部サービスが止まったときの振る舞いを確かめる                                                                                                                                     |
| タグ                 | E2Eテストに付ける印。`@smoke`(デプロイ後の確認)、`@prod-check`(本番の読み取りだけの確認)、`@traffic`(検証の環境での閲覧の繰り返し)、`@degraded`(縮退の起動での読み取り)。`@smoke`の規約は[デプロイ後のスモークテスト](001-test-strategy.md#デプロイ後のスモークテスト)に従う |
| 対応表               | 要件や外部サービスの障害の種類ごとに、期待する振る舞い・それを確かめる自動テスト・確かめる場所を並べた表                                                                                                                                                                     |
| 指摘                 | 検証で見つけた、要件に合わない箇所の記録。重大度・担当の機能・状態を持つ                                                                                                                                                                                                     |
| 受け入れた危険       | 重大度が重大・高の指摘であっても、開発者がリリースを止めないと決めた危険。決定の日・決定者・理由・見直しの条件を記録する                                                                                                                                                     |

## 通しのE2E

### 流れの単位

通しのE2Eは、利用者の流れを次の単位で分け、各単位を1つのテストファイルにする。

| 流れ                         | 確かめる内容                                                                                                                                         |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 公開までの流れ               | 登録と確認、投稿の登録、公開の予約、公開前の組み合わせ、他の利用者による投票、結果の確定、一覧への掲載と詳細の表示、参加の枠と組み合わせ、勝敗の確定 |
| 管理者の措置                 | 利用者のコンテンツの通報、管理者の措置、利用者側での非表示、投稿者への通知、監査ログへの記録                                                         |
| ヘルプとアカウント           | ヘルプ記事の公開と利用者側での検索、法務文書の表示、データのエクスポートの要求とダウンロード、退会                                                   |
| 同時の書き込み               | 多数の利用者が同じ対象へ同時に書き込んでも誤りが無く、数え上げが書き込みの件数と一致すること                                                         |
| 外部サービスを止めた読み取り | 縮退の起動で、利用者の主要な読み取りの画面が成功すること(「[外部サービスを止めた読み取り](#外部サービスを止めた読み取り縮退)」)                      |

- 決済の支払いを含む流れは、テスト用の支払い手段で支払いと反映を確かめる。外部の決済の前提(テスト用の鍵・転送先・支払い手段)が揃わない環境では、その部分を対象外として表示し、残りの段階を続ける。対象外の表示を、テストを失敗させる扱いにしない。
- 通しのE2Eの流れの各画面で、「[自動の検査](#自動の検査)」と同じ規則(WCAG 2.2のAとAAの規則)の自動の検査を行う。違反が0件であることを確かめる。

### 独立性と再現性

- 各テストは他のテストに依存せず、単独で実行できること。同じテストを繰り返しても結果が変わらないこと。
- テストの前提の利用者とデータは、画面の操作で作ることを優先する。画面から作れない状態(権限の状態・停止の状態など)だけを、ローカルのデータベースへの直接の投入で用意する。
- ローカル専用の前提(メールの受信箱の内容・ローカルのデータベースへの直接の投入・定期実行の起動)を持つテストは、`@smoke`を付けず、検証の環境のスモークテストに含めない。

### 定期実行の時刻の制御

- 定期実行の段階は、実際の時刻の経過を待たず、起動の時刻を指定して定期実行を起動することで進める。補助は[定期実行の起動](../infra/003-async-processing.md#e2eからの起動)に従う。
- 業務日付の異なる起動を、指定した順に行い、その都度の画面の結果を確かめる。
- 実際の時刻で判定する受け付けを含む段階は、起動の時刻と実際の時刻が同じ業務日付になるように組む。業務日付の切り替わりの時間帯に当たる場合は、その段階を対象外として表示する。

## 閲覧の繰り返し

- 未ログインの閲覧の流れ(主要な公開のページを順に開き、主要な照会を送る流れ)を、ブラウザのE2Eテストで繰り返す。繰り返す時間は環境変数(変数名は[本プロジェクト固有の値](../../../onboardings/project-values.md)に置く)で秒数として指定する。
- 環境変数が未設定のときは、テストを対象外と表示して成功で終わる。この成功は閲覧が行われたことを示さないため、静かな成功になる危険がある。閲覧の繰り返しの結果は、判定の道具の標本数(性能の検証の表)で確かめ、標本数が下限に満たなければ環境変数を設定して取り直す。
- このテストは`@traffic`を付け、検証の環境に対して実行する。ローカル専用の前提を持たない。
- 繰り返しで集まった計測は、[性能の検証](003-performance-verification.md#graphqlの応答時間)の標本として使う。標本が足りない操作は、このテストを繰り返して増やす。

## 全経路のアクセシビリティ

### 経路の一覧

- 利用者側・管理者側の全経路を、経路・代表の状態(データがある・空・誤り)・状態を用意する方法とともに一覧表にする。代表の状態には、未ログイン・利用者としてのログイン・管理者のロールごとのログインを含め、経路が必要とするログインの状態で開く。
- 一覧は、アプリの生成されたルートの木(ルート定義の生成物)の全経路を含むことを単体テストで確かめる。新しい経路を足したときに一覧へ足し忘れると、この単体テストが失敗する。
- 代表の状態の用意は、画面の操作またはローカルの状態の直接の用意で行う。用意の方法は、E2Eの補助として再利用する。

### 自動の検査

- 検査の道具は、axe-coreを版を固定してルートの依存に入れ、ページへ注入して使う。専用のラッパーは使わず、axe-coreを直接注入する。
- 検査の規則は、WCAG 2.2のAとAAの規則(タグ`wcag2a`・`wcag2aa`・`wcag21a`・`wcag21aa`・`wcag22aa`)とする。
- 検査は、代表の状態の描画が終わった後に行う。
- 違反が0件であれば合格とする。違反は、経路・達成基準・要素(セレクタ)を指摘として記録し、担当の機能の範囲で直した後に、同じ検査を行い直す。

### 手動の確認

自動の検査で検出できない達成基準は、チェックリストに沿ってブラウザで確かめる。

- フォーカスの順序が画面の読み順と一致すること。
- 見出しの構造が、画面の内容の階層を表していること。
- 代替テキストが、画像の役割に合っていること。
- 操作の対象の大きさが、押し間違えを防ぐ大きさであること。
- 動きのある表示を、利用者が止められること。
- 画面の幅を再配置の基準の幅(WCAG 2.2の達成基準1.4.10の320CSSピクセル相当)にしたとき、内容が1列に再配置され、横へのスクロールを要しないこと。
- 文字の間隔を利用者が変えたとき、内容が切れたり重なったりしないこと。

キーボードと画面の幅と文字列の伸びは、E2Eテストで確かめる。

- 主要な利用者の流れと管理者の措置を、キーボードだけで操作する。フォーカスが見え、フォーカスが閉じ込められないことを確かめる。
- 利用者側の各ページを、代表の幅(本プロジェクトの幅の値は[本プロジェクト固有の値](../../../onboardings/project-values.md)に置く)で表示し、レイアウトが崩れないことを確かめる。
- ブラウザの翻訳などで文字列が長くなった状態を再現し、レイアウトが崩れないことを確かめる。

スクリーンリーダーでの確認は自動化しない。主要な流れごとに確認の手順を用意し、開発者が読み上げを確かめて記録する。

## セキュリティの基線

### 確かめる項目

- 応答のセキュリティヘッダー: HSTS・`X-Content-Type-Options`・`Referrer-Policy: same-origin`・Permissions-Policy・nonce付きのCSPと`frame-ancestors 'none'`。画面の経路は、全経路の一覧の経路を1つずつ、代表の状態で開いて確かめる。一覧に載る経路は画面の経路であり、APIサーバー・イベントサーバー・画像配信の応答は一覧に載らないため、それぞれの経路へ直接要求して確かめる。どちらもローカルと検証の環境で確かめる。
- 認証のCookieの属性、認証情報を含む応答の`Cache-Control: no-store`、GraphQLのintrospectionの無効化と許可リスト外の操作・ネスト・エイリアス・バッチの拒否、公開APIのCORS、`Content-Length`の無いアップロードの拒否、画像配信ドメインへ認証のCookieが送られないこと。
- 読み取りだけで確かめられる項目は、`@smoke`と`@prod-check`を付けた基線のテストにする。本番に対して実行するのは、開発者が指示したときに限る。
- ローカルでだけ確かめられる項目(Cookieの属性の細部・`no-store`・`Content-Length`の無い要求)は、ローカル専用の基線のテストにする。

### 対応表

- 各要件について、満たしていることを示す根拠(自動テスト・設定・検証の環境での確認)を対応表にする。根拠の無い要件は指摘として記録する。
- 依存パッケージの既知の脆弱性の検査と、シークレットの検出を、リポジトリ全体で実行し、結果を記録する。記録には検出された値を書かない。
- CDNの管理画面で、マネージドのルールセットが有効であることを開発者が確かめる手順を用意する。
- 入力の境界の検証・生SQLの禁止・生HTMLの挿入の禁止・所有権の判定を、コードのレビューで確かめ、指摘を重大度とともに記録する。

## 外部サービスを止めた読み取り(縮退)

### 対応表

外部サービスごとに、障害の種類(時間切れ・認証の失敗・上限・応答の誤り)の行を作り、次の列を埋める。

- 期待する振る舞い(利用者への案内・後の再試行・操作の拒否のどれか)
- それを確かめる自動テスト(テストファイルの名前)
- 運用者へ通知されるか(エラートラッキングへの送信の有無)

対応表の全ての行の自動テストが成功することを確かめる。自動テストが無い行は、担当の機能へ追加を依頼し、記録する。通知されない障害は指摘として記録する。

### 起動の差し替え

- 道具は、外部サービスごとに、縮退の起動に使う環境変数の差し替えと起動のコマンドを表示する。差し替えの値は本物の鍵や宛先を含まない。
- 差し替えの方式は3種類ある。
  - 無効な固定の値を渡す。鍵や宛先の形式に合う無効な値で、認証の失敗・時間切れ・応答の誤りを起こす。
  - 鍵を渡さない。無効な鍵では恒久的な拒否(常に認証が通らない応答)になり、縮退の案内に倒れないサービスでは、鍵を外して「未設定」の縮退を起こす。
  - 宛先を接続できない先へ差し替える。接続の失敗や時間切れを起こす。
- 差し替えの手段が無いサービス(宛先も鍵も設定に無いサービスを含む)は、道具が別の行に表示する。そのサービスは対応表だけで確かめる。
- 呼び出し: `bun <検証の道具の入口> degraded-env <サービス名>...`。`all`は全てのサービス、`--matrix`は対応表の行を表示する。`--help`は使い方を表示する。
- 表示された起動のコマンドで、ローカルのapiとeventを差し替えを付けて起動し、`@degraded`を付けたE2Eテストを実行する。

### 読み取りの確認

- `@degraded`のテストは、縮退の起動で次の読み取りが成功することを確かめる。プロダクトの閲覧・プロフィールの表示・ディレクトリ・トップページ・ヘルプの表示。
- 道具が表示した止めたサービスの差し替えの環境変数を付けずに起動すると、そのサービスは止まっていないため、`@degraded`のテストは対象外と表示される。対象外の表示は成功の表示と並ぶため、縮退の確認を済ませた記録には、差し替えを付けて起動したことを残す。
- 書き込みを含む操作(決済・画像の判定・キーワード抽出・メール送信)は、縮退の案内が出ることか、後で再試行されることを対応表で確かめる。

## 指摘の記録と依頼

### 指摘の様式

指摘は次の項目を持つ1行の記録にする。

| 項目               | 内容                                       |
| ------------------ | ------------------------------------------ |
| ID                 | `F-<連番>`                                 |
| 見つけた検証       | 検証の名前と要件の番号                     |
| 重大度             | 重大・高・中・低のいずれか                 |
| 担当の機能         | 直すべき機能の仕様の名前                   |
| 状態               | 未着手・依頼済み・解消済み・申し送り       |
| リリースを止めるか | 重大または高で、受け入れた危険ではないもの |
| 解消の参照         | 担当の機能の作業の番号またはコミット       |
| 確かめ直した日時   | 同じ検証を再実行した日時(UTC)              |

### 依頼の流れ

1. 検証で基準を満たさない箇所を見つけ、指摘として記録する。
2. 再現の手順と計測の値を添えて、担当の機能へ依頼する。依頼には秘密の値と個人情報を含めない。
3. 担当の機能が、その機能の範囲で直す。
4. 同じ検証を再実行し、基準を満たしたことを確かめ、確かめ直した日時を記録して解消済みにする。

### 重大度と受け入れた危険

- 重大・高の指摘は、リリースの前に解消し、解消を確かめ直す。
- 中・低の指摘は、申し送りとして記録し、後の変更で扱う。
- 重大・高であっても、開発者がリリースを止めないと決めた危険は、受け入れた危険として記録する。記録には、決定の日・決定者・理由・見直しの条件を書く。受け入れた危険は、リリースを止める指摘の数に数えない。
