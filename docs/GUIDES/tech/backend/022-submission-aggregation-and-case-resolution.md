# 投稿の集約と案件の完了・再開

利用者が対象(利用者・投稿・コメントなど)について送る投稿(通報・申告など)を、同じ対象の未完了の案件へ集約し、管理者が案件の状態を変えて完了・再開する規約を定める。案件と投稿のテーブル、集約の一体の確定と未完了の案件を対象ごとに1つにする部分一意索引、受付時点の分類の名前と分類の同時の削除、状態と完了の記録、手での状態の変更と操作による完了の違い、再開と同じ対象の未完了の案件との競合、確定の条件の違反の見分け、当事者への通知の冪等のキー、対応期間と目標の超過、照会の期限、保持期間と物理削除、及びテストを扱う。

措置(他の機能の集約の状態の変更)と案件の完了を同じ一括の書き込みで確定する参加者は「[集約をまたぐ管理操作の記録](021-cross-aggregate-admin-action-records.md)」(特に「[参加者の登録口](021-cross-aggregate-admin-action-records.md#参加者の登録口)」)に、監査ログの文と最新の日時の照会は「[監査ログの記録](008-audit-logging.md)」に、確定の後の通知の依頼は「[外部の通知の冪等な反映](009-idempotent-event-reflection.md#外部の副作用の依頼)」に、一括の書き込みの取り消しは「[Cloudflare D1の制約と対処](../db/002-d1-constraints.md)」に、退会と物理削除の波及処理は「[ユーザーライフサイクルイベント](007-user-lifecycle-events.md)」と「[集約のライフサイクルイベント](012-aggregate-lifecycle-events.md)」に、日次のジョブは「[非同期処理の設計](../infra/003-async-processing.md)」に従う。投稿の受け付けの回数制限と連絡先の要否は「[会員と未ログインが同じ操作を使う投稿の制限](../security/011-mixed-identity-submission-limits.md)」に従う。

## 前提と用語

ORMにDrizzle、データベースにCloudflare D1、DIコンテナにInversifyを使い、要求ごとに処理単位のコンテナを作る構成(「[処理単位のコンテナ](002-layered-architecture-on-workers.md#処理単位のコンテナ)」)を前提とする。部品の置き場所は、共用部品・共通ライブラリの配置先と`<APIサーバーのアプリ>`の`src/`からのパスで示す。部品の名前は例であり、`<ドメイン>`は投稿を扱う機能のディレクトリの名前に置き換える。

## 使う場面

同じ対象に複数の利用者が投稿し、運営が対象ごとに1回で対応する場合に使う。1件の投稿に1件の対応をする投稿(問い合わせなど)は、投稿の行に状態を持ち(「[未ログインの投稿の保護](../security/008-anonymous-submission-protection.md)」)、案件を作らない。

- 対象ごとの件数と分類ごとの内訳を一覧に示し、件数の多い対象から対応できる。
- 措置(非公開化・停止など)は1回だけ行い、その対象の全ての申出者へ結果を知らせる。
- 完了した後に届いた投稿は新しい案件にする。完了の判断の後に新しい事情が届いたことを、完了した案件の中に埋もれさせない。

## テーブル

例のテーブル名は`cases`・`submissions`・`submission_categories`とする。

| テーブル                | 主な列                                                                                                                                                                                                                                                                                                                                                   |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cases`                 | `target_kind`・`target_id`(参照を消した案件はNULL)・`target_owner_user_id`・親の集約の列(`product_id`など)・`target_detached_at`・`status`・`status_changed_at`・`last_reported_at`・`<期間を数える分類>`の最初の受付日時・`closed_at`・`resolution`・`resolution_action_id`・`closing_reason`・投稿者への通知の状態と依頼の日時・最後の照会の日時と内容 |
| `submissions`           | `case_id`(→`cases`)・`reporter_user_id`(→`users`)・`contact_email`・`category_id`(→分類)・`category_name`(受付時点の名前)・`reason`・`reported_at`・`deleted_at`・申出者への通知の状態と依頼の日時                                                                                                                                                       |
| `submission_categories` | 名前(大文字小文字を区別しない一意)・標準の分類の印                                                                                                                                                                                                                                                                                                       |

- 状態と完了の日時は`(status IN (<完了の状態>)) = (closed_at IS NOT NULL)`のCHECKで結ぶ。完了の記録の列は完了の日時と同じ文で入れ、同じ文で消す。
- 対象への参照は`(target_id IS NULL) = (target_detached_at IS NOT NULL)`のCHECKで結ぶ。`resolution_action_id`は完了の種類が措置のときだけ持つ(CHECK)。
- 未完了の案件を対象ごとに1つにする部分一意索引を`(target_kind, target_id) WHERE closed_at IS NULL`に張る。Drizzleでは`uniqueIndex().on(table.targetKind, table.targetId).where(…)`に、索引の条件をバインド変数にしない`sql`のテンプレートで`closed_at is null`を渡して生成する。参照を消した案件は`target_id`がNULLで、SQLiteはNULLどうしを区別するため衝突しない。
- 投稿は、ログイン中の利用者のIDと連絡先を同時に持たない(`NOT (reporter_user_id IS NOT NULL AND contact_email IS NOT NULL)`)。送信元IPアドレスは保存しない。
- 案件は対象のテーブルに外部キーを張らない。対象の物理削除を止めず、削除の時期に参照だけを消す(「[保持期間と物理削除](#保持期間と物理削除)」)。`resolution_action_id`も、措置の記録が措置の機能の規則で物理削除され得るため外部キーを持たない。
- 索引は、一覧の並び(`last_reported_at`・`id`)、状態ごとの件数(`status`・`last_reported_at`)、物理削除の対象(`target_owner_user_id`・親の集約の列・`reporter_user_id`)、保持期間の削除(`closed_at`・`target_detached_at`)、依頼待ちの通知(通知の状態・`case_id`)に張る。

## 集約の一体の確定

投稿の受け付けは、案件の作成か更新と投稿の挿入を1つの一括の書き込みで確定する。案件を読んでから作るか決めると、同じ対象への同時の2件がどちらも案件が無いと読み、2つ目の案件の作成が一意索引の違反で失敗する。

```typescript
const caseUpsert = db
  .insert(cases)
  .values({ id: newCaseId, targetKind, targetId, lastReportedAt: at /* … */ })
  .onConflictDoUpdate({
    target: [cases.targetKind, cases.targetId],
    // 部分一意索引を衝突の対象にするには、索引と同じ条件をバインド変数にせずsqlで書く
    targetWhere: sql`${cases.closedAt} is null`,
    set: {
      lastReportedAt: sql`max(${cases.lastReportedAt}, excluded.last_reported_at)`,
      firstMarkedAt: sql`coalesce(${cases.firstMarkedAt}, excluded.first_marked_at)`,
      updatedAt: sql`excluded.updated_at`,
    },
  });

const openCaseId = db
  .select({ id: cases.id })
  .from(cases)
  .where(
    and(
      eq(cases.targetKind, targetKind),
      eq(cases.targetId, targetId),
      isNull(cases.closedAt),
    ),
  );
const categoryName = db
  .select({ name: submissionCategories.name })
  .from(submissionCategories)
  .where(eq(submissionCategories.id, categoryId));

await db.batch([
  caseUpsert,
  db.insert(submissions).values({
    id: submissionId,
    caseId: sql`(${openCaseId})`,
    categoryName: sql`(${categoryName})`,
    /* … */
  }),
]);
```

- 衝突は`onConflictDoUpdate`の`targetWhere`で扱い、`onConflictDoNothing({ target, where })`は使わない(「[ユニーク制約のあるテーブルへの追加](../db/002-d1-constraints.md#ユニーク制約のあるテーブルへの追加)」)。完了した案件は索引の外にあるため、完了の後の投稿は新しい案件を作る。
- 投稿の案件のIDと受付時点の分類の名前は、副問い合わせで同じ一括の書き込みの中で埋める。前の文が作るか更新した未完了の案件を引くため、読み直さない。
- 最後の受付日時は`MAX`で更新する。受付日時は要求の初めに読み、対象の確認と回数制限を挟んでから書き込むため、先に時刻を読んだ要求が後で確定し得る。`<期間を数える分類>`の最初の受付日時は`COALESCE`で、最初の値を後の投稿で上書きしない。`updated_at`は後で確定した要求の値になり、戻り得る。
- 分類の名前を投稿の行に写し、分類の名前の変更・削除の後も受付時点の名前を示す。分類の削除は投稿を標準の分類へ付け替え、受付時点の名前は変えない。
- 分類が同時に削除されると、副問い合わせの名前がNULLになり、NOT NULLの違反で一括の書き込み全体が取り消される。SQLiteはNOT NULLを外部キーより先に検査するため、違反の文言(`NOT NULL constraint failed: <投稿のテーブル>.category_name`)を原因の連鎖でたどって見分け、分類の不在の結果を返す。他の失敗はそのまま投げる。

## 状態と完了の記録

状態は未対応・対応中・対応済・却下の4つで、完了の記録は最後の完了のものだけを持つ。状態を変える経路は、手での状態の変更と操作による完了の2つに分ける。

| 経路             | 変更できる組み合わせ                         | 理由                                  | 当事者への通知                                          | 監査ログ                                                                         |
| ---------------- | -------------------------------------------- | ------------------------------------- | ------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 手での状態の変更 | 現在と異なる全ての状態(完了どうしも含む)     | 未対応⇄対応中は任意、完了と再開は必須 | 送らない。依頼待ち(`pending`)の通知を`none`へ取りやめる | 状態の変更の種別に変更前と後の状態。完了は完了の種別に詳細`manual`と変更前の状態 |
| 操作による完了   | 未完了の案件から対応済(措置・措置なし)・却下 | 必須                                  | 申出者へ結果を、却下では投稿者へも却下を依頼待ちにする  | 完了の種別に詳細`operation`と変更前の状態                                        |

- 手での状態の変更は、変更前と後の状態から種類(`progress`・`close`・`reopen`)を決める。変更後が完了なら完了どうしでも`close`にして完了の記録を書き直し、変更前が完了で変更後が未完了なら`reopen`、他は`progress`にする。同じ状態への変更は入力の誤りにする。
- 手での完了は運営の記録の訂正などに使い、通知しない。通知を送る完了は操作で行う。手での完了と再開は、依頼済み(`requested`)と送らなかった(`skipped`)記録を残し、まだ送っていない依頼待ちだけを取りやめる。
- 操作による完了は未完了の案件にだけ行い、完了した案件では「完了済み」の失敗を返す。完了した案件に操作するには、先に手で状態を戻す。
- 操作による完了では、通知の宛先がある投稿(ログイン中の利用者か連絡先のあるもの)を依頼待ちに、他を`none`にする。再開の後の完了では、前の完了で依頼済みの投稿も、この完了の通知として依頼待ちに戻す。退会で論理削除された投稿は対象にしない。
- 却下の投稿者への通知は依頼待ちにする。対象への参照を消した案件は投稿者を引けないため`skipped`にする。措置による完了では投稿者へ通知しない。措置の通知は措置の機能が送る。
- 措置による完了は、措置の機能の操作に参加を付けて行い、参加者が完了の文を措置と同じ一括の書き込みに加える(「[参加者の登録口](021-cross-aggregate-admin-action-records.md#参加者の登録口)」)。参加者は案件を読まず、参加の値と`context.actionId`(措置の記録のID)から完了の文を返す。完了済み・物理削除済みの案件は、次の節の違反で措置ごと取り消される。参照を消した案件には措置を行わない。
- 再開は、完了の日時・完了の種類・措置の記録のID・完了の理由を消す。行った措置は取り消さない(措置の取り消しは措置の機能の操作で行う)。

### 再開と未完了の案件の競合

完了した後に同じ対象へ届いた投稿は新しい未完了の案件を作るため、完了した案件を再開すると、未完了の案件が対象に2つになり得る。再開の文の`closed_at`のNULLへの更新が部分一意索引に違反し、一括の書き込み全体が取り消される。この違反を`open-case-exists`の結果にし、未完了の別の案件で対応するよう示すエラーを返す。

### 照会

`<期間を数える分類>`の案件では、投稿者へ照会(弁明・事情の確認の依頼)を送れる。照会は対応中の案件にだけ送り、最後の照会の日時と内容を案件に記録する。

- 照会の送信の依頼を先に行い、成功してから記録する。依頼の失敗では記録せずにエラーを返す。依頼の後の記録だけが失敗したときは送った照会の記録が欠けるため、報告のポートで運用者へ知らせる。
- 照会のメールには冪等のキーを渡さない。同じ内容を管理者が送り直す操作は、別の照会として送る。

## 確定の条件と違反の見分け

状態の変更・完了・照会の一括の書き込みは、次の順に文を並べる。

1. 案件の存在の検査: 案件の行が無いときだけ、NOT NULLの列(`target_kind`)にNULLを入れる行を挿入する`INSERT … SELECT … WHERE NOT EXISTS (…)`。読んだ後に案件が物理削除されていれば違反で全体を取り消す。`CASE`式の更新は行が無いと0件の更新で成功し、監査ログだけが残るためである(「[版の検査で一括の書き込み全体を取り消す](../db/002-d1-constraints.md#版の検査で一括の書き込み全体を取り消す)」)。
2. 状態の前進: `status = CASE WHEN status = <変更前の状態> THEN <変更後の状態> ELSE NULL END`(操作による完了は`status IN (<未完了の状態>)`、照会は`status = <対応中>`を条件にする)。同時に別の変更が確定していればNOT NULLの違反で全体を取り消す。
3. 他の更新: 完了の記録・投稿の通知の状態・照会の記録。
4. 監査ログの文(「[操作と同じ一括の書き込みに含める](008-audit-logging.md#操作と同じ一括の書き込みに含める)」)。前進の文の違反で同時の2回目を止めるため、監査ログの条件付きの記録(`guard`)は使わない。

| 違反の文言                                                                           | 結果               | ユースケースが返すエラー       |
| ------------------------------------------------------------------------------------ | ------------------ | ------------------------------ |
| `NOT NULL constraint failed: <案件のテーブル>.status`                                | `conflict`         | 他の操作で状態が変わった(競合) |
| `NOT NULL constraint failed: <案件のテーブル>.target_kind`                           | `not-found`        | 案件が見つからない             |
| `UNIQUE constraint failed: <案件のテーブル>.target_kind, <案件のテーブル>.target_id` | `open-case-exists` | 未完了の別の案件がある         |

- 違反は、D1のエラーが`cause`に持つSQLiteのエラーと、Drizzleが包むエラーの原因の連鎖をたどって文言で見分ける。列の名前の後を`(?::|$)`で区切り、`status`と`status_changed_at`のような前方が同じ列を取り違えない。操作ごとに起こり得る結果だけを受け、他の違反と失敗はそのまま投げる。
- SQLiteはNOT NULLを列の定義順に、CHECKと一意索引より前に検査する。存在の検査の挿入は、違反させる列のほかのNOT NULLの列に有効な値を入れ、違反の列を取り違えないようにする。
- 措置による完了で措置の機能の確定が失敗したときは、案件を読み直して、案件が無ければ案件の不在、未完了でなくなっていれば競合、他は措置の機能のエラーをそのまま返す。措置の対象の不在(措置の機能の`*_not_found`)は「対象が無い」の失敗に変え、措置なしの対応済か却下へ導く。措置の対象が既に目的の状態(変化なし)なら案件を完了せずに「措置済み」の失敗を返し、措置なしの対応済へ導く。

## 当事者への通知

通知の依頼と送り直しの流れは「[通知の依頼と送り直し](021-cross-aggregate-admin-action-records.md#通知の依頼と送り直し)」と同じで、記録の単位と冪等のキーだけが異なる。

- 申出者への結果の通知の状態は投稿ごと、投稿者への却下の通知の状態は案件ごとに持つ。完了の後に通知の部品へ案件のIDを渡し、部品が依頼待ちの記録を読んで宛先ごとにまとめる。ログイン中の利用者の投稿は利用者ごとに、未ログインの投稿は連絡先ごとに1通にまとめ、宛先の無い未ログインの投稿は`skipped`にする。
- 冪等のキーは、申出者への通知を`<まとまりの投稿のIDの最小>:<完了の日時のミリ秒>`、投稿者への通知を`<案件のID>:<完了の日時のミリ秒>`にする。完了の日時を含めるため、再開して再び完了すると新しい通知として送れる。キーに宛先と入力の値を含めない。
- 依頼待ちの記録の一覧は、退会で論理削除された投稿も含める。退会の論理削除は通知の状態を変えないため、除くと依頼待ちのまま永久に残る。通知の部品は宛先(退会した利用者の連絡先など)を引けなければ`skipped`にする。
- 通知の部品は、表示する投稿の有無で絞らずに案件を読む。全ての投稿が論理削除された案件を読めないと、その案件が日次の送り直しの先頭の枠を取り続ける。
- 日次のジョブは、完了の日時が`<送り直しの待ち時間>`より前の依頼待ちの案件を件数の上限まで送り直し、1件の失敗はログに残して続け、失敗の件数を報告のポートで1回知らせる。

## 対応期間

`<期間を数える分類>`の案件に、起点から完了までの経過と目標の超過を示す。

```typescript
export interface ResponseTimeInput {
  // <期間を数える分類>の最初の投稿の受付日時
  readonly startedAt: Date;
  readonly status: CaseStatus;
  // 完了した案件の最後の完了の日時。得られなければundefined
  readonly completedAt: Date | undefined;
  readonly now: Date;
}

export interface ResponseTime {
  readonly startedAt: Date;
  readonly completedAt: Date | null;
  // 完了した案件で完了の日時が得られなければnull
  readonly elapsedMs: number | null;
  readonly alerts: readonly ('start-overdue' | 'decision-overdue')[];
}
```

- 確認開始の超過(`start-overdue`)は、未対応のまま`now − startedAt`が`<確認開始の目標>`を超えたとき。判断の超過(`decision-overdue`)は、未完了なら`now − startedAt`が、完了なら`completedAt − startedAt`が`<判断の目標>`を超えたとき。境界は「超える」(`>`)で、ちょうどは超過でない。
- 完了から戻した案件は未完了として現在までを数え、起点は変えない。
- 日時の差だけを使う純粋な関数にする。営業日を単純な24時間で数える場合も、土日と祝日を区別しない旨を関数の定数の近くに書く。
- 完了の日時の正を監査ログに置く場合(運営の判断の記録を監査ログで残す要件など)は、案件の最後の完了の操作種別の最新の日時を`latestForMany`で一覧の対象をまとめて引く(「[最新の日時の照会](008-audit-logging.md#最新の日時の照会)」)。一覧の行ごとに照会しない。監査ログの保持期間を過ぎて得られなければ、経過を`null`・超過を空にして「不明」と示す。保持期間の削除の判定には案件の`closed_at`(完了と同じ一括の書き込みで入る)を使う。
- 照会の期限は送信の日時に`<回答の期限>`を足した日時で、期限を超えたら超過として示す。

## 保持期間と物理削除

| 契機                               | 処理                                                                                                                                                                       |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 申出者の退会                       | 同期の波及処理が、退会と同じ一括の書き込みで申出者の投稿を論理削除する(「[同期の波及処理](007-user-lifecycle-events.md#同期の波及処理)」)                                  |
| 利用者の物理削除の時期             | 申出者の投稿の物理削除(論理削除済みを含む)・投稿者の案件の対象への参照の消去・投稿が無くなった案件の削除を、毎回全て行う                                                   |
| 親の集約(投稿など)の物理削除の時期 | 親の集約とその子(コメントなど)を対象とする案件の対象への参照の消去。案件と投稿は残す                                                                                       |
| 日次のジョブ                       | 完了から`<未ログインの投稿の保持期間>`を過ぎた未ログインの投稿・参照を消してから`<参照を消した案件の保持期間>`を過ぎた案件と投稿・投稿が無くなった案件の削除をこの順に行う |

- 対象への参照の消去は、`target_id`・`target_owner_user_id`・親の集約の列をNULLにし、`target_detached_at`に処理の時刻を入れる。案件と申出者の理由は書き換えずに残し、削除された対象の識別子だけを持たない。
- 物理削除の時期の処理は、各段を上限件数ずつ行い、残りの有無を削除と同じ一括の書き込みの中で条件の行を1件読み直して決める。どれかの段に残りがあれば続きを返す(「[残りの有無を続きへ対応付ける](007-user-lifecycle-events.md#残りの有無を続きへ対応付ける)」)。投稿が無くなった案件の削除は件数だけを返すため、上限ちょうどを消した回は残りがあるとみなす。
- 投稿は案件に外部キーを持つため、論理削除済みの投稿が残る案件は削除しない。
- 未ログインの投稿の削除は`closed_at <= <予定時刻 − 保持期間>`で判定する。再開した案件は`closed_at`がNULLのため対象外で、再び完了すると新しい完了の日時から数え直す(「[状態の変更日時による判定](../security/008-anonymous-submission-protection.md#状態の変更日時による判定)」と同じ考え方)。
- 保持期間を暦の年で数える場合は、同じ日が無い2月29日を月末へ寄せ、期間に満たない案件を消さない(共通ライブラリの`core/time/utc-calendar.ts`の`utcYearsBefore`で求める)。各段は1回の起動の回数の上限まで繰り返し、残りは翌日に任せる。閾値は予定時刻から求めるため、同じ日に2回実行しても結果は変わらない。

## ログ

- 受け付けとユースケースは、操作の種類・案件と対象と操作者のID・結果・件数だけをログに出す。メールアドレス・申出者の理由・照会の内容・ハンドル・ニックネーム・名称・送信元IPアドレスを含めない(「[伏せ字の規則](../infra/004-logging-and-error-tracking.md#伏せ字の規則)」)。ユーザーを対象にする投稿の対象の参照がハンドルなら、解決した後のIDだけを出す。
- 日次のジョブと物理削除の処理は件数だけを出す。
