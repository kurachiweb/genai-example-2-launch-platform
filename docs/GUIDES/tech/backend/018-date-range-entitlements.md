# 日付の範囲で有効になる購入済みの権利

利用者が開始日と終了日を選んで1回の決済で購入し、業務日付のその範囲だけ有効になる権利(掲載の枠・利用の枠など)の規約を定める。両端を含む業務日付の期間と0:00の切り替わり、保存の状態と見せる状態の分離、表示の時点の判定、選べる範囲の求め方、重なりを前進の文で判定する方法、開始と終了の通知の依頼待ちの列、日割りの金額の整数の計算、利用できなかった区間の記録と日数の数え方、日割りの返金の時機、及びテストを扱う。

## 両端を含む業務日付の期間

- 期間は業務日付の開始日と終了日で持ち、時点で持たない。権利は開始日の0:00(業務時刻)に始まり、終了日の翌日の0:00に終わる。0:00の切り替わりを行の更新で表さず、表示の時点の今日との比較で表す(「[表示の時点の判定](#表示の時点の判定)」)。
- 日数は`countBusinessDaysInclusive(開始日, 終了日)`(両端を含む)で数え、保存する。終了日が開始日より前なら0を返すため、検証で弾く。日数は2つの暦日のUTCの0:00の差から求め、業務時刻の時点の差を日数に割らない。
- 開始日は今日から`<開始日の先までの日数>`日後まで、日数は1〜`<期間の日数の上限>`に限る。検証は違反の欄ごとに理由のコード(開始日の形式違反・過去・遠すぎる、終了日の形式違反・開始日より前・長すぎる)を返す純粋な関数にし、受付と決済の確定の両方で同じ関数を使う。画面は検証の関数を使わず、サーバーが返す選べる範囲で選ばせる(「[選べる範囲](#選べる範囲)」)。
- 決済の反映の期限は、開始日の翌日の0:00の1ミリ秒前にする。決済の機能は期限ちょうどの支払いを期限内とするため、翌日の0:00ちょうどの確定を期限切れにするには期限をその直前の時点にする。開始日を過ぎた決済は、反映の期限切れとして自動で返金される。
- 未決済の行は決済の開始の前に作り、決済の開始の失敗では同じ操作で消す。開始日を過ぎて残った未決済の行は、`<日次の保守の時刻>`のジョブが上限件数ずつ消す。

## 保存の状態と見せる状態

保存する状態は3つに限り、利用者と管理者に見せる状態は読み取りの時点で導く。0:00の切り替わり、対象の非公開化と復元、持ち主の停止と解除で行を書き換えない。

| 保存の状態        | 条件                                               | 見せる状態 |
| ----------------- | -------------------------------------------------- | ---------- |
| `pending_payment` | —                                                  | 未決済     |
| `paid`            | 対象が論理削除されている、または今日が終了日より後 | 終了       |
| `paid`            | 開始日より前で、対象が表示できない(非公開化・停止) | 停止中     |
| `paid`            | 開始日より前                                       | 予定       |
| `paid`            | 期間内で、対象が表示できない                       | 停止中     |
| `paid`            | 期間内                                             | 有効       |
| `terminated`      | —                                                  | 強制終了   |

- 表を上から評価する1つの純粋な関数にし、画面とサーバーとエクスポートが同じ関数を使う。エクスポートのように停止中を分けない出力は、開始日との前後で予定か有効へ振り分ける関数を別に置く。
- 持ち主の退会は行の論理削除(`deleted_at`)で表し、表示・通知・一覧・管理画面・エクスポートの全てから除く。対象の論理削除は、対象の削除の同期の波及処理が同じ一括の書き込みで権利の行の列(`target_deleted_at`)に記録する。管理画面の絞り込み・強制終了・重なりの判定・削除の確認の件数は、対象の照会を介さずこの列で判定する。
- 強制終了できるのは、決済済み・論理削除なし・対象の論理削除なし・終了日が今日以降の権利だけにする(停止中を含む)。判定の関数と強制終了の前進の文の条件を同じにする。

## 表示の時点の判定

有効な権利の一覧(表示する枠など)は写しを持たず、表示の時点に1回の問い合わせで求める。

```sql
SELECT entitlements.id, entitlements.tier, entitlements.target_id
FROM entitlements
JOIN <対象> ON <対象>.id = entitlements.target_id
JOIN users ON users.id = <対象>.user_id
WHERE entitlements.state = 'paid' AND entitlements.deleted_at IS NULL
  AND entitlements.starts_on <= ?1 AND entitlements.ends_on >= ?1
  AND <対象の表示の条件>
```

- `?1`は表示の時点の業務日付の今日にする。日付の列は`YYYY-MM-DD`の固定長の文字列のため、文字列の比較で前後を判定する。
- 非公開化・停止・退会・論理削除は、対象を持つ機能が公開する表示の条件(`<対象の表示の条件>`)が除き、解除されれば次の照会から含まれる。権利の機能に写しや状態の列を持たないため、解除の通知の取りこぼしで表示が戻らないことが起きない。
- 索引は`(state, starts_on, ends_on)`に置き、上流の対象のテーブルには主キーの結合だけを使って索引を足さない。名称などの表示の値は、対象の機能の一括の照会で1回で読み、件数に比例した問い合わせをしない。
- 同じ問い合わせを特定の利用者向けに使わない。時点の判定の口は「[時点・期間・一括の判定](010-subscription-entitlements.md#時点期間一括の判定)」の形にする。

## 選べる範囲

開始日と終了日の選べる範囲を、今日・選んだ開始日(任意)・同じ対象と同じ種類の決済済みの期間から1つの純粋な関数で求め、「[選べる範囲をサーバーから受け取る](../frontend/012-business-date-calendar.md#選べる範囲をサーバーから受け取る)」の形(`earliest`・`latest`・理由付きの`unavailable`)で返す。

| 範囲                           | `earliest` | `latest`                                                                                            | `unavailable`                                                                                       |
| ------------------------------ | ---------- | --------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 開始日                         | 今日       | 今日+`<開始日の先までの日数>`日                                                                     | 決済済みの期間(今日以降に掛かるもの)の各日                                                          |
| 終了日(開始日を渡したときだけ) | 開始日     | 開始日+(`<期間の日数の上限>`−1)日と、開始日より後に始まる最初の決済済みの期間の開始日の前日の早い方 | 開始日より後に始まる最初の決済済みの期間の開始日から、開始日+(`<期間の日数の上限>`−1)日まで(重なり) |

- 終了日は、後に続く決済済みの期間の開始日の前日で打ち切る。その後の日を終了日にすると、間の決済済みの期間を含んで重なるためである。打ち切った後の日も`unavailable`に重なりの理由で返し、利用者がその日を選べない理由を知れるようにする。終了日の`unavailable`は`latest`より後に並ぶため、画面はカレンダーの最後の月を`unavailable`の終わりまで広げる(「[選べない日の示し方](../frontend/012-business-date-calendar.md#選べない日の示し方)」)。
- `unavailable`の範囲は、開始日では`[earliest, latest]`に、終了日では`[開始日, 開始日+上限]`に切り詰め、切り詰めて空になる範囲(今日より前に終わる期間、上限より後に始まる期間)は作らない。
- 範囲の外の日の理由(過去・遠すぎる・開始日より前・長すぎる)は、画面が範囲の種類から決める。重なりだけをサーバーが`unavailable`で返す。
- 渡した開始日が開始日の範囲で選べない日(範囲の外・決済済みの期間の中)なら、例外にせず終了日の範囲を`null`で返す。表示中に0:00を越えた後と、申込が重なりで拒否されて範囲を取り直した後に起きるため、画面は開始日を選び直させる。開始日の形式違反だけを検証の失敗にする。
- 照会は申し込める対象(本人の対象など)だけに答え、他人の対象の決済済みの期間を返さない。照会は次の0:00の時点を返し、画面はその時点で取り直す(「[表示中の境界の取り直し](../frontend/012-business-date-calendar.md#表示中の境界の取り直し)」)。

## 重なりを前進の文で判定する

同じ対象・同じ種類の決済済みの期間は重ならない。申込の受付では重なりを読み取りで確かめて拒否するが、未決済の申込は重なってよく、決済の確定の時点の判定を前進の文の中に置く。

```sql
UPDATE entitlements SET
  state = CASE WHEN state = 'pending_payment' AND deleted_at IS NULL AND NOT EXISTS (
            SELECT 1 FROM entitlements AS other
            WHERE other.target_id = entitlements.target_id AND other.tier = entitlements.tier
              AND other.state = 'paid' AND other.deleted_at IS NULL AND other.target_deleted_at IS NULL
              AND other.id <> entitlements.id
              AND other.starts_on <= entitlements.ends_on AND other.ends_on >= entitlements.starts_on)
          THEN 'paid' ELSE NULL END,
  purchase_id = ?, amount_total = ?, paid_at = ?, start_notice = ?, updated_at = ?
WHERE id = ?
```

- 2つの期間`[a1, a2]`と`[b1, b2]`は`a1 <= b2 AND a2 >= b1`で重なる(終了日と開始日が同じ日も重なる)。読み取りの判定と文の条件と選べる範囲の関数を同じ式にする。
- 権利の付与の口は、確定の時点で読んだ行に同じ判定を行い、通らなければ付与できない購入として拒否する。通れば上の文を返し、決済の機能が購入の記録と同じ一括の書き込みで確定する。準備から確定までの間に重なる決済が確定したか、行が論理削除されたら、状態がNULLになりNOT NULLの違反で全体が取り消され、決済の機能が準備を呼び直して拒否し、全額を自動で返金する。
- 同じ行の2回目の決済(決済済み・強制終了の行への支払い)は、付与の口が拒否しても、前進の文を返して文が購入の一意索引とNOT NULLの違反で失敗しても、決済の機能が同じ二重決済の判定の鍵で確定済みの購入を見つけて二重の決済として扱う。
- 終了日を過ぎた権利と強制終了の権利は重なりに数えない。強制終了で空いた日は新しい申込に選べる。

## 開始と終了の通知の依頼待ち

開始・終了・強制終了の通知は、行の通知ごとの状態の列(`none`→`pending`→`requested`・`skipped`)で依頼待ちを記録し、送信をメッセージの処理に分ける。

| 契機                         | 依頼待ちにする通知 | 条件                                                                                     |
| ---------------------------- | ------------------ | ---------------------------------------------------------------------------------------- |
| `<開始の通知の時刻>`のジョブ | 開始               | 決済済み・論理削除なし・開始日が今日・未依頼                                             |
| `<開始の通知の時刻>`のジョブ | 終了               | 決済済み・論理削除なし・終了日が今日より前・未依頼・利用できない日の精算済み             |
| 決済の確定                   | 開始               | 確定の時刻の業務日付が開始日で、時刻が`<開始の通知の時刻>`以後(前進の文で依頼待ちにする) |
| 強制終了                     | 強制終了           | 強制終了の一括の書き込みで依頼待ちにする                                                 |
| 精算の処理                   | 終了               | 精算の後に、ジョブと同じ条件で記録する                                                   |
| `<日次の保守の時刻>`のジョブ | 開始・終了         | ジョブと同じ条件で記録し直し、依頼待ちが残っていれば送信を依頼する                       |

- 依頼待ちの記録は集合の条件付きの更新(`none`だけを`pending`へ)にし、2回実行しても結果が変わらない。決済の確定の時刻とジョブの時刻の競合(ジョブの直前の確定で依頼待ちにならなかった行)は、日次の保守のジョブの記録し直しが拾う。
- 決済の確定の時刻が開始の通知の時刻より前なら依頼待ちにせず、その日のジョブに任せる。時刻の定数はジョブの登録と前進の文で1つの定数を共有する。
- 送信の処理は依頼待ちを上限件数ずつ読み、通知ごとに`pending`→`requested`の条件付きの更新で取ってから、送る時点の条件(開始は決済済み・今日が終了日以前・対象が表示できる、終了は決済済み・対象が論理削除されていない、強制終了は強制終了の状態)を確かめる。条件に合わない・宛先が無い・送信基盤が受け付けない通知は`skipped`にし、一時的な失敗は`pending`へ戻して例外にする。依頼待ちが残れば遅延再送で続ける。
- 論理削除・強制終了の行の依頼待ちも読み出しの対象にして`skipped`にする。読み出しから除くと、依頼待ちの有無の判定が真のまま残り、日次の保守のジョブが毎日空の送信を依頼し続ける。
- 送信の依頼(メッセージの送信)の失敗は警告のログにとどめ、依頼待ちの行が残るため日次の保守のジョブが送り直す。
- 依頼待ちの部分索引(`WHERE start_notice = 'pending' OR …`)と、終了の通知と精算の対象の部分索引(`ends_on`、未精算か終了の通知が未依頼の決済済みの行だけ)を置く。統計の無いD1では状態の等号で絞れる索引が選ばれ得るため、照会は`INDEXED BY`で部分索引を指定し、部分索引の条件をリテラルで書く(バインド変数では部分索引の条件に一致せず、`INDEXED BY`が実行時のエラーになる)。

## 日割りの金額

- 日割りの金額は`floor(支払った金額 × 日数 ÷ 期間の日数)`で求め、整数の掛け算の後に割って切り捨てる。浮動小数点の割合を掛けない。金額は最小通貨単位の整数で持つ。
- 入力が整数でない・負・期間の日数が0・日数が期間の日数より大きいときは`RangeError`にする。呼び出し元がこの入力を作らないことを型と検証で保つ。
- 強制終了の未利用の日数と、利用できない日数は同じ日を含まない(「[利用できなかった日数](#利用できなかった日数)」)。両方の金額の合計は支払った金額を超えないため、管理者の手動の返金が無ければ返金の依頼の口の残りの額の検査で拒否されない。
- 見積もり(照会)と確定は同じ関数と同じ今日(処理の時点の業務日付)で求める。照会と確定の間に0:00を越えると値が変わるため、確定の結果に確定した日数と金額を返して表示する。

## 利用できなかった日数

対象の非公開化と持ち主の停止を、権利の行の写しでなく主体(対象・持ち主)ごとの区間として記録し、精算の時点に権利の期間と重ねて日数を数える。

- 区間は、非公開化・停止の確定の同期の波及処理が、同じ一括の書き込みで記録する。始まりは「同じ主体の継続中の区間が無いときだけ挿入する」(`INSERT … SELECT … WHERE NOT EXISTS`)、終わりは「継続中の区間の終わりを記録する」1文にする。時点はイベントの確定の時刻(`occurredAt`)にする。確定が取り消されれば区間も記録されない。
- 精算は、対象と持ち主の両方の区間のうち、半開区間`[開始日の0:00, 数え終わりの日の翌日の0:00)`に重なるものを読む(`started_at < to`かつ、`ended_at`がnullか`> from`)。
- 区間を日付に直すときは、始まりは時点の業務日付、終わりは区間の最後の瞬間(終わりの時点の1ミリ秒前)の業務日付にする。0:00ちょうどに解除した区間は前日までになり、解除した日を含めない。継続中の区間は数え終わりの日まで続くものとして数える。終わりが始まり以前の区間は無視する。
- 日数は、開始日から数え終わりの日までのうち、いずれかの区間に含まれる日の数にする。区間を日付の範囲に切り詰めてから併合して数え、非公開化と停止が重なった日や、1日に何度も始まり終わる区間を1日と数える。数え終わりの日が開始日より前なら0にする。
- 数え終わりの日は、通常の終わりでは終了日、強制終了では強制終了の日の前日にする。強制終了の日以後は未利用の日数として返金するため、同じ日を2回返金しない。
- 区間は権利に外部キーで結ばず、終わってから`<区間の保持日数>`日を過ぎたものを日次の保守のジョブが上限件数ずつ消す(保持の境界ちょうどの区間は残す)。主体の物理削除では主体の区間を消す。

## 日割りの返金の時機

利用できない日の返金は、非公開化の取り消し・停止の解除のたびではなく、権利の終わりに権利ごとに1回だけ求めて依頼する。解除を待たずに数えを打ち切れ、重なった停止や繰り返しの停止でも1回の計算で済むため、二重の返金が起きない。

| 権利の終わり   | 精算の起動                                                                                             | 依頼する返金                                                 |
| -------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------ |
| 終了日の経過   | 終了日の翌日の`<開始の通知の時刻>`のジョブが精算のメッセージを送る。漏れは日次の保守のジョブが送り直す | 終了日までの利用できない日数分                               |
| 強制終了の確定 | 強制終了の一括の書き込み                                                                               | 未利用の日数分と、強制終了の日の前日までの利用できない日数分 |

- 精算は1件ごとに区間の照会・決済の機能の読み取り・一括の書き込み・依頼の送信の往復を要するため、定期実行の処理では行わず、メッセージの処理で`<精算の件数の上限>`件ずつ行い、残れば遅延再送で続ける。
- 1件の精算は、精算済みの列の前進の文(決済済み・論理削除なし・対象の論理削除なし・未精算のときだけ値を書き、そうでなければNULLにする)を先頭に置き、返金の依頼の文と1つの一括の書き込みで確定する。前進の文のNOT NULLの違反だけを「条件が変わった」として飛ばし、確定したら依頼を送る。
- 返金の依頼キーは`<返金の依頼キーの接頭辞>:<購入のID>:<理由>`にし、返金の種類(未利用・利用できない日)ごとに別の理由にする。1つの購入が1つの権利に対応するため、権利ごと・種類ごとに一意になり、再実行でも返金の依頼の口が既存の依頼を返す。
- 金額が0、権利の論理削除(退会)、対象の論理削除のある権利は依頼せず返金不要にする。退会と対象の削除の同期の波及処理が、未精算の権利を同じ一括の書き込みで返金不要にする。
- 返金できる残りの額を超えると拒否されたときは、金額を空(残りの全額)にして1回だけ依頼し直す。依頼し直しの拒否を含む拒否は「[返金の後処理](017-single-elimination-brackets.md#返金の後処理)」の写像で返金不要・返金済み・拒否に分け、権利の終わりの処理を止めない。返金済みと拒否は運用者へ知らせる。
- 強制終了は2つの依頼を順に計画する。未利用の日数分を先に計画し、それが残りの全額か返金済みになったら、利用できない日数分は計画せずに返金済み(その金額が0なら返金不要)にする。確定前の残りの全額の依頼を後の計画の残りの額が数えず、決済サービスで失敗する二重の依頼を作るためである。
- 1件の精算の例外は、その権利を除いて残りの精算を続け、エラートラッキングへ送る。除く件数にも上限を設け、系統的な障害で1回の処理が実行の上限に当たらないようにする。
- 依頼を求めた日数と金額は、返金不要以外の結果でも行に残し、管理画面と運用者の調査に使う。利用者への知らせは返金の依頼の口の自動の返金の通知に頼らず、終了・強制終了の通知の本文に依頼した日数と金額を載せる。このため終了の通知は精算の後にだけ依頼待ちにする(「[開始と終了の通知の依頼待ち](#開始と終了の通知の依頼待ち)」)。

## テスト

- 期間の検証と選べる範囲は単体テストで、今日・上限の日・上限の翌日の開始日、上限の日数と上限+1日、終了日が開始日より前、実在しない日付、重なりの両端(終了日と開始日が同じ日)、後に続く期間での打ち切りとその後の重なり、今日をまたぐ期間、上限より後に始まる期間で範囲を作らないこと、選べない開始日で終了日の範囲が`null`になることを確かめる。
- 見せる状態は表の全ての行を、開始日の前日・当日・終了日・翌日と、非公開化・論理削除で確かめる。
- 日割りの金額は、全日数・1日・0日と端数の切り捨て(例: 2,100×1÷7)を確かめる。利用できない日数は、開始日より前に始まった区間・日の途中の始まりと解除・0:00ちょうどの解除・非公開化と停止の重なり・継続中の区間・数え終わりが開始日より前・強制終了の日をまたぐ区間を確かめる。
- Workers統合テストで、表示の問い合わせの0:00の前後と除外と解除、前進の文が準備の後の重なる確定と論理削除で取り消されること、同じ行の2回目の決済が二重の決済になること、反映の期限の翌日の0:00ちょうどの確定が期限切れになること、開始の通知の時刻の前後の確定、依頼待ちの記録の2回の実行で変わらないこと、精算の2回の処理で返金の依頼が増えないこと、強制終了と精算と退会の同期の競合で返金の依頼ごと取り消されることを確かめる。返金の依頼を確かめるテストは、決済の機能の購入の行(確定済み・支払いの識別子・金額)をテスト専用の書き込みで作り、返金の依頼の口が実際の行を読むようにする。
