# 監視とアラート

利用者が使う入口を外部から確かめる死活監視、エラートラッキングとメトリクスの値を使うアラートの規則、アラートの重大度と初動の対応付け、外部サービスの無料枠の使用量の通知と有償の契約への切り替え、外部ステータスページへの公開の範囲と利用者への導線の判断、稼働率の毎月の確認、監視の設定に個人情報と秘密情報を含めない規則を定める。障害の発生後の手順は「[障害対応](../operations/005-incident-response.md)」に、ログとエラートラッキングへの送信の規則は「[ログ管理とエラートラッキング](../infra/004-logging-and-error-tracking.md)」に従う。

## 前提と用語

監視は外部からの死活監視・エラートラッキング・メトリクス・ログの4つの層で行い、通知は運用担当者が受け取る経路へ送る構成を前提とする。監視の具体の対象・閾値・通知先・サービスの名前は技術ドキュメントに書かず、「[本プロジェクト固有の値](../../../onboardings/project-values.md)」に置く。

| 用語                 | 意味                                                                                                               |
| -------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 死活監視             | 外部の複数の地域から、利用者が使う入口の応答を定期的に確かめる仕組み                                               |
| 内容の確認           | 応答のステータスコードに加えて、ページが期待する語を含むかを確かめること                                           |
| アラート             | 誤り・ジョブ・外部サービスの設定・利用量・応答時間の値が、アラートの規則の条件に当たったときに運用担当者へ送る通知 |
| 重大度               | 障害の影響の大きさの区分(S1〜S4)。「[重大度](../operations/005-incident-response.md#重大度)」に従う                |
| 初動                 | 通知を受けた運用担当者が最初に取る行動。アラートの規則の表の「初動」の欄に対応付ける                               |
| 無料枠               | 外部サービスが無料で使わせる利用量の上限                                                                           |
| 閾値の割合           | 無料枠の上限に対して、通知を送る利用量の割合                                                                       |
| 外部ステータスページ | 利用者に稼働状況と稼働率を公開する、外部サービスのページ                                                           |

## 監視の層

| 層                           | 対象                                                                                                                | 手段                                                                                | 検知する例                                   |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- | -------------------------------------------- |
| 外部からの死活監視           | 利用者が使う入口(利用者向けの画面・運用者向けの入口・APIサーバーとイベントサーバーのヘルスチェック・画像配信の経路) | 外部の死活監視サービスで、複数の地域から定期的に確かめる                            | 応答しない・期待する内容を含まない           |
| エラートラッキングとトレース | サーバーとブラウザの例外、定期実行の失敗、リクエストのトレース                                                      | エラートラッキングのサービス(Sentry)のアラート                                      | 新しい種類の誤り・誤りの急増・定期実行の失敗 |
| メトリクス                   | 応答時間の分布、利用状況の傾向、外部サービスの利用量                                                                | 計測の道具の画面と通知                                                              | 応答時間の超過・無料枠の使用量               |
| ログ                         | 処理単位の要約、定期実行の要約                                                                                      | 構造化ログ(「[ログの出力](../infra/004-logging-and-error-tracking.md#ログの出力)」) | 予算の超過・遅いジョブ                       |

- ヘルスチェックの経路がデータベースを読まない場合、死活監視だけではデータベースや中継の障害を検知できない。利用者向けの画面の内容を確かめる対象を含め、その障害を検知できるようにする。
- 層をまたいで同じ障害を知らせる場合は、通知の経路と初動をアラートの規則の表で一度だけ定め、各層の通知がその行を参照する。

## 死活監視

### 対象と間隔

- 対象は、利用者が使う入口ごとに定める。対象の一覧・経路・期待する語は本プロジェクト固有の値の文書に置く。
- ヘルスチェックの経路を持たない入口は、公開されている内容を1つ選び、その経路を対象にする。
- 間隔は、外部サービスの無料の範囲で選べる最短の間隔にする。
- 複数の地域から確かめ、2つ以上の地域で失敗したときだけ通知する。1つの地域の一時的な失敗で通知しない。
- 検証環境も同じ対象で監視してよい。

### 内容の確認

- 期待する語は、利用者が見る変わりにくい見出しなど、ページの内容が変わっても外れにくい語を選ぶ。
- 語を変えるときは、監視の設定も同じ変更で直す。
- 対象の経路にクエリを付けない。利用者の値や認証の値を含む経路は対象にしない(「[個人情報と秘密情報を監視の設定に含めない](#個人情報と秘密情報を監視の設定に含めない)」)。

### 通知

- 通知は、対象の名前・時刻・失敗の種類(応答しない・期待する内容を含まない)・地域を含む。
- 通知の重大度は、対象が止まったときの影響の範囲で定める。利用者の入口が全体に応答しなければS1とする。
- 同じ失敗が続く間に同じ通知を繰り返し送らない(「[同じ文言を繰り返し送る通知](../infra/004-logging-and-error-tracking.md#同じ文言を繰り返し送る通知)」)。

## アラートの規則

### 規則の定め方

アラートの規則は1件ごとに次の4つを持つ。

1. 条件: 件数・割合・時間の窓と、比較の基準(直前の一定期間の平均など)
2. 重大度: 「障害対応」のS1〜S4
3. 通知先: 運用担当者が受け取る経路。経路の値は本プロジェクト固有の値の文書に置く
4. 初動: 通知を受けた運用担当者が最初に取る行動と、その参照先

- 新しい規則を足すときは、4つを同じ変更で定め、本プロジェクト固有の値の文書を更新する。
- 規則の重大度は、影響の大きさで選ぶ。下の表の重大度は目安であり、影響の実態が違えば、障害の記録に理由を残して付け替える。

### 規則の区分と初動

| 区分                     | 条件の例                                               | 重大度の目安 | 初動                                                                                                                  |
| ------------------------ | ------------------------------------------------------ | ------------ | --------------------------------------------------------------------------------------------------------------------- |
| 新しい種類の誤り         | 本番で初めて記録された種類の誤り                       | S3           | 内容を確かめ、担当の機能を特定する                                                                                    |
| 誤りの急増               | 誤りの件数が直前の一定期間の平均を大きく超える         | S2           | 直近のデプロイを確かめ、[ロールバックと復旧](../operations/002-rollback-and-recovery.md)の判断をする                  |
| デッドレター             | 再送を尽くしても処理できなかったメッセージが記録された | S3           | 種類を確かめ、再送の判断をする                                                                                        |
| 定期実行の失敗           | 定期実行のジョブが失敗した                             | S2           | ジョブが冪等であることを確かめてから再実行する([重複配信と冪等性](../infra/003-async-processing.md#重複配信と冪等性)) |
| 外部サービスの設定の誤り | 外部サービスの鍵・設定が無効、または欠けている         | S2           | 鍵と設定を確かめる                                                                                                    |
| 送信の上限               | メールなどの送信の日次の上限に達した                   | S3           | 上限の引き上げを申請する                                                                                              |
| 送信者情報の未設定       | 送信に必要な送信者の情報が設定されていない             | S2           | 管理の画面で設定する                                                                                                  |
| 応答時間の超過           | 主要な操作の応答時間の上位の値が基準を超えた           | S3           | 遅い操作を特定し、担当の機能へ依頼する                                                                                |
| 定期実行の予算の超過     | 定期実行の要約の時間が予算を超えた(警告)               | S3           | 要約から遅いジョブを特定し、担当の機能へ依頼する                                                                      |
| 無料枠の使用量           | 無料枠の使用量が閾値の割合に達した                     | S3           | 有償の契約への切り替えを判断する([無料枠の使用量](#無料枠の使用量))                                                   |

## 無料枠の使用量

1. 無料枠を使う外部サービスごとに、上限・数える単位(月ごとの一意な件数など)・期間・環境をまたいで共有するかを、本プロジェクト固有の値の文書に記録する。
2. 使用量が無料枠の上限に対する閾値の割合に達したら、通知を送る。閾値の割合は本プロジェクト固有の値の文書に定める。
3. 通知を設定できないプラン・サービスでは、通知の代わりに定期の確認で代える。確認の頻度は通常は週1回とし、公開の直後と検証の期間は毎日とする。確認する画面と、確認の結果を残す方法を手順に書く。
4. 検証(負荷試験・大量のデータの投入・閲覧の回帰テストなど)が無料枠を消費する場合は、検証の前後の使用量を検証の記録に残し、検証が枠を消費したことを示す。
5. 閾値に達したら、開発者が有償の契約へ切り替えるかを判断する。切り替えの手順は[本番準備と演習](../operations/006-release-readiness-and-drills.md)に示す。
6. 有償の契約の後は、使用量の通知を見直す。金額の基準の通知は、無料枠の中では金額が発生しないため働かないので、有償の契約の後に設定する。
7. 契約と通知の設定は開発者が行う(「[AIエージェントが実行しない操作](../operations/001-deployment.md#aiエージェントが実行しない操作)」)。

## 外部ステータスページ

- 公開するのは、利用者が使う本番環境の区分ごとの稼働状況と稼働率とする。運用者だけが使う入口と検証環境は載せない。
- 利用者の目に入る場所(サイトのフッターなど)へ外部ステータスページのリンクを置くかは、ページ配置の規則に定めがあればそれに従って判断する。定めが無ければ置かず、判断と理由を記録する。
- リンクを置かない間の案内は、障害の告知([外部ステータスページでの告知](../operations/005-incident-response.md#外部ステータスページでの告知))と、問い合わせへの返信で行う。リンクの掲載は、改善の提案として記録する。

## 稼働率の確認

- 目標の稼働率は本プロジェクト固有の値の文書に置く。判定は、外部ステータスページが公開する稼働率で行う。
- 毎月、前月の稼働率を外部ステータスページで確かめ、目標と比べて日付・値・判定を記録する。
- 目標を下回った場合は、障害の記録をもとに[振り返り](../operations/005-incident-response.md#振り返り)を行う。
- 計画的な停止を稼働率に含めるかは、ステータスページの定義に従い、判定の記録に残す。

## 設定の手順と試験

1. 監視の設定は開発者が監視サービスとステータスページの画面で行う。AIエージェントは行わない。
2. 設定した対象・間隔・地域・内容の確認の語・通知の経路を、本プロジェクト固有の値の文書に記録する。
3. 設定の後、検証環境の対象の1つを意図的に失敗させる(対象の経路を一時的に存在しない経路へ変える)。通知が届くことを確かめ、対象を元に戻す。
4. アラートも同様に、試験のイベントを送り、通知が届くことを確かめる。
5. 試験の結果(日時・対象・通知が届いたか)を記録する。

- 意図的な失敗の試験は検証環境の対象で行い、本番環境の対象の経路は変えない。

## 個人情報と秘密情報を監視の設定に含めない

- 監視の設定(対象のURL・内容の確認の語・アラートの条件・通知の本文・試験のイベント)に、利用者のメールアドレス・IPアドレス・利用者を表すID・トークン・鍵を含めない。
- 対象のURLのクエリに、利用者の値や認証の値を含めない。クエリを持たない経路を対象にする。
- 監視サービスとエラートラッキングの資格情報(APIのトークンなど)は[シークレットの管理](001-secret-management.md)に従って扱い、設定の画面の記録や文書に値を残さない。
- 通知の本文に利用者の入力が含まれ得る場合は、[伏せ字の規則](../infra/004-logging-and-error-tracking.md#伏せ字の規則)を通す。
