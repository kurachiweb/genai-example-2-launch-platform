# ソフトウェア要件定義書(IEEE 29148準拠)

## 1. イントロダクション

### 1.1 目的

本文書は、Launch Stadiumのソフトウェア要件を定義する。
本システムは、プロダクト同士の1対1での対戦形式によるローンチプラットフォームを提供する。
選ばれたプロダクトのみを掲載する点にこそ価値があると考え、ローンチする人や応援する人が勝利体験と成長への期待を感じられることを目指す。

### 1.2 スコープ

対象範囲に含む機能の一覧は2.2節に示す。
なお本プロジェクトでは以下の要件・機能は対象としない。

- マルチクラウドによる冗長化
- UI文言の多言語対応(日本語以外のUI表示切替)
- OSネイティブアプリ
- 複数ユーザーで1プロダクトを共同運用する組織機能及び組織アカウント
- 共同編集
- マークダウンエディタでの画像添付
- マークダウン文章表示時のコードブロックのシンタックスハイライト
- チャージバックに関する決済プラットフォームへの証拠提出(representment)自動化
- 未ログインユーザー及び停止中のユーザーからの問い合わせに対する返信

### 1.3 定義・略語

本サービスの利用者に向けた用語定義は以下の通りである。

- **パスワードリセット**: ユーザーがパスワードを忘れてしまいログインできない場合に利用する手続き
- **パスワード変更**: ログイン中ユーザーがパスワードを変更したい場合に利用する手続き
- **プロダクト**: ユーザーが投稿する、SaaS等WebサイトへのURL及び紹介内容を含む記事
- **ローンチ**: プロダクトを投稿し公開すること
- **マッチ**: 2つのプロダクト間の対戦
- **ペアリング**: ローンチする2つのプロダクトを対戦相手として組み合わせること
- **予選**: ローンチ日に行われるマッチ
- **サポーター**: マッチ中のプロダクトにUpvoteしたユーザー
- **Upvote**: プロダクトへの支持を示す投票操作。1ユーザー1マッチにつき1回のみ行え、取り消しも可能
- **最終Upvote時間**: 特定のマッチにおける最も遅いUpvoteの、マッチ開始からの経過時間。取り消されたUpvoteや退会した・管理者に停止されたユーザーによるものを除く
- **ディレクトリ**: マッチに勝利したプロダクトが掲載されるカタログ
- **週**: UTC-08:00時間で連続する月曜日から日曜日までの1週間単位、Product of the Week決定トーナメントの区切り基準となる
- **トーナメント**: 予選に勝利したプロダクト同士による、Product of the Week/Yearを選出するためのマッチ
- **再ローンチ**: 一度ローンチしたプロダクトを再度ローンチすること
- **フォロー**: 興味ある他ユーザーの動向を継続的に把握するため、あるユーザーが他ユーザーをお気に入り登録する操作
- **フォロワー**: あるユーザーをフォローしているユーザー
- **有料プラン**: 都度決済の免除及び敗北後再ローンチの間隔短縮等の特典を付与する定期課金プラン
- **APIキー**: 公開API利用時に発行される認証用の鍵
- **スポンサー広告**: ユーザーが自身の過去にローンチしたプロダクトの中から選び、対価を支払うことで所定の広告スペースに掲載する広告
- **ヘルプ記事**: 管理者がマークダウン形式で作成する、サービスの使い方や仕組み等を説明するコンテンツ
- **ヘルプ記事カテゴリ**: ヘルプ記事を分類するための、管理者側から管理するラベル

### 1.4 文書概要

本文書は、ステークホルダー要件、システム機能要件、外部インターフェース要件、非機能要件、データ要件、法的要件、国際化要件を定義する。

## 2. 全体的な記述

### 2.1 サービスの展望

Launch Stadiumは、Product HuntやUneedの競合として位置づけられる新しいローンチプラットフォームである。サッカーの試合をテーマとし、1対1での対戦形式により「必ず半分は勝者になる」仕組みを提供する。

- 予選機能
- 再ローンチ機能
- ディレクトリ機能
- ローンチへのコメント機能
- プロダクト評価機能
- 通報機能
- Product of the Week決定トーナメント機能
- Product of the Year決定トーナメント機能
- スポンサーシップ機能

- システム管理機能
  - 管理者アカウント
  - ユーザー生成コンテンツ管理
  - 管理者生成コンテンツ管理
  - 設定全般
- メール通知機能
- ファイルアップロード・配信機能
- 決済機能(都度決済)
- マークダウン文章入力機能

- レート制限機能

### 2.3 ユーザークラスと特性

- **プロダクト投稿者**: 自身のプロダクトをローンチする
- **サポーター**: 気に入ったプロダクトにUpvoteし、応援する
- **プロダクト探索者**: ディレクトリから優れたプロダクトを探す
- **システム管理者**: プラットフォーム全体を管理する

### 2.4 運用環境

- **クライアント**: モダンWebブラウザ(Chrome, Firefox, Safari, Edge最新版)
- **サーバー**: Cloudflare Workers(Workers Paidプラン)
- **インフラ**: Cloudflare各種サービス(ゾーンFreeプラン)、AWS(Amazon Rekognition)、Google Cloud(Natural Language AI)

### 2.5 設計・実装の制約

- FCP(First Contentful Paint)を最優先とした設計
- Cloudflare Workers実行環境の制約
  - Worker起動時のグローバルスコープ処理は1秒以内
  - Workerのバンドルサイズは非圧縮で64MiB以内(参考:[2026年9月4日の仕様変更](https://developers.cloudflare.com/changelog/post/2026-09-04-increased-worker-size-limit/))
  - Workers Paidプランの場合、規定値としてリクエスト毎CPU時間は30秒以内

### 2.6 前提と依存関係

- Cloudflare各種サービスの利用可能性
- Cloudflare Cron Triggers(再ローンチ制限の期限管理、個人データ削除等の定期実行基盤)の利用可能性
- Cloudflare Queues(データエクスポート・検索インデックス正規化等の非同期処理基盤)の利用可能性
- GitHubリポジトリとの連携
- Stripe(決済処理基盤)の利用可能性
- Cloudflare Email Service(本番環境のメール送信基盤)の利用可能性
- Cloudflare Turnstile(bot対策・不正防止基盤)の利用可能性
- Amazon Rekognition(画像の自動モデレーション基盤)の利用可能性
- Have I Been PwnedのPwned Passwords API(漏洩パスワード照合基盤)の利用可能性
- DISIFY API(使い捨てメールアドレス判定基盤)の利用可能性

## 3. ステークホルダー要件

### 3.1 既存サービスの課題

Product HuntやUneedなど既存のローンチプラットフォームは、数々のプロダクトが投稿される中で日毎に1位を決める仕組み。
尊敬する素晴らしいサービスであるが、以下の課題点があると感じている。

1. ランキング上位が正義という仕組み → 1位〜3位ほどの上位にならない限り注目されにくく、成功したとは見做されにくい。
2. ランキング内に全く違うカテゴリのプロダクトが混ざっている → AIのような流行りのジャンル以外は不利。
3. 頻繁な再ローンチが規約で制限されているか、そうでなくてもコミュニティから忌み嫌われかねない → AI時代の高頻度アップデートと相性が悪い。
4. ランキング上位を目指すためのローンチ前準備が多すぎる → 無名の新人は作業量でも集客力でも不利。

### 3.2 本サービスの解決策

1. ~~ランキング上位が正義という仕組み~~ → 1対1勝負なので、必ず半分は勝ちになる。毎日勝ちプロダクトを量産する仕組み。
2. ~~ランキング内に全く違うカテゴリのプロダクトが混ざっている~~ → 1対1の対戦相手は可能な限り同カテゴリのプロダクトが選ばれるため、真っ向勝負できる。
3. ~~頻繁な再ローンチが規約で制限されているか、そうでなくてもコミュニティから忌み嫌われかねない~~ → 頻繁な再ローンチをハングリー精神の表れとして容認する。
4. ~~ランキング上位を目指すためのローンチ前準備が多すぎる~~ → 勝てるまで再ローンチできるため、PDCAを回すなど対策できる。

## 4. システム機能要件

## 4.1 ユーザー機能

- **FR-USER-001**: システムは、ユーザー登録機能として、必須項目(25文字以内のニックネーム・メールアドレス・パスワード)の入力による登録機能を提供しなければならない(FR-USER-013、NFR-SECUR-024〜028、NFR-SECUR-031に対応)
- **FR-USER-002**: システムは、ユーザー登録時に利用規約とプライバシーポリシーへの同意チェックを必須とし、同意した日時を記録しなければならない
- **FR-USER-003**: システムは、ユーザー登録時にハンドル文字列として、他の未退会ユーザーや退会後未削除のユーザーの現在のハンドル文字列・保持中の旧ハンドル文字列と重複せず、予約語(FR-UPROF-012)でもないランダムな英数字12文字を自動設定しなければならない
- **FR-USER-004**: システムは、ユーザー登録時に主キーとは別の仮名化IDをUUID形式で生成し、外部キー制約を設けず、監査ログ(FR-ADMAG-001)と決済履歴(FR-PYMNT-004)のデータにのみ使用する識別子として保存しなければならない(DR-002、DR-012、DR-013に対応)
- **FR-USER-005**: システムは、ユーザー登録時にメールアドレス確認機能及び同メールの再送機能を提供し、メール内登録確認リンクの遷移先で登録処理を完了させなければならない(FR-RLMIT-001、NFR-SECUR-033〜035に対応)
- **FR-USER-006**: システムは、FR-USER-005のメールアドレス確認を済ませていないユーザーに対し、プロダクト・コメント・評価の投稿機能やUpvote、フォロー、都度決済、有料プラン加入、データエクスポート、システムからの通知メール送信を制限しなければならない
- **FR-USER-007**: システムは、新しいメールアドレスへの確認メール送信を伴うメールアドレス変更機能を提供しなければならない(FR-USER-008、NFR-SECUR-033〜035に対応)
- **FR-USER-008**: システムは、FR-USER-007のメールアドレス変更要求時に、入力されたメールアドレスが既に他の未退会ユーザーに登録済みかを大文字小文字問わず判定し、重複の有無によらず要求者へ同一のレスポンスを返し、重複がある場合は確認メールを送信してはならない(NFR-SECUR-041に対応)
- **FR-USER-009**: システムは、メールアドレスとパスワードによるログイン機能を提供しなければならない(NFR-SECUR-022〜025、NFR-SECUR-028、NFR-SECUR-031に対応)
- **FR-USER-010**: システムは、未ログインユーザー向けにメールアドレスによるパスワードリセット機能を提供しなければならない(FR-RLMIT-001、NFR-SECUR-033〜035に対応)
- **FR-USER-011**: システムは、利用者側の全ページで、ログインユーザーに対しログアウト機能を提供しなければならない(NFR-SECUR-029に対応)
- **FR-USER-012**: システムは、APIサーバー経由のユーザー登録、パスワードリセット要求、ログイン、プロフィール編集、メールアドレス変更要求、パスワード変更要求、退会の各操作時にはSW-018による検証に成功した場合のみ、その処理を許可しなければならない(LR-003に対応)
- **FR-USER-013**: システムは、ユーザー登録時に、入力されたメールアドレスが既に他の未退会ユーザーに登録済みでないかを大文字小文字問わず判定し、重複する場合は登録リクエストを拒否しなければならない
- **FR-USER-014**: システムは、メールアドレス確認完了時(メールアドレス変更時を含む)に、ローカル部をダミーに置き換えた文字列により使い捨てメールアドレスかを判定し、結果を「使い捨て」「通常」「未判定」のいずれかで保存しなければならない(SW-020、LR-003に対応)
- **FR-USER-024**: システムは、FR-USER-014の判定結果を判定サービスから得られない場合、「未判定」としてメールアドレス確認を完了させ、後から非同期で判定し直さなければならない
- **FR-USER-015**: システムは、現在のパスワードの入力とメールでの確認を求めたうえでのパスワード変更機能を提供しなければならない(NFR-SECUR-025〜027、NFR-SECUR-030、NFR-SECUR-035に対応)
- **FR-USER-016**: システムは、ユーザーが自身のログイン中セッションの一覧(端末情報・最終利用日時)を確認し、個別または一括で失効させられる機能を提供しなければならない(NFR-SECUR-028〜031に対応)
- **FR-USER-017**: システムは、ユーザーが任意でTOTPによる多要素認証を有効化・無効化でき、リカバリコードを再発行できる機能を提供しなければならない(NFR-SECUR-031、NFR-SECUR-032に対応)
- **FR-USER-018**: システムは、ユーザーが退会した場合、自身によるプロダクト・コメント・評価・通報の投稿、Upvote、自身に関連するフォロー・被フォロー一覧、スポンサー広告、問い合わせ、並びに自身及び自身のプロダクトが保持中の旧ハンドル文字列を論理削除しなければならない
- **FR-USER-025**: システムは、ユーザーが退会した場合、そのユーザーのデータエクスポートの要求の記録と、生成途中のものを含むZIPアーカイブ(FR-UDATA-003)を物理削除しなければならない
- **FR-USER-026**: システムは、退会により論理削除された問い合わせを、物理削除までの間、管理者側で読み取り専用(返信・対応ステータス変更不可)として表示しなければならない
- **FR-USER-019**: システムは、ユーザーが退会した場合、DR-002に定める期間が経過する直前の日次バッチで、FR-USER-018により論理削除されたユーザーデータ(FR-COMNT-009に定めるコメントを除く)と、そのユーザーに関するファイル(FR-UDATA-003、FR-INQRY-016、FR-FILEU-009、FR-FILEU-010、及びSW-022の隔離バケットへ移動された当該ユーザーの画像)を物理削除し、紐付くStripe Customerオブジェクトも削除しなければならない(FR-PRDCT-015、SW-005、FR-FILEU-019に対応)
- **FR-USER-027**: システムは、FR-USER-019の物理削除時、そのユーザーが投稿者であるユーザープロフィール・プロダクト・コメントへの通報の案件と通報を削除せず、対象への参照(対象・投稿者・対象のプロダクトの識別子)だけを消し、申出者の理由は書き換えずに残さなければならない
- **FR-USER-028**: システムは、FR-USER-027により対象への参照を消した通報の案件と通報を、参照の消去から3年経過後に日次バッチ処理により物理削除しなければならない
- **FR-USER-029**: システムは、保有者のユーザーが存在しないファイルを日次バッチ処理により探し、物理削除しなければならない(SW-005に対応)
- **FR-USER-020**: システムは、退会または停止済みのユーザーアカウントへのログインや、当該ユーザーによる書き込み操作(FR-USER-030・FR-USER-031に定める操作を除く)を拒否しなければならない
- **FR-USER-030**: システムは、停止済みのユーザーについて、既存セッションでのログアウト・セッション失効(FR-USER-016)・退会・データエクスポートの要求とダウンロード(FR-UDATA-001)・自身のAPIキーの削除(FR-PAPI-007)を受け付けなければならない
- **FR-USER-031**: システムは、停止済みのユーザーからの問い合わせ(FR-INQRY-001)と通報(FR-REPOT-001)を、未ログインユーザーによるものとして受け付けなければならない
- **FR-USER-021**: システムは、FR-USER-007のメールアドレス変更が完了した際、変更前のメールアドレス宛に変更完了を通知するメールを送信しなければならない
- **FR-USER-022**: システムは、FR-USER-010のパスワードリセットが完了した際、完了を通知するメールをユーザーへ送信しなければならない
- **FR-USER-023**: システムは、FR-USER-015のパスワード変更が完了した際、完了を通知するメールをユーザーへ送信しなければならない

## 4.2 ユーザープロフィール機能

- **FR-UPROF-001**: システムは、ユーザープロフィール設定機能として、必須項目(25文字以内のニックネーム・25文字以内のハンドル文字列)及び任意項目(プロフィール画像・50文字以内のヘッドライン・5,000文字以内の自己紹介・10件までの外部WebサイトURL)の入力機能を提供しなければならない
- **FR-UPROF-002**: システムは、ユーザープロフィール画像のアップロード機能として、500kB(512,000バイト)までの画像を受け付け、超過した場合は送信を拒否しなければならない(FR-FILEU-001〜010に対応)
- **FR-UPROF-003**: システムは、ユーザープロフィール設定にてハンドル文字列の入力を、英数字で始まり英数字・ハイフン・アンダースコアのみで構成された25文字以内の文字列に限り受け付けなければならない
- **FR-UPROF-004**: システムは、ユーザープロフィールの自己紹介入力を5,000文字以内のマークダウン形式で受け付け、超過した場合は保存リクエストを拒否しなければならない(FR-MDOWN-001〜010に対応)
- **FR-UPROF-005**: システムは、ユーザープロフィール設定にて入力されたハンドル文字列が既に登録済みかを大文字小文字問わず判定する機能を提供しなければならない
- **FR-UPROF-006**: システムは、FR-UPROF-005でそのハンドル文字列が他の未退会ユーザーや退会後未削除のユーザー(FR-USER-018)の現在のハンドル文字列として設定済みであれば、プロフィール保存リクエストを拒否しなければならない
- **FR-UPROF-007**: システムは、設定されたハンドル文字列をユーザー詳細ページのURLスラッグ(先頭に`@`付き)として使用しなければならない
- **FR-UPROF-008**: システムは、ユーザープロフィール設定にて10件までの外部WebサイトURLを任意の25文字以内の名前と共に入力できる機能を提供し、11件以上の入力を拒否しなければならない(NFR-SECUR-044に対応)
- **FR-UPROF-009**: システムは、ユーザープロフィールに表示する自己紹介の変換後HTML(FR-MDOWN-004)に含まれるリンクや外部WebサイトURL(FR-UPROF-008)のリンクに`rel="ugc"`を付与しなければならない
- **FR-UPROF-010**: システムは、ハンドル文字列の変更時、変更前の文字列を1つだけ保持しなければならない(既存の保持分は置き換え、大文字小文字の表記だけの変更では保持分を変えない)
- **FR-UPROF-014**: システムは、他のユーザー(退会後未削除のユーザーを含む)が保持中の旧ハンドル文字列と一致するハンドル文字列の保存を受け付け、その確定と同時に元の保持者の当該旧ハンドル文字列を物理削除しなければならない
- **FR-UPROF-011**: システムは、保持中の旧ハンドル文字列によるアクセスを現在のハンドル文字列のURLへ一時的リダイレクト(HTTP 302)し、FR-UPROF-014により旧ハンドル文字列が物理削除された時点でそのリダイレクトを止めなければならない
- **FR-UPROF-012**: システムは、別途定める予約語一覧の文字列(大文字小文字を区別しない)が入力された場合、FR-UPROF-006と同様に拒否しなければならない
- **FR-UPROF-013**: システムは、有料プランの特典を提供している間(FR-PPLAN-003・FR-PPLAN-006・FR-PPLAN-012)のユーザーについて、公開プロフィールページに有料プランへ加入中であることを示す表示を行わなければならない

## 4.4 データポータビリティ機能

## 4.5 プロダクト機能

- **FR-PRDCT-003**: システムは、プロダクト説明入力を20,000文字以内のマークダウン形式で受け付け、超過した場合は保存リクエストを拒否しなければならない(FR-MDOWN-001〜010に対応)

- **FR-PRDCT-009**: システムは、FR-PRDCT-008でそのハンドル文字列が自身を含めた未退会ユーザーや退会後未削除のユーザーが登録した他プロダクト(論理削除後に物理削除されていないものを含む)の現在のハンドル文字列として設定済みであれば、プロダクト保存リクエストを拒否しなければならない
- **FR-PRDCT-024**: システムは、他プロダクトが保持中の旧ハンドル文字列(FR-PRDCT-018)と同じハンドル文字列の設定を受け付けなければならない

- **FR-PRDCT-011**: システムは、プロダクトの論理削除機能を提供しなければならない(FR-ADMUG-009、FR-TOURW-021・FR-TOURY-021に対応)
- **FR-PRDCT-012**: システムは、ペアリング(FR-GAME-004)実行後マッチ直前、トーナメントマッチ直前(FR-TOURW-015・FR-TOURY-015)、そしてマッチ中のプロダクトのローンチ日やカテゴリ変更、論理削除を拒否しなければならない

- **FR-PRDCT-014**: システムは、APIサーバー経由のプロダクト操作時にはSW-018による検証に成功した場合のみ、その処理を許可しなければならない(LR-003に対応)

- **FR-PRDCT-016**: システムは、ユーザーの公開プロフィールページにて、ディレクトリに掲載されたプロダクト(ログインユーザー自身なら未掲載も含む)を対象にローンチ履歴表示機能を提供しなければならない(FR-DIR-001に対応)

- **FR-PRDCT-018**: システムは、プロダクトのハンドル文字列変更時、変更前の文字列をFR-UPROF-010と同様の方式で保持し、他のプロダクトが同じ文字列を設定した時点で元の保持者から取り除かなければならない
- **FR-PRDCT-019**: システムは、保持中の旧ハンドル文字列によるプロダクト詳細ページへのアクセスを、FR-UPROF-011と同様に扱わなければならない
- **FR-PRDCT-025**: システムは、旧ハンドル文字列を保持するプロダクトの論理削除時、または他のプロダクトが同じ文字列を設定した時点で、その旧ハンドル文字列による転送を終了しなければならない
- **FR-PRDCT-020**: システムは、別途定める予約語一覧の文字列(大文字小文字を区別しない)が入力された場合、FR-PRDCT-009と同様に拒否しなければならない

- **FR-PRDCT-022**: システムは、管理者により非公開化(FR-ADMUG-007)されている間も、投稿者による画面からのプロダクト内容の編集と論理削除を受け付けなければならない
- **FR-PRDCT-026**: システムは、非公開化されている間のプロダクトについて、次回ローンチ日の登録・予約を拒否しなければならない
- **FR-PRDCT-027**: システムは、非公開化されている間のプロダクトについて、公開API経由の説明文の更新(FR-PAPI-004)を、書き込みの時点で非公開化されている場合も含めて拒否しなければならない(FR-PAPI-011に対応)

## 4.7 予選機能

- **FR-GAME-002**: システムは、同カテゴリのプロダクトが奇数個だったためにFR-GAME-001でペアリングできなかったプロダクト同士を、ランダムにペアリングするよう制御しなければならない
- **FR-GAME-003**: システムは、その日にローンチするプロダクトが奇数個だったためにFR-GAME-002でペアリングできなかったプロダクトを、マッチ開始時点で勝者としなければならない
- **FR-GAME-004**: システムは、UTC-08:00時間で毎日23時45分に、ローンチを翌日に控えたプロダクトに対しFR-GAME-001〜003の処理を実行しなければならない(SW-005に対応)
- **FR-GAME-005**: システムは、予選機能として、トップページにてその日にローンチされている全ての予選マッチを一覧表示しなければならない
- **FR-GAME-006**: システムは、FR-GAME-005の予選一覧における各項目に、予選マッチ中の各プロダクト情報(ロゴ・名称・タグライン・カテゴリ・外部Webサイトを開くボタン)を表示し、加えてログインユーザー以外によるプロダクトであればUpvoteボタン(FR-VOTE-001〜005)を表示しなければならない
- **FR-GAME-007**: システムは、予選マッチ中の各プロダクト情報内にて、そのプロダクトがディレクトリ掲載対象(FR-DIR-001)またはログインユーザーにより投稿されたものであれば、詳細ページ(FR-DIR-003)に遷移する導線を設けなければならない
- **FR-GAME-008**: システムは、UTC-08:00時間でローンチ当日0時にマッチを開始し、同23時40分に終了しなければならない(SW-005に対応)
- **FR-GAME-009**: システムは、予選終了時点(FR-GAME-008に定める終了時刻、またはFR-GAME-013によりマッチが終了した時点)でUpvote数の確定値及び最終Upvote時間を保持しなければならない(SW-005に対応)
- **FR-GAME-010**: システムは、予選終了時点でUpvote数の多い方を勝者としなければならない(SW-005に対応)
- **FR-GAME-011**: システムは、予選終了時点でUpvote数が同じで1以上あれば、最終Upvote時間が早いプロダクトを勝者としなければならない(SW-005に対応)
- **FR-GAME-016**: システムは、予選終了時点でUpvote数が同じで1以上、かつ最終Upvote時間も同じであれば、先に記録されたUpvoteの側を勝者としなければならない(SW-005に対応)
- **FR-GAME-012**: システムは、予選終了時点でUpvote数が両者0であれば、どちらも敗者としなければならない(SW-005に対応)
- **FR-GAME-013**: システムは、マッチ中のプロダクトを投稿したユーザーが退会または管理者によって停止された時点、またはそのプロダクトが管理者によって非公開化された時点で、Upvote受付を停止してマッチを終了し、対戦相手を直ちに勝者としなければならない(FR-GAME-009に対応)
- **FR-GAME-014**: システムは、マッチ直前でペアリング済みのプロダクトを投稿したユーザーが退会または管理者によって停止された場合、またはそのプロダクトが管理者によって非公開化された場合は、対戦相手のプロダクトをマッチ開始時点で勝者としなければならない
- **FR-GAME-017**: システムは、FR-GAME-014の事由に両方のプロダクトが該当した場合、両者をマッチ開始時点で敗者としなければならない

## 4.8 再ローンチ機能

- **FR-TOURY-024**: システムは、Product of the Week優勝の確定時点で有料プランの特典を受けられる投稿ユーザーには、決済を求めずにその時点で参加資格を与えなければならない
- **FR-TOURY-025**: システムは、Product of the Week優勝の確定後、FR-TOURY-002の決済期限までに有料プランへ加入した投稿ユーザーには、加入が有効になった時点で参加資格を与えなければならない
- **FR-TOURY-026**: システムは、決済期限の後に反映された決済(FR-PYMNT-011)について、同一プロダクトのより新しいローンチが予約済みであれば、参加資格を与えず自動で全額返金しなければならない(FR-PYMNT-017に対応)
- **FR-TOURY-004**: システムは、UTC-08:00時間でトーナメント決勝日の6日前の23時45分に、参加資格を得たプロダクトによるトーナメントの組み合わせを、FR-TOURY-005・FR-TOURY-006の方式により決定しなければならない(SW-005に対応)
- **FR-TOURY-027**: システムは、組み合わせ決定の時点で非公開化中、または投稿ユーザーが停止中のプロダクトを組み合わせから除き、復元・停止解除後も当該トーナメントへの参加資格を停止しなければならない(FR-PYMNT-015に対応)
- **FR-TOURY-028**: システムは、組み合わせ決定の時点で参加資格を得たプロダクトが64を超える場合、Product of the Week優勝の日時が新しい順に64個を対象とし、残りの参加資格を停止しなければならない(FR-PYMNT-015に対応)
- **FR-TOURY-005**: システムは、参加プロダクト数(N)に対してトーナメント2回戦以降の参加プロダクト数が必ずN未満で最大の2の冪(最大32)になるように、1回戦の組み合わせでは参加プロダクト内で予選勝利時Upvote数が多い順に、同じUpvote数なら勝利した予選の最終Upvote時間が早い順に並べて、0個以上のプロダクトをシード扱いするよう制御しなければならない
- **FR-TOURY-006**: システムは、参加資格を得た非シードのプロダクトをローンチ日が早い順に並べ、隣接するプロダクト同士をトーナメント1回戦(FR-TOURY-007)の対戦相手として決定しなければならない
- **FR-TOURY-007**: システムは、トーナメント1回戦を決勝日の5日前に実施しなければならない。ただし参加資格を得たプロダクトが2個なら決勝日に、3〜4個なら1日前に、5〜8個なら2日前に、9〜16個なら3日前に、17〜32個なら4日前に実施しなければならない
- **FR-TOURY-008**: システムは、UTC-08:00時間でトーナメントマッチ実施日の0時にトーナメントマッチを開始し、同23時40分に終了しなければならない(SW-005に対応)
- **FR-TOURY-009**: システムは、トーナメントマッチが行われる場合、対象のプロダクト情報(FR-GAME-006)をトップページにて表示しなければならない
- **FR-TOURY-010**: システムは、トーナメントマッチ終了時点(FR-TOURY-008に定める終了時刻、またはFR-TOURY-014によりマッチが終了した時点)でUpvote数の確定値及び最終Upvote時間を保持しなければならない(SW-005に対応)
- **FR-TOURY-011**: システムは、トーナメントマッチ終了時点でUpvote数の多い方を勝者としなければならない(SW-005に対応)
- **FR-TOURY-012**: システムは、トーナメントマッチ終了時点でUpvote数が同じで1以上あれば、最終Upvote時間が早いプロダクトを勝者としなければならない(SW-005に対応)
- **FR-TOURY-030**: システムは、トーナメントマッチ終了時点でUpvote数が同じで1以上、かつ最終Upvote時間も同じであれば、先に記録されたUpvoteの側を勝者としなければならない(SW-005に対応)
- **FR-TOURY-013**: システムは、トーナメントマッチ終了時点でUpvote数が両者0であれば、どちらも敗者としなければならない(SW-005に対応)
- **FR-TOURY-014**: システムは、トーナメントマッチ中のプロダクトについて、投稿したユーザーが退会または管理者によって停止された時点、またはそのプロダクトが管理者によって非公開化された時点で、Upvote受付を停止してマッチを終了し、対戦相手を直ちに勝者としなければならない(FR-TOURY-010に対応)
- **FR-TOURY-015**: システムは、組み合わせが決定あるいは前ラウンドで勝利し、マッチ直前となっているプロダクトについて、投稿したユーザーが退会または管理者によって停止された場合、またはそのプロダクトが管理者によって非公開化された場合は、対戦相手のプロダクトをマッチ開始時点で勝者としなければならない
- **FR-TOURY-016**: システムは、トーナメントマッチの勝者同士で翌日に次ラウンドを実施しなければならない
- **FR-TOURY-029**: システムは、障害により次ラウンドの予定を実施日の0時までに作成できなかった場合、決勝が決勝実施日を過ぎても以降の実施日を1日ずつ遅らせ、NFR-OBLOG-003により検知できるようにしなければならない
- **FR-TOURY-017**: システムは、プロダクトが次ラウンドに進出した際、FR-TOURY-013・FR-TOURY-015により隣接するマッチがどちらも敗者であった場合はマッチ開始時点で勝者としてさらに次ラウンドに進出させ、これを対戦相手が決まるまで繰り返すよう制御しなければならない
- **FR-TOURY-018**: システムは、トーナメントで優勝したプロダクトにProduct of the Year賞を授与しなければならない
- **FR-TOURY-019**: システムは、トーナメントの各ラウンドに参加するプロダクト数が0である場合や、FR-TOURY-013・FR-TOURY-015により同ラウンドの全プロダクトが敗者となった場合は、トーナメントを終了すると共にFR-TOURY-018の賞をどのプロダクトにも授与しないよう制御しなければならない
- **FR-TOURY-020**: システムは、トーナメントの各ラウンドに参加するプロダクト数が1である場合は、トーナメントを終了すると共にそのプロダクトを決勝で勝利したものとして扱い、FR-TOURY-018の賞を授与しなければならない
- **FR-TOURY-021**: システムは、FR-TOURY-001の対象プロダクトが組み合わせ決定(FR-TOURY-004)前に投稿ユーザーによる個別削除(FR-PRDCT-011)または退会(FR-PRDCT-013)により論理削除された場合、トーナメントへの参加資格を失わせて、FR-TOURY-003にかかわらず以後は参加資格を与えてはならない(FR-PYMNT-009に対応)

## 4.15 スポンサーシップ機能

掲載プランの価格はStripeのダッシュボード上で設定する。

- **FR-SPONS-001**: システムは、ログインユーザー自身のプロダクトのうち、ローンチ開始時間を迎えたローンチを持ち、非公開化・論理削除されていないものから1つ選び、スポンサー広告を申し込める機能を提供しなければならない
- **FR-SPONS-002**: システムは、スポンサー広告の掲載プランとして、価格が異なる複数のティア(Legend/Gold/Silver)を提供しなければならない
- **FR-SPONS-017**: システムは、ティア毎・日毎の広告の掲載数に上限を設けず、表示条件を満たす全ての広告を表示しなければならない
- **FR-SPONS-003**: システムは、スポンサー広告の掲載期間として、UTC-08:00時間で今日から365日後までの日を開始日とする1〜366日の期間を、1日単位で選べるようにしなければならない
- **FR-SPONS-018**: システムは、同一プロダクト・同一ティアで決済済みかつ終了・強制終了していない広告と、掲載期間が1日でも重なる申し込みを拒否しなければならない
- **FR-SPONS-019**: システムは、決済確定の時点でFR-SPONS-018の重なりがある申し込みには、掲載権を与えてはならない(FR-PYMNT-017に対応)
- **FR-SPONS-004**: システムは、スポンサー広告の申し込みに対し、申し込みページ中にプラン及び期間に応じた価格(FR-PYMNT-002)を表示し、FR-PYMNT-001による都度決済を提供しなければならない(SW-016に対応)
- **FR-SPONS-005**: システムは、決済が完了した広告をFR-SPONS-003で選択した期間の間、広告スペースにて表示しなければならない(FR-SPONS-016に対応)
- **FR-SPONS-006**: システムは、トップページ・ディレクトリページ・プロダクト詳細ページの広告スペースにて、申し込まれたティアに応じ表示位置・表示サイズ等の目立ち度を制御しなければならない
- **FR-SPONS-007**: システムは、広告スペースの同一ティア内では、表示毎にランダムに広告を並べなければならない
- **FR-SPONS-008**: システムは、Legend/Goldプランのスポンサー広告にプロダクトのロゴ・名称・タグラインを、Silverプランのスポンサー広告にプロダクトのロゴ・名称を表示しなければならない
- **FR-SPONS-009**: システムは、スポンサー広告のリンクに`rel="sponsored"`を付与し、クリックされた場合は対象プロダクトの外部Webサイトを別タブで開かなければならない
- **FR-SPONS-010**: システムは、各スポンサー広告に、広告であることを明示するラベルを表示しなければならない(LR-002に対応)
- **FR-SPONS-011**: システムは、ユーザーが自身の申し込んだスポンサー広告の一覧及び掲載状況(掲載中/終了、FR-SPONS-016で表示を止めている間はその旨も含む)を確認できる機能を提供しなければならない
- **FR-SPONS-012**: システムは、APIサーバー経由のスポンサー広告申し込み操作時にはSW-018による検証に成功した場合のみ、その処理を許可しなければならない(LR-003に対応)
- **FR-SPONS-013**: システムは、UTC-08:00時間で毎日0時7分に、当日を掲載開始日とするスポンサー広告について、申し込んだユーザーへ掲載開始通知メールを送信しなければならない(SW-005に対応)
- **FR-SPONS-020**: システムは、当日を掲載開始日とする広告の決済が当日0時7分以降に確定した場合、確定の直後に掲載開始通知メールを送信しなければならない
- **FR-SPONS-014**: システムは、UTC-08:00時間で毎日0時7分に、前日を掲載終了日とするスポンサー広告について、申し込んだユーザーへ掲載終了通知メールを送信しなければならない(SW-005に対応)
- **FR-SPONS-015**: システムは、FR-SPONS-013・014の通知メール送信処理をイベントサーバーがCloudflare Queuesのconsumerとして非同期処理しなければならない(SW-004に対応)
- **FR-SPONS-016**: システムは、広告の対象プロダクトが非公開化(FR-ADMUG-007)されている間、その投稿ユーザーが停止(FR-ADMUG-004)されている間、及び論理削除(FR-PRDCT-011・FR-PRDCT-013)された後は、その広告を表示してはならない(FR-SPONS-005に対応)
- **FR-SPONS-021**: システムは、非公開化・停止により広告の表示を止めた日数分の金額(セント未満切り捨て)を、掲載期間の終わり(強制終了ではその時点)に日割りで自動返金しなければならない(FR-PYMNT-010に対応)
- **FR-SPONS-022**: システムは、FR-SPONS-021の日数を、掲載期間のうち一部でも表示を止めたUTC-08:00時間の日付の数とし、非公開化と停止が重なった日は1日と数えなければならない
- **FR-SPONS-023**: システムは、投稿ユーザーによる個別削除(FR-PRDCT-011)または退会(FR-PRDCT-013)で掲載が終わった広告には、FR-SPONS-021の返金をしてはならない

## 4.16 ヘルプページ機能

- **FR-HELP-001**: システムは、ヘルプページトップにて公開状態のヘルプ記事を全件、カテゴリ別に分類し、管理者が指定したカテゴリの並び順(FR-ADMCF-020)で表示しなければならない
- **FR-HELP-002**: システムは、ヘルプ記事一覧の各カテゴリ内で、ピン留めされた記事を先頭に、ピン留めされた記事とそれ以外の記事をそれぞれ管理者が指定した並び順(FR-ADMAG-024)で表示しなければならない

- **FR-HELP-004**: システムは、公開状態のヘルプ記事を対象に、50文字以内でのキーワード検索機能を提供しなければならない(FR-FTS-001・FR-FTS-002に対応)
- **FR-HELP-005**: システムは、下書き状態のヘルプ記事を、利用者側の一覧表示・検索結果・詳細ページへの直接URLアクセスのいずれからも参照できないよう制御しなければならない
- **FR-HELP-006**: システムは、利用者側各ページの共通フッターに、ヘルプページトップ及び全てのピン留めヘルプ記事(FR-ADMAG-011)へのリンクを、ヘルプページトップと同じ順(FR-ADMCF-020・FR-ADMAG-024)で表示しなければならない
- **FR-HELP-007**: システムは、ヘルプ記事詳細ページのURLとして、管理者側で設定されたハンドル文字列(FR-ADMAG-013)をスラッグとして使用しなければならない
- **FR-HELP-008**: システムは、ヘルプ記事詳細ページに、カテゴリ、作成した管理者、更新日時、本文、及び同カテゴリに属する他のヘルプ記事タイトルのリンク一覧を表示しなければならない

## 4.17 問い合わせチャット機能

未ログインユーザー及び停止中のログインユーザーからの問い合わせは、その連絡先メールアドレスに管理者が手動で返信するため、本機能のスコープ外とする。

- **FR-INQRY-001**: システムは、問い合わせフォームにて、未ログインユーザー及び停止(FR-ADMUG-004)中のログインユーザーから、カテゴリ・25文字以内のニックネーム・連絡先メールアドレス・5,000文字以内のメッセージを必須項目として受け付けなければならない(FR-RLMIT-002に対応)
- **FR-INQRY-021**: システムは、問い合わせフォームにて、停止中でないログインユーザーから、カテゴリ・5,000文字以内のメッセージを必須項目として受け付けなければならない
- **FR-INQRY-002**: システムは、停止中でないログインユーザーからの問い合わせと、未ログインユーザー及び停止中のログインユーザーからの問い合わせを、それぞれ別のテーブルへ保存しなければならない
- **FR-INQRY-003**: システムは、問い合わせフォームの選択肢として、問い合わせカテゴリのマスタ管理機能(FR-ADMCF-012)に登録されているカテゴリの一覧を表示しなければならない
- **FR-INQRY-004**: システムは、停止中でないログインユーザーが問い合わせフォームを開いた場合、ニックネーム及び連絡先メールアドレスの入力欄を表示せず、当該ユーザーのプロフィール画像及びニックネームを表示しなければならない
- **FR-INQRY-018**: システムは、停止中のログインユーザーが問い合わせフォームを開いた場合、未ログインユーザーと同じ入力欄を表示し、回答が入力された連絡先メールアドレスへ届く旨を表示しなければならない
- **FR-INQRY-005**: システムは、停止中でないログインユーザーが問い合わせフォームを送信する場合に限り添付ファイルの入力欄を表示し、1度に20枚まで、合計20MB(20,971,520バイト)までの複数ファイル添付を受け付け、超過した場合は送信を拒否しなければならない(FR-FILEU-001〜010に対応)
- **FR-INQRY-006**: システムは、APIサーバー経由の問い合わせフォーム送信操作時(ログインの有無を問わない)にはSW-018による検証に成功した場合のみ、その処理を許可しなければならない
- **FR-INQRY-019**: システムは、問い合わせチャットでの追加メッセージ(FR-INQRY-014)及び管理者からの返信(FR-ADMAG-019)に、SW-018による検証を求めてはならない
- **FR-INQRY-007**: システムは、問い合わせチャットページの閲覧及び利用、並びに添付ファイルのダウンロード(SW-011の配信エンドポイント)を、当該問い合わせの投稿者本人であるログインユーザー、またはログイン中の管理者アカウントに限定しなければならない
- **FR-INQRY-008**: システムは、停止中でないログインユーザーによる問い合わせフォーム送信完了後、当該問い合わせに対応する問い合わせチャットページへ遷移しなければならない
- **FR-INQRY-009**: システムは、未ログインユーザー及び停止中のログインユーザーによる問い合わせフォーム送信完了後、送信完了メッセージを表示しなければならない
- **FR-INQRY-010**: システムは、問い合わせチャットページに、問い合わせフォームで入力されたメッセージ、その後ユーザーが送信した追加メッセージ、及び管理者からの返信メッセージを時系列で一覧表示しなければならない
- **FR-INQRY-011**: システムは、管理者からの返信メッセージの項目に、対応した管理者のプロフィール画像及びニックネームを表示しなければならない
- **FR-INQRY-012**: システムは、返信メッセージを送った管理者が削除された場合、FR-INQRY-011の管理者情報に代わり削除済みとして表示しなければならない

- **FR-ADMCF-018**: システムは、有料プラン未加入のユーザーに対して有料プランへの導線を表示するかどうかを管理者が切り替えられる機能フラグの設定機能を提供しなければならない
- **FR-ADMCF-025**: システムは、FR-ADMCF-018の機能フラグがオフの間、有料プランの新規加入の受付を停止し、加入済みユーザーの特典・状態表示・Stripe Customer Portalは維持しなければならない
- **FR-ADMCF-019**: システムは、最上位管理者が、FR-NOTIF-007の送信者情報(事業者名・連絡先メールアドレス・有効な物理的郵送先住所)を各200文字以内で設定する機能を提供しなければならない(LR-005に対応)
- **FR-ADMCF-020**: システムは、モデレーター以上の権限を持つ管理者が、「その他」を含むヘルプ記事カテゴリの並び順を変更できる機能を提供し、追加したカテゴリを末尾に置かなければならない(FR-HELP-001に対応)

## 4.24 メール通知機能

- **FR-NOTIF-001**: システムは、UTC-08:00時間でマッチ前日の23時45分、ペアリング(FR-GAME-004・FR-TOURW-004・FR-TOURY-004)後にマッチ開始予告通知メールを、両プロダクトを登録したユーザーに送信しなければならない(SW-005に対応)

- **FR-NOTIF-002**: システムは、UTC-08:00時間でマッチ当日の23時45分、ペアリング(FR-GAME-004・FR-TOURW-004・FR-TOURY-004)後に勝敗結果通知メールを、両プロダクトを登録したユーザーに送信しなければならない(トーナメントの準決勝以前で勝利した場合は、翌日もマッチがあるためFR-NOTIF-001と本件を1つの通知に統合する)(SW-005に対応)

- **FR-NOTIF-003**: システムは、マッチの開始時、そのプロダクトを投稿したユーザーのフォロワーに開催通知メールを送信しなければならない

- **FR-NOTIF-006**: システムは、FR-NOTIF-003について、同一ユーザー宛の通知対象マッチが同日に複数存在する場合、1通の通知メールに集約しなければならない
- **FR-NOTIF-007**: システムは、FR-NOTIF-001〜004の通知メールに、FR-ADMCF-019で設定された送信者情報を表示しなければならない(LR-005に対応)
- **FR-NOTIF-020**: システムは、送信者情報(FR-ADMCF-019)が未設定の間、FR-NOTIF-001〜004の通知メールを送信せず、エラートラッキング(NFR-OBLOG-003)で検知できるようにしなければならない
- **FR-NOTIF-008**: システムは、FR-NOTIF-001〜004の通知メールにRFC 8058のHTTPS URIを含む`List-Unsubscribe`ヘッダー及び`List-Unsubscribe-Post: List-Unsubscribe=One-Click`ヘッダーを付与すると共に、当該URIへのPOSTリクエストをイベントサーバーで受け付け、ログイン不要かつ1クリックの操作のみで当該通知種別の配信停止を完了させる機能を提供しなければならない(LR-005に対応)
- **FR-NOTIF-021**: システムは、FR-NOTIF-002で統合した通知では、ワンクリックの配信停止の対象を勝敗結果通知の種別とし、本文に両方の通知種別の配信停止用リンクを表示しなければならない
- **FR-NOTIF-022**: システムは、FR-NOTIF-001・FR-NOTIF-002の送信を、同日23時45分のペアリング(FR-GAME-004)とトーナメントの処理(FR-TOURW-004・FR-TOURY-004)が全て完了した時点で開始しなければならない
- **FR-NOTIF-023**: システムは、23時55分までに完了しない処理がある場合、その時点でFR-NOTIF-022の送信を開始し、エラートラッキング(NFR-OBLOG-003)で検知できるようにしなければならない
- **FR-NOTIF-009**: システムは、FR-NOTIF-001〜004の通知メール本文に配信停止用リンクを表示すると共に、ログイン不要かつリンク先表示と確認操作のみで当該通知種別の配信停止が完了する機能を提供しなければならない(LR-005に対応)
- **FR-NOTIF-010**: システムは、配信停止用リンクのトークン(FR-NOTIF-008・FR-NOTIF-009)をユーザー及び通知種別ごとに発行し、NFR-SECUR-006の方式でハッシュ化して保存し、平文は送信するメール内のURLでのみ提示しなければならない
- **FR-NOTIF-011**: システムは、配信停止用リンクのトークン(FR-NOTIF-008・FR-NOTIF-009)について、ユーザーが退会するまでの間有効としなければならない
- **FR-NOTIF-012**: システムは、FR-NOTIF-001〜004の通知メール送信処理をイベントサーバーがCloudflare Queuesのconsumerとして非同期処理しなければならない(SW-004に対応)

## 4.25 ファイルアップロード・配信機能

アップロードリクエストのヘッダー検証(FR-FILEU-005)は、ストレージ課金の濫用と任意コンテンツの持ち込みを抑止するための事前制御である。`Content-Type`はクライアントの申告値でありファイル内容を保証しないため、書き込み前の実体検証(FR-FILEU-007)が必要である。
画像の機械判定は数秒から数十秒かかる非同期処理であるため、不適切な画像がアップロードされる可能性を考慮しつつも即時配信を優先し、大多数を占める適切な画像を見るユーザー体験の低下を避ける。
問い合わせの添付ファイル(FR-INQRY-016)を画像形式でもファイル用非公開バケットへ保存するのは、配信ごとの認可判定が認証Cookieの届く同一オリジンからの配信(SW-011)を前提とし、別オリジンから配信するSW-012の画像配信経路では成立しないためである。

- **FR-FILEU-001**: システムは、クリックによるファイル選択操作やドラッグ&ドロップ操作によるファイルアップロード機能を提供しなければならない
- **FR-FILEU-002**: システムは、画像ファイルのアップロード時の許可形式を、JPEG・PNG・GIF・WebP・SVGとしなければならない
- **FR-FILEU-003**: システムは、非SVG画像ファイルのアップロード時に、編集ダイアログ上でリサイズ及び切り取り(トリミング)ができる機能を提供しなければならない(FR-FILEU-002に対応)
- **FR-FILEU-024**: システムは、FR-FILEU-003の編集結果をブラウザ上で画像として作り直し(JPEGの原本はJPEG、それ以外はPNG)、アップロードしなければならない
- **FR-FILEU-025**: システムは、問い合わせの添付ファイル(FR-INQRY-016)には、画像形式であってもFR-FILEU-003の編集ダイアログを表示してはならない
- **FR-FILEU-004**: システムは、ファイル選択後アップロード開始前に、各ファイルの情報(ファイル名・サイズ・形式、画像の場合は小さなサムネイル)を表示する機能を提供しなければならない
- **FR-FILEU-005**: システムは、アップロードリクエストの`Content-Length`及び`Content-Type`ヘッダーを、アップロード種類ごとに定めた上限値及び許可形式と照合し、適合しない場合はR2への書き込み前にリクエストを拒否しなければならない(SW-009、FR-FILEU-002に対応)
- **FR-FILEU-006**: システムは、アップロードリクエストの受信時にオブジェクトキー(R2内での保存パス)を、暗号論的乱数による推測不能な十分なエントロピーを持つ識別子としてサーバー側で採番しなければならない(NFR-SECUR-039に対応)
- **FR-FILEU-007**: システムは、FR-FILEU-005でSVG及びプレーンテキスト以外と申告されたアップロードリクエストについて、先頭バイト(マジックバイト)を読み取り、申告されたMIMEタイプと一致しない場合、R2への書き込みを行わずアップロードを拒否しなければならない(SW-009に対応)
- **FR-FILEU-008**: システムは、FR-FILEU-005でSVGと申告されたアップロードリクエストについて、テキストとして読み取れるか、及びXMLとして構文が壊れていないかを検査し、いずれかを満たさない場合、R2への書き込みを行わずアップロードを拒否しなければならない(SW-009に対応)
- **FR-FILEU-009**: システムは、R2のファイル用非公開バケットへの書き込み時に、オブジェクトメタデータとして`Content-Disposition: attachment`及び`Cache-Control: private, no-store`を設定しなければならない(FR-FILEU-017、SW-009、SW-011に対応)
- **FR-FILEU-010**: システムは、画像の原本をR2の画像用非公開バケットへ保存しなければならない。ただし問い合わせの添付ファイル(FR-INQRY-016)は、画像形式であってもファイル用非公開バケットへ保存しなければならない(FR-FILEU-002に対応)
- **FR-FILEU-011**: システムは、画像用非公開バケットへ保存された画像(FR-FILEU-010)をイベントサーバー内で、JPEGでもPNGでもないフォーマットであればwasm-image-optimizationによりPNGに変換し、長辺が640px超なら縦横比を維持するように長辺を640pxにリサイズした上で、Amazon Rekognitionによる自動判定により性的・暴力・犯罪など不適切と判定された画像を隔離バケットへ移動しなければならない(SW-009、SW-017、SW-022に対応)
- **FR-FILEU-012**: システムは、画像用非公開バケットへ保存された画像(FR-FILEU-010)のうちSVGについて、FR-FILEU-011の判定に加えてスクリプトが含まれているかも検査し、含まれていれば隔離バケットへ移動しなければならない(SW-022に対応)
- **FR-FILEU-013**: システムは、FR-FILEU-011・FR-FILEU-012により隔離バケットへ移動された画像を、管理者による手動モデレーション(FR-ADMUG-013)の対象にしなければならない
- **FR-FILEU-014**: システムは、画像が隔離バケットへ移動された場合、SW-010のキャッシュパージ機能により、当該画像の全バリアントに対応するエッジキャッシュを無効化しなければならない
- **FR-FILEU-015**: システムは、SW-012の配信経路における非SVG画像の配信時に、SW-012のWorkers Images Bindingによりあらかじめ定義したサイズ・フォーマットへ変換しなければならない(FR-FILEU-002に対応)
- **FR-FILEU-016**: システムは、SW-012の配信経路におけるSVGの配信時に、NFR-SECUR-010のセキュリティヘッダに加えてトークンなしのCSP`sandbox`ディレクティブ、`default-src 'none'`及び`style-src 'unsafe-inline'`を付与し、FR-FILEU-012の判定をすり抜けたSVG内スクリプトの実行、クリックジャッキング、及びSVGを単独で開いた際の外部リソース読み込みによる閲覧者情報の外部送信を防がなければならない(FR-FILEU-002、NFR-SECUR-040に対応)
- **FR-FILEU-017**: システムは、ファイル用非公開バケットに保存したファイル(FR-FILEU-009)の配信時に、FR-FILEU-009のオブジェクトメタデータによりブラウザでのインライン表示・実行を防止しなければならない(FR-INQRY-013に対応)
- **FR-FILEU-018**: システムは、アップロードリクエストの受信時にクライアントが申告した元ファイル名から、パス区切り文字・制御文字・先頭のドットを除去し255バイト以内に切り詰めた文字列を、FR-FILEU-006のオブジェクトキーと共に保存しなければならない(FR-UDATA-002に対応)
- **FR-FILEU-019**: システムは、FR-USER-019・FR-PRDCT-021・FR-FILEU-021・FR-FILEU-022による物理削除時にSW-010のキャッシュパージ機能により、当該画像の全バリアントに対応するエッジキャッシュを無効化しなければならない
- **FR-FILEU-020**: システムは、画像ファイルのアップロード時に原本の幅・高さ(ピクセル数)を読み取り、データベースに保存しなければならない
- **FR-FILEU-021**: システムは、画像が別の画像へ差し替えられた場合、画像用非公開バケット及び隔離バケット内の旧画像を即時に物理削除しなければならない(FR-FILEU-006、DR-001に対応)
- **FR-FILEU-022**: システムは、画像がユーザーにより削除された場合、削除から14日が経過する直前の日次バッチで、画像用非公開バケット及び隔離バケット内の当該画像を物理削除しなければならない(SW-005、DR-001に対応)
- **FR-FILEU-023**: システムは、FR-FILEU-005でプレーンテキストと申告されたアップロードリクエストについて、UTF-8として読み取れないかNUL文字を含む場合、R2への書き込みを行わずアップロードを拒否しなければならない(SW-009に対応)

## 4.26 決済機能

チャージバック(dispute)は係争が60〜120日程度長期化し得るため、有料プランの特典及び都度決済により付与された権利は自動的に変更しない。特典停止が必要と判断した場合は、既存の管理者機能(ユーザー停止、FR-ADMUG-023等)により個別に対応する。チャージバックに関する証拠提出(representment)は、Stripeのダッシュボード上で管理者が直接行う。

- **FR-PYMNT-001**: システムは、Stripe Checkout Sessions APIのセッションに紐付くStripe Payment Elementによる決済情報入力機能を提供し、決済手段はカード・Apple Pay・Google Pay・Linkのみを受け付けなければならない(FR-TOURW-002・FR-TOURY-002に対応)
- **FR-PYMNT-014**: システムは、決済セッションが完了しても支払いが確定していない場合、支払いの確定を反映するまで権利を付与してはならない
- **FR-PYMNT-002**: システムは、期間の長さに比例する都度決済を提供する際、Stripeのダッシュボード上で設定した1日あたり単価をもとに、決済セッション作成時に日数を数量として指定しなければならない(FR-SPONS-004に対応)
- **FR-PYMNT-003**: システムは、イベントサーバーにてStripe Webhookにより都度決済/定期課金イベントを受信し、ユーザーの決済履歴へ反映しなければならない(NFR-SECUR-013、DR-010、DR-011に対応)
- **FR-PYMNT-004**: システムは、ユーザーが自身の決済履歴を確認できる機能を提供しなければならない
- **FR-PYMNT-005**: システムは、Stripeのダッシュボード上で管理者が手動実行した返金処理、及びFR-PYMNT-010により実行した返金処理をFR-PYMNT-003のWebhookにより受信し、ユーザーの決済履歴へ反映しなければならない(FR-PPLAN-003に対応)
- **FR-PYMNT-006**: システムは、Stripeからチャージバック(dispute)の発生通知をFR-PYMNT-003のWebhookにより受信し、ユーザーの決済履歴へ反映しなければならない
- **FR-PYMNT-007**: システムは、FR-PYMNT-006のチャージバック通知を受信した場合であっても、有料プランの特典及び都度決済により付与された権利(トーナメント参加資格、スポンサー広告掲載等)を自動的に停止・剥奪・復元してはならない
- **FR-PYMNT-008**: システムは、FR-PYMNT-003のStripe Webhookによる反映処理に加えて、決済後のランディングページ(`return_url`)表示時にも同一の反映処理を呼び出さなければならない(DR-010に対応)
- **FR-PYMNT-009**: システムは、FR-TOURW-021・FR-TOURY-021の対象プロダクトについて、参加資格の都度決済(FR-TOURW-002・FR-TOURY-002)が完了している場合は自動で全額返金しなければならない(SW-016に対応)
- **FR-PYMNT-015**: システムは、FR-TOURW-025・FR-TOURY-027・FR-TOURY-028により参加資格を停止したプロダクトについて、参加資格の都度決済が完了している場合は自動で全額返金しなければならない
- **FR-PYMNT-010**: システムは、本システムが実行する返金処理(自動返金及び各機能が依頼する全額・一部の返金)をイベントサーバーがCloudflare Queuesのconsumerとして非同期処理し、一時的エラーは再試行し、なお失敗した場合はNFR-OBLOG-003のエラートラッキングにより検知しなければならない(SW-004に対応)
- **FR-PYMNT-011**: システムは、決済期限(FR-TOURW-002・FR-TOURY-002)から組み合わせ決定(FR-TOURW-004・FR-TOURY-004)までの間に、未反映の参加資格の決済をStripe APIと突合し、決済済みならFR-PYMNT-008の反映処理を呼び出さなければならない(DR-010、SW-005に対応)
- **FR-PYMNT-012**: システムは、トーナメント参加資格の決済が完了しても組み合わせ決定(FR-TOURW-004・FR-TOURY-004)までに反映されなかった場合、FR-TOURW-003・FR-TOURY-003にかかわらず参加資格を与えず、自動で全額返金しなければならない(FR-PYMNT-011、SW-016に対応)
- **FR-PYMNT-013**: システムは、決済セッションの有効期限を、決済期限のある都度決済(FR-TOURW-002・FR-TOURY-002)では作成から24時間後と決済期限の早い方、それ以外の都度決済及び定期課金では作成から1時間後としなければならない
- **FR-PYMNT-016**: システムは、権利を付与済みの購入と同じ購入種別・同じ対象に別の決済セッションで重ねて確定した決済(二重決済)について、権利を与えず自動で全額返金しなければならない
- **FR-PYMNT-017**: システムは、権利の付与を受け持つ機能が付与できないと判定した購入の決済について、権利を与えず自動で全額返金しなければならない(FR-TOURW-024・FR-TOURY-026・FR-SPONS-019に対応)
- **FR-PYMNT-018**: システムは、自動返金(FR-PYMNT-009・FR-PYMNT-012・FR-PYMNT-015〜017)を依頼した場合、返金の旨と理由を購入したユーザー(退会済みを除く)へシステム送信メールで通知しなければならない

## 4.27 マークダウン文章入力機能

本節の機能は、マークダウン形式の入力を受け付ける全ての箇所、すなわちプロフィール自己紹介(FR-UPROF-004)、プロダクト説明文(FR-PRDCT-003)、ローンチへのコメント(FR-COMNT-001)、ヘルプ記事(FR-ADMAG-005)、利用規約・プライバシーポリシー・法的通知(FR-ADMAG-006)に共通して適用する。

- **FR-MDOWN-001**: システムは、マークダウンエディタ機能として、マークダウン構文(見出し・強調・リンク・リスト・引用・コードブロック等)の入力を補助するツールUIを入力欄と共に提供しなければならない
- **FR-MDOWN-002**: システムは、FR-MDOWN-001のツール一覧から見出しレベル1と画像を除外しなければならない
- **FR-MDOWN-003**: システムは、マークダウン入力欄ごとに、入力中内容のリアルタイムプレビュー表示機能を提供しなければならない
- **FR-MDOWN-004**: システムは、マークダウン文章をGFM(GitHub Flavored Markdown)準拠のパーサーによりHTMLへ変換して表示しなければならない
- **FR-MDOWN-005**: システムは、FR-MDOWN-004のHTML変換において、マークダウン構文のうちRaw HTMLを無効化し、通常の文字列として描画しなければならない(GFMパーサーは既定でRaw HTMLをそのまま解釈するため、明示的な無効化設定が必要)
- **FR-MDOWN-006**: システムは、FR-MDOWN-004のHTML変換時に、見出し文字列中の英数字・スペース・ハイフン・アンダースコア部分はスラッグ化(slugify)しそれ以外の文字種はURLエンコードした文字列にFR-MDOWN-011の接頭辞を付けて、アンカーIDとして各階層の見出しへ付与(同一IDには連番を追加)し、アンカーリンクとして機能させなければならない
- **FR-MDOWN-011**: システムは、FR-MDOWN-006のアンカーIDの接頭辞を既定で`user-content-`とし、1ページに複数の本文を並べる箇所では`user-content-<本文の識別子>-`としなければならない
- **FR-MDOWN-012**: システムは、本文中の`#`から始まるリンクの参照先と、脚注など本文に由来する他のIDにも、FR-MDOWN-006と同じ変換と接頭辞を適用しなければならない
- **FR-MDOWN-007**: システムは、FR-MDOWN-004のHTML変換時に、本文中のリンクについて同一オリジン内であれば同じタブで、別オリジンであれば別タブで開くよう制御しなければならない
- **FR-MDOWN-008**: システムは、FR-MDOWN-004のHTML変換時に、マークダウン構文中の見出しレベル1及び画像タグを通常の文字列として描画しなければならない
- **FR-MDOWN-009**: システムは、FR-MDOWN-004による変換後のHTMLに対し、許可タグ・許可属性のアローリスト方式によるサニタイザを適用しなければならない
- **FR-MDOWN-010**: システムは、FR-MDOWN-009のサニタイザにおいて、`href`属性及び`src`属性の値は`http`・`https`・`mailto`スキームと、`#`から始まるページ内アンカーリンクのみを許可しなければならない

## 4.28 キーワード検索機能

本節の機能は、キーワード検索を受け付ける全ての箇所、すなわちディレクトリ掲載プロダクト(FR-DIR-006)、公開ヘルプ記事(FR-HELP-004)に共通して適用する。

- **FR-FTS-001**: システムは、キーワード検索機能として、入力テキストをもとにSQLite FTS5(unicode61トークナイザ、`remove_diacritics 2`による発音区別符号の削除)の全文検索インデックスを用いたキーワード検索機能を提供しなければならない
- **FR-FTS-002**: システムは、検索実行時の入力テキストに対しNFKC正規化を行い、FTS5の`MATCH`式構文注入を防ぐために引用符をエスケープしてスペース区切りの各単語を二重引用符で囲み、各単語を前方一致(`"単語"*`)で照合しなければならない
- **FR-FTS-003**: システムは、検索対象元データの作成・編集をトリガーとして、イベントサーバーがCloudflare Queuesのconsumerとして実行する非同期処理内で検索対象の文字列をFR-FTS-004〜006に従い正規化し、全文検索用のテーブルに保存しなければならない(SW-004に対応)
- **FR-FTS-004**: システムは、正規化プロセスの段階として、マークダウン形式(FR-MDOWN-001〜010)の文章であればマークダウン構文を除去しなければならない
- **FR-FTS-005**: システムは、正規化プロセスの段階としてFR-FTS-004に次ぎ、NFKC正規化を実施しなければならない
- **FR-FTS-006**: システムは、正規化プロセスの段階としてFR-FTS-005に次ぎ、外部APIによりキーワードを抽出し、半角スペースで結合するよう処理しなければならない(SW-023に対応)
- **FR-FTS-008**: システムは、FR-FTS-006の外部APIが再試行の上限まで失敗した場合、または認証・設定の誤りで失敗した場合、正規化テキストをキーワードの代わりに索引し、日次バッチで抽出をやり直さなければならない(NFR-AVAIL-002に対応)
- **FR-FTS-009**: システムは、FR-FTS-006の外部APIがテキストの言語に対応していない場合、再試行せずに正規化テキストをキーワードの代わりに索引しなければならない
- **FR-FTS-007**: システムは、検索対象元データが削除された際、紐付く検索インデックスも即時削除しなければならない

## 4.29 レート制限機能

- **FR-RLMIT-001**: システムは、メールアドレス確認、メールアドレス変更の確認及びパスワードリセット要求のメールの送信について、宛先メールアドレス単位で1時間に3回、送信元IPアドレス単位で1時間に5回を上限としたレート制限機能をDurable Objectsにより提供し、上限超過時は429 Too Many Requestsを返却しなければならない(FR-USER-005、FR-USER-007、FR-USER-010、FR-ADMAC-012、FR-ADMAC-014、FR-RLMIT-017、COM-005に対応)
- **FR-RLMIT-021**: システムは、FR-RLMIT-001の送信回数を、メールの種類ごとに初回の送信を含めて数えなければならない
- **FR-RLMIT-002**: システムは、利用者側フロントエンドサーバーのドメインに対し、未ログインでの問い合わせ送信(停止中のユーザーによる送信を含む)について送信元IPアドレス単位で1時間に5回を上限としたレート制限機能をDurable Objectsにより提供し、上限超過時は429 Too Many Requestsを返却しなければならない(FR-INQRY-001、FR-RLMIT-017に対応)
- **FR-RLMIT-003**: システムは、利用者側フロントエンドサーバーのドメインに対し、通報について送信元IPアドレス単位で1時間に10回を上限としたレート制限機能を、ログイン中(停止中を除く)は同基準のユーザー単位レート制限も併せてDurable Objectsにより提供し、上限超過時は429 Too Many Requestsを返却しなければならない(FR-REPOT-001、FR-RLMIT-017に対応)
- **FR-RLMIT-004**: システムは、APIキー発行について、同時に有効なキー数の上限を設けず、新規発行操作(FR-PAPI-006による発行を含む)をユーザー単位で1時間に3回までに制限するレート制限機能をDurable Objectsにより提供し、上限超過時は429 Too Many Requestsを返却しなければならない(FR-PAPI-001に対応)
- **FR-RLMIT-005**: システムは、データエクスポート要求について、ユーザー単位で24時間に3回を上限としたレート制限機能をDurable Objectsにより提供し、上限超過時は429 Too Many Requestsを返却しなければならない(FR-UDATA-001に対応)
- **FR-RLMIT-006**: システムは、公開APIのうちAPIキーによる認証が必要なエンドポイントについて、APIキーを発行したユーザー単位で読み取り操作は1分あたり30回、書き込み操作(更新)は1分あたり15回を上限としたレート制限機能をDurable Objectsにより提供し、上限超過時は429 Too Many Requestsを返却しなければならない(FR-PAPI-002に対応)
- **FR-RLMIT-007**: システムは、公開APIの全エンドポイントについて、送信元IPアドレス単位で1分あたり60回を上限としたレート制限機能をRate limiterバインディングにより提供し、上限超過時は429 Too Many Requestsを返却しなければならない(FR-PAPI-002に対応)
- **FR-RLMIT-008**: システムは、利用者側・管理者側フロントエンドサーバー、APIサーバー及びイベントサーバーへのリクエストについて、Worker毎に送信元IPアドレス単位で10秒あたり100回を上限としたレート制限機能をRate limiterバインディングにより提供し、上限超過時は429 Too Many Requestsを返却しなければならない
- **FR-RLMIT-022**: システムは、決済サービスからのWebhook通知、RFC 8058のワンクリック配信停止、及びSW-012の画像配信専用ドメイン宛てのリクエストを、FR-RLMIT-008の対象から除外しなければならない
- **FR-RLMIT-009**: システムは、FR-USER-009・FR-ADMAC-002のログイン試行失敗回数のカウント(NFR-SECUR-022、NFR-SECUR-023)を、ログインが成功した時点でリセットしなければならない

- **FR-RLMIT-013**: システムは、FR-RLMIT-003の通報回数のカウントを、カウント対象期間の開始から1時間経過した時点でAlarm APIによりリセットしなければならない
- **FR-RLMIT-014**: システムは、FR-RLMIT-004のAPIキー新規発行回数のカウントを、カウント対象期間の開始から1時間経過した時点でAlarm APIによりリセットしなければならない

- **NFR-SECUR-001**: システムは、認証Cookieの名前に`__Host-`プレフィックスを付け、`Secure`属性及び`Path=/`を付与し`Domain`属性は指定せず、加えて`HttpOnly`・`SameSite=Lax`属性を付け、そのCookieによる認証を実装しなければならない(COM-003、COM-004に対応)

- **NFR-SECUR-006**: システムは、十分なエントロピーを持つ乱数として発行される秘密情報をハッシュ化する場合、Web Crypto APIの`crypto.subtle`によりHMAC-SHA512形式(固定ペッパーを鍵として使用)でハッシュ化して保存し、検証時はタイミングセーフな比較を行わなければならない

- **NFR-AVAIL-005**: システムは、デプロイ失敗時に直前の正常稼働バージョンへロールバックできなければならない
- **NFR-AVAIL-006**: システムは、Cloudflare D1データについて、RPO(目標復旧時点)24時間以内・RTO(目標復旧時間)4時間以内を満たすバックアップ・復旧体制を整備しなければならない

- **NFR-AVAIL-008**: システムは、DBマイグレーションを伴うデプロイにExpand/Contractパターンを適用し、スキーマ変更とコードデプロイを分離しなければならない(NFR-AVAIL-004、NFR-AVAIL-005に対応)

- **DR-003**: システムは、データポータビリティ機能として、ユーザーが自身のデータをエクスポートできる機能を提供しなければならない(FR-UDATA-001に対応)

- **DR-021**: システムは、ユーザーの退会時に、データエクスポートの要求の記録と残っているZIPアーカイブを物理削除しなければならない
