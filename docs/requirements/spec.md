# ソフトウェア要件定義書(IEEE 29148準拠)

## 1. イントロダクション

### 1.1 目的

本文書は、Launch Stadiumのソフトウェア要件を定義する。
本システムは、プロダクト同士の1対1での対戦形式によるローンチプラットフォームを提供する。
選ばれたプロダクトのみを掲載する点にこそ価値があると考え、ローンチする人や応援する人が勝利体験と成長への期待を感じられることを目指す。

### 1.2 スコープ

対象範囲に含む機能の一覧は2.2節に示す。
なお本プロジェクトでは以下の要件・機能は対象としない。

- マルチクラウドによる冗長化
- UI文言の多言語対応(日本語以外のUI表示切替)
- OSネイティブアプリ
- 複数ユーザーで1プロダクトを共同運用する組織機能及び組織アカウント
- 共同編集
- マークダウンエディタでの画像添付
- マークダウン文章表示時のコードブロックのシンタックスハイライト
- チャージバックに関する決済プラットフォームへの証拠提出(representment)自動化
- 未ログインユーザーからの問い合わせに対する返信

### 1.3 定義・略語

本サービスの利用者に向けた用語定義は以下の通りである。

- **パスワードリセット**: ユーザーがパスワードを忘れてしまいログインできない場合に利用する手続き
- **パスワード変更**: ログイン中ユーザーがパスワードを変更したい場合に利用する手続き
- **プロダクト**: ユーザーが投稿する、SaaS等WebサイトへのURL及び紹介内容を含む記事
- **ローンチ**: プロダクトを投稿し公開すること
- **マッチ**: 2つのプロダクト間の対戦
- **ペアリング**: ローンチする2つのプロダクトを対戦相手として組み合わせること
- **予選**: ローンチ日に行われるマッチ
- **サポーター**: マッチ中のプロダクトにUpvoteしたユーザー
- **Upvote**: プロダクトへの支持を示す投票操作。1ユーザー1マッチにつき1回のみ行え、取り消しも可能
- **最終Upvote時間**: 特定のマッチにおける最も遅いUpvoteの、マッチ開始からの経過時間。取り消されたUpvoteや退会した・管理者に停止されたユーザーによるものを除く
- **ディレクトリ**: マッチに勝利したプロダクトが掲載されるカタログ
- **週**: UTC-08:00時間で連続する月曜日から日曜日までの1週間単位、Product of the Week決定トーナメントの区切り基準となる
- **トーナメント**: 予選に勝利したプロダクト同士による、Product of the Week/Yearを選出するためのマッチ
- **再ローンチ**: 一度ローンチしたプロダクトを再度ローンチすること
- **フォロー**: 興味ある他ユーザーの動向を継続的に把握するため、あるユーザーが他ユーザーをお気に入り登録する操作
- **フォロワー**: あるユーザーをフォローしているユーザー
- **有料プラン**: 都度決済の免除及び敗北後再ローンチの間隔短縮等の特典を付与する定期課金プラン
- **APIキー**: 公開API利用時に発行される認証用の鍵
- **スポンサー広告**: ユーザーが自身の過去にローンチしたプロダクトの中から選び、対価を支払うことで所定の広告スペースに掲載する広告
- **ヘルプ記事**: 管理者がマークダウン形式で作成する、サービスの使い方や仕組み等を説明するコンテンツ
- **ヘルプ記事カテゴリ**: ヘルプ記事を分類するための、管理者側から管理するラベル

### 1.4 文書概要

本文書は、ステークホルダー要件、システム機能要件、外部インターフェース要件、非機能要件、データ要件、法的要件、国際化要件を定義する。

## 2. 全体的な記述

### 2.1 サービスの展望

Launch Stadiumは、Product HuntやUneedの競合として位置づけられる新しいローンチプラットフォームである。サッカーの試合をテーマとし、1対1での対戦形式により「必ず半分は勝者になる」仕組みを提供する。

### 2.2 サービスの機能

- ユーザー機能
- ユーザープロフィール機能
- ユーザーフォロー機能
- データポータビリティ機能
- プロダクト機能
- Upvote機能
- 予選機能
- 再ローンチ機能
- ディレクトリ機能
- ローンチへのコメント機能
- プロダクト評価機能
- 通報機能
- Product of the Week決定トーナメント機能
- Product of the Year決定トーナメント機能
- スポンサーシップ機能
- ヘルプページ機能
- 問い合わせチャット機能
- 有料プラン機能
- 公開API機能
- システム管理機能
  - 管理者アカウント
  - ユーザー生成コンテンツ管理
  - 管理者生成コンテンツ管理
  - 設定全般
- メール通知機能
- ファイルアップロード・配信機能
- 決済機能(都度決済)
- マークダウン文章入力機能
- キーワード検索機能
- レート制限機能

### 2.3 ユーザークラスと特性

- **プロダクト投稿者**: 自身のプロダクトをローンチする
- **サポーター**: 気に入ったプロダクトにUpvoteし、応援する
- **プロダクト探索者**: ディレクトリから優れたプロダクトを探す
- **システム管理者**: プラットフォーム全体を管理する

### 2.4 運用環境

- **クライアント**: モダンWebブラウザ(Chrome, Firefox, Safari, Edge最新版)
- **サーバー**: Cloudflare Workers(Workers Paidプラン)
- **インフラ**: Cloudflare各種サービス(ゾーンFreeプラン)、AWS(Amazon Rekognition)、Google Cloud(Natural Language AI)

### 2.5 設計・実装の制約

- FCP(First Contentful Paint)を最優先とした設計
- Cloudflare Workers実行環境の制約
  - Worker起動時のグローバルスコープ処理は1秒以内
  - Workerのバンドルサイズは非圧縮で64MiB以内(参考:[2026年9月4日の仕様変更](https://developers.cloudflare.com/changelog/post/2026-09-04-increased-worker-size-limit/))
  - Workers Paidプランの場合、規定値としてリクエスト毎CPU時間は30秒以内

### 2.6 前提と依存関係

- Cloudflare各種サービスの利用可能性
- Cloudflare Cron Triggers(再ローンチ制限の期限管理、個人データ削除等の定期実行基盤)の利用可能性
- Cloudflare Queues(データエクスポート・検索インデックス正規化等の非同期処理基盤)の利用可能性
- GitHubリポジトリとの連携
- Stripe(決済処理基盤)の利用可能性
- Cloudflare Email Service(本番環境のメール送信基盤)の利用可能性
- Cloudflare Turnstile(bot対策・不正防止基盤)の利用可能性
- Amazon Rekognition(画像の自動モデレーション基盤)の利用可能性
- Have I Been PwnedのPwned Passwords API(漏洩パスワード照合基盤)の利用可能性
- DISIFY API(使い捨てメールアドレス判定基盤)の利用可能性
- Sentry(エラートラッキング基盤)の利用可能性
- FlareWarden(外部ステータスページ・死活監視基盤)の利用可能性
- Google Cloud Natural Language AI(文章分析基盤)の利用可能性

## 3. ステークホルダー要件

### 3.1 既存サービスの課題

Product HuntやUneedなど既存のローンチプラットフォームは、数々のプロダクトが投稿される中で日毎に1位を決める仕組み。
尊敬する素晴らしいサービスであるが、以下の課題点があると感じている。

1. ランキング上位が正義という仕組み → 1位〜3位ほどの上位にならない限り注目されにくく、成功したとは見做されにくい。
2. ランキング内に全く違うカテゴリのプロダクトが混ざっている → AIのような流行りのジャンル以外は不利。
3. 頻繁な再ローンチが規約で制限されているか、そうでなくてもコミュニティから忌み嫌われかねない → AI時代の高頻度アップデートと相性が悪い。
4. ランキング上位を目指すためのローンチ前準備が多すぎる → 無名の新人は作業量でも集客力でも不利。

### 3.2 本サービスの解決策

1. ~~ランキング上位が正義という仕組み~~ → 1対1勝負なので、必ず半分は勝ちになる。毎日勝ちプロダクトを量産する仕組み。
2. ~~ランキング内に全く違うカテゴリのプロダクトが混ざっている~~ → 1対1の対戦相手は可能な限り同カテゴリのプロダクトが選ばれるため、真っ向勝負できる。
3. ~~頻繁な再ローンチが規約で制限されているか、そうでなくてもコミュニティから忌み嫌われかねない~~ → 頻繁な再ローンチをハングリー精神の表れとして容認する。
4. ~~ランキング上位を目指すためのローンチ前準備が多すぎる~~ → 勝てるまで再ローンチできるため、PDCAを回すなど対策できる。

## 5. 外部インターフェース要件

### 5.1 ユーザーインターフェース

- **UI-001**: システムは、レスポンシブデザインを採用しなければならない
- **UI-002**: システムは、shadcn/uiベースの一貫したデザインシステムを使用しなければならない
- **UI-003**: システムは、アクセシビリティ標準(WCAG 2.2 AA)に準拠しなければならない
- **UI-004**: システムは、フォーム入力欄からフォーカスを外した時にバリデーションフィードバック(エラー表示、送信ボタンの活性制御等)を提供しなければならない
- **UI-005**: システムは、ローディング状態・空状態(データなし)・エラー状態それぞれに対応した表示を提供しなければならない
- **UI-006**: システムは、ファイルアップロード時にプレビュー表示(画像の場合は編集ダイアログによるリサイズ・切り取りを含む)、ドラッグ&ドロップ、ファイル形式・サイズの事前フィードバックを提供しなければならない(FR-FILEU-001〜004に対応)

### 5.2 ハードウェアインターフェース

- **HW-001**: システムは、ファイルアップロード時に、クライアント端末のカメラ・ファイルシステムからのファイル選択インターフェースをサポートしなければならない

### 5.3 ソフトウェアインターフェース

- **SW-001**: システムは、利用者側・管理者側それぞれのフロントエンドサーバーとの通信にGraphQL APIを提供しなければならない(COM-003に対応)
- **SW-002**: システムは、公開APIとしてRESTful APIを提供しなければならない
- **SW-003**: システムは、データベースとしてCloudflare D1(SQLiteベース)をサポートしなければならない
- **SW-004**: システムは、Cloudflare Queuesによる非同期処理をサポートしなければならない(FR-UDATA-004、FR-FTS-003、FR-NOTIF-012〜014、FR-SPONS-015、FR-PYMNT-010、SW-009に対応)
- **SW-005**: システムは、Cloudflare Cron Triggersによる定期実行をサポートしなければならない(FR-USER-019、FR-COMNT-009、FR-PRDCT-021、FR-GAME-004、FR-GAME-008〜012、FR-TOURW-004、FR-TOURW-007、FR-TOURW-010〜013、FR-TOURY-004、FR-TOURY-008、FR-TOURY-010〜013、FR-NOTIF-001、FR-NOTIF-002、FR-SPONS-013、FR-SPONS-014、FR-PYMNT-011、DR-002、DR-004、DR-012〜017に対応)
- **SW-006**: システムは、Cloudflare Web Analyticsによるメトリクス監視をサポートしなければならない(NFR-OBLOG-001に対応)
- **SW-007**: システムは、FlareWardenによる死活監視・外部ステータスページをサポートしなければならない(NFR-AVAIL-001、NFR-OBLOG-001に対応)
- **SW-008**: システムは、Cloudflare Durable Objectsによる状態管理(厳密なレート制限カウント、ログイン試行の強制拒否クールダウン期間)をサポートしなければならない
- **SW-009**: システムは、Cloudflare R2を画像等ファイルのオブジェクトストレージとし、フロントエンドサーバー経由のストリーミングアップロードをサポートし、画像用非公開バケットへの書き込み成功後は直ちにQueueへメッセージを送信しなければならない(FR-FILEU-005〜013、NFR-SECUR-039、NFR-SECUR-042、SW-004に対応)

- **SW-011**: システムは、R2のファイル用非公開バケットに保存済みのファイルについて、利用者側・管理者側それぞれのフロントエンドサーバーが認証Cookie(NFR-SECUR-001)の届く同一オリジンにて配信エンドポイントを提供し、APIサーバーが認可判定とR2読み出しを行い、フロントエンドサーバーの中継によりストリーミング配信しなければならない(FR-INQRY-007、FR-UDATA-007に対応)

- **SW-016**: システムは、Stripe Checkout Sessions API・Stripe Refunds API・Stripe Customer Portal及びStripe Webhookによる決済処理連携を提供しなければならない
- **SW-017**: システムは、Amazon Rekognition APIを用いた画像自動判定処理を提供しなければならない(FR-FILEU-011に対応)
- **SW-018**: システムは、Cloudflare Turnstileによるウィジェット埋め込み及びAPIサーバー側でのsiteverify検証機能を提供しなければならない(FR-USER-012、FR-FOLOW-009、FR-PRDCT-014、FR-VOTE-006、FR-COMNT-008、FR-REPOT-006、FR-SPONS-012、FR-INQRY-006に対応)
- **SW-019**: システムは、Have I Been PwnedのPwned Passwords range API(k-Anonymity方式)によるパスワード漏洩照合を提供しなければならない(NFR-SECUR-026に対応)
- **SW-020**: システムは、DISIFY APIによる使い捨てメールアドレス判定を提供しなければならない(FR-USER-014に対応)
- **SW-021**: システムは、Sentryによるエラートラッキング及びパフォーマンストレーシングを提供しなければならない(NFR-OBLOG-003に対応)

### 5.4 通信インターフェース

- **COM-001**: システムは、標準的なHTTP/HTTPSプロトコルをサポートしなければならない
- **COM-002**: システムは、TLS 1.2以上による暗号化通信を使用しなければならない
- **COM-003**: システムは、公開APIのRESTエンドポイント(SW-002)を除きブラウザとAPIサーバー間の直接通信を行わせず、利用者側・管理者側それぞれのフロントエンドサーバーがAPIサーバーへのGraphQLリクエスト、SW-009のファイルアップロードリクエスト、及びSW-011のファイルダウンロードリクエストを中継しなければならない(NFR-PERF-005、NFR-SECUR-001、NFR-SECUR-015に対応)
- **COM-004**: システムは、セッション識別子をAPIサーバーが生成・検証し、利用者側・管理者側それぞれのフロントエンドサーバーは受領した識別子をCookieとして発行するのみとし、以降のリクエストではブラウザから受信したCookieの値をAPIサーバーへの中継リクエストへ引き継がなければならない(NFR-SECUR-001に対応)
- **COM-005**: システムは、フロントエンドサーバーがAPIサーバーへリクエストを中継する際、元のクライアントIPアドレスを付与しなければならない(FR-RLMIT-001、NFR-SECUR-015、NFR-SECUR-023に対応)

## 6. 非機能要件

### 6.1 パフォーマンス要件

- **NFR-PERF-001**: システムは、FCP 1.6秒以内を達成しなければならない(CloudflareダッシュボードのSpeed>Observatoryで確認)
- **NFR-PERF-002**: システムは、同時接続ユーザー数100人をサポートしなければならない
- **NFR-PERF-003**: システムは、GraphQL APIのクライアント観測で95パーセンタイル300ms以内のレスポンスタイムを達成しなければならない(`@sentry/tanstackstart-react`のBrowser Tracingを利用しリクエスト10回あたり1回計測)
- **NFR-PERF-004**: システムは、GraphQLにおけるN+1問題を回避するためDataLoaderを使用しなければならない
- **NFR-PERF-005**: システムは、フロントエンドサーバー〜APIサーバー間の全通信について、インターネットを経由しない低レイテンシ呼び出しのためにCloudflare Service BindingsのHTTPインターフェースを使用しなければならない

### 6.2 セキュリティ要件

- **NFR-SECUR-001**: システムは、認証Cookieの名前に`__Host-`プレフィックスを付け、`Secure`属性及び`Path=/`を付与し`Domain`属性は指定せず、加えて`HttpOnly`・`SameSite=Lax`属性を付け、そのCookieによる認証を実装しなければならない(COM-003、COM-004に対応)
- **NFR-SECUR-002**: システムは、セッション識別子をWeb Crypto APIの`crypto.getRandomValues()`により32バイトの暗号論的乱数として生成しなければならない(COM-004に対応)
- **NFR-SECUR-003**: システムは、CSRFから保護するため、NFR-SECUR-001の認証を要する状態変更リクエストについて、利用者側・管理者側それぞれのフロントエンドサーバーにおいて、`Sec-Fetch-Site`ヘッダーが存在する場合はその値が`same-origin`であること、存在しない場合は`Origin`ヘッダーの値が自サイトのオリジンと一致することを検証し、いずれの検証にも失敗したリクエストを拒否しなければならない(COM-003に対応)
- **NFR-SECUR-004**: システムは、パスワードのような低エントロピー秘密をハッシュ化する場合、Web Crypto APIの`crypto.subtle`によりPBKDF2-HMAC-SHA512形式で、反復回数10万回、かつ固定ペッパー付きでハッシュ化しなければならない — OWASPの推奨は22万回以上だが、Cloudflare Workersは[DoS対策として10万回以内に制限してしまう](https://github.com/cloudflare/workerd/issues/1346)ため
- **NFR-SECUR-005**: システムは、ユーザーや管理者アカウント毎に、Web Crypto APIの`crypto.getRandomValues()`により16バイト以上の暗号論的乱数のソルトを生成してNFR-SECUR-004のハッシュ化に用い、ハッシュ化後のパスワードと共に保存しなければならない
- **NFR-SECUR-006**: システムは、十分なエントロピーを持つ乱数として発行される秘密情報をハッシュ化する場合、Web Crypto APIの`crypto.subtle`によりHMAC-SHA512形式(固定ペッパーを鍵として使用)でハッシュ化して保存し、検証時はタイミングセーフな比較を行わなければならない

- **LR-006**: システムは、ユーザーデータを扱うにあたり個人情報保護法、GDPR、CCPA/CPRA(米国カリフォルニア州)、LGPD(ブラジル)等、事業展開する主要地域のプライバシー関連法に準拠しなければならない
- **LR-007**: システムは、表示価格、返金対応、定期購入の自動更新及び解約について、事業展開する各国の消費者保護法に準拠しなければならない
- **LR-008**: システムは、Stripeにより有料プラン・決済機能を提供する際、特定商取引法に基づく事業者情報(事業者名・連絡先・税込価格・支払方法・返金ポリシー等)を表示しなければならない
- **LR-009**: システムは、表示価格を消費税及び海外の付加価値税等を含む税込のUSD総額に統一し、Stripe Taxにより購入者居住地に応じた税額を算出しなければならない
