## ローカル状態の保存先と共有するアプリ

WranglerのD1・R2ローカルモードの実データは`/workspace/.wrangler/state`に置く。このディレクトリはGit管理に含めない。

- `--persist-to`を持つWranglerのコマンドには`--persist-to /workspace/.wrangler/state`を付け、D1・R2系のコマンドではさらに`--local`を付ける。

```sh
wrangler dev --persist-to /workspace/.wrangler/state
wrangler d1 migrations apply <データベース名> --local --persist-to /workspace/.wrangler/state
```

- 次のアプリが、このローカル状態を共有する。

| アプリ                      | 起動方法                                                  | 保存先の指定                                                                             |
| --------------------------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `apps/api`・`apps/event`    | `wrangler dev`                                            | `--persist-to /workspace/.wrangler/state`                                                |
| `apps/client`・`apps/admin` | `@cloudflare/vite-plugin`による`vite dev`・`vite preview` | `vite.config.ts`の`cloudflare({ persistState: { path: '/workspace/.wrangler/state' } })` |

- `apps/api`と`apps/event`のWrangler設定では、`database_id`・R2のバケット名(`bucket_name`)、及び`wrangler dev`が優先して使う`preview_database_id`・`preview_id`・`preview_bucket_name`を、両アプリで同一の値にする。

## 互換性日付

全アプリのWrangler設定(`@cloudflare/vite-plugin`でビルドする`apps/client`・`apps/admin`を含む)で、`compatibility_date`を`2026-08-04`と定義する。この日付では、互換性フラグ`nodejs_compat`・`nodejs_compat_v2`が自動で有効になる。

## 単体テストの設定ファイル

単体テスト(Bun)の共通設定ファイルは`/workspace/bunfig.toml`である。ルート(`/workspace`)以外のディレクトリで`bun test`を実行する場合は、`--config=/workspace/bunfig.toml`を明示する。

```sh
cd /workspace/apps/api
bun test --config=/workspace/bunfig.toml unit.test
```

- 各アプリの`package.json`の`test:unit`スクリプトでは、アプリのディレクトリからの相対パス`--config=../../bunfig.toml`で指定する([スクリプト契約](../GUIDES/tech/coding/001-javascript-typescript-conventions.md#スクリプト契約))。

## シークレット注入の実行接頭辞

ローカル環境でシークレットを使うコマンド(`bun run dev`・`wrangler dev`・`vite build`など)は、先頭に`infisical --telemetry=false run --env dev -- `を付けて実行する。

```sh
infisical --telemetry=false run --env dev -- bun run dev
```

- `--telemetry=false`は、本プロジェクトで`infisical`のすべてのコマンドに付ける共通のオプションである。
- `dev`は、ローカル環境のInfisicalの環境種別である。デプロイ先検証環境は`staging`、本番環境は`prod`を指定する。

| `CHROMIUM_PATH`の値(実行ファイルへのシンボリックリンク)  | `/opt/ms-playwright-bin/chrome` | `Dockerfile`の`ENV` |
| Playwrightのブラウザの導入先(`PLAYWRIGHT_BROWSERS_PATH`) | `/opt/ms-playwright`            | `Dockerfile`の`ENV` |

- コンテナの起動時に、`scripts/entrypoint.sh`が`/workspace/scripts/setup-chromium.sh`を実行する。このスクリプトが、ルートの`@playwright/test`の版に合わせて共有Chromiumを導入し、`CHROMIUM_PATH`のシンボリックリンクを張り直す。技術ドキュメントの「コンテナの起動時にこの処理を行う仕組み」は、このスクリプトを指す。
- `CHROMIUM_PATH`は、`config/vitest/browser.ts`の`resolveBrowserLaunchOptions`(ブラウザテストと、`playwright.config.ts`によるE2Eテスト)と、`.mcp.json`の`chrome-devtools`・`playwright`の両MCPサーバーの引数`${CHROMIUM_PATH}`が読む。

## Workerとリソースの名前と識別子

`apps/api/wrangler.jsonc`・`apps/event/wrangler.jsonc`に書いている値である。ローカル環境の値はWrangler設定のルートに、デプロイ先の値は`env.staging`・`env.prod`に書く。

| リソース                             | ローカル環境                                    | デプロイ先検証環境(`staging`)                       | 本番環境(`prod`)                                 |
| ------------------------------------ | ----------------------------------------------- | --------------------------------------------------- | ------------------------------------------------ |
| `apps/api`のWorker名                 | `genai-example-2-api`                           | `genai-example-2-api-staging`                       | `genai-example-2-api-prod`                       |
| `apps/event`のWorker名               | `genai-example-2-event`                         | `genai-example-2-event-staging`                     | `genai-example-2-event-prod`                     |
| D1の`database_name`                  | `genai-example-2-dev`                           | `genai-example-2-staging`                           | `genai-example-2-prod`                           |
| D1の`database_id`                    | `00000000-0000-4000-8000-000000000001`          | `00000000-0000-0000-0000-000000000000`(仮の値)      | `00000000-0000-0000-0000-000000000000`(仮の値)   |
| R2のバケット名(画像・ファイル・隔離) | `genai-example-2-{images,files,quarantine}-dev` | `genai-example-2-{images,files,quarantine}-staging` | `genai-example-2-{images,files,quarantine}-prod` |
| 本体Queueの名前                      | `genai-example-2-jobs-dev`                      | `genai-example-2-jobs-staging`                      | `genai-example-2-jobs-prod`                      |
| デッドレターQueueの名前              | `genai-example-2-jobs-dlq-dev`                  | `genai-example-2-jobs-dlq-staging`                  | `genai-example-2-jobs-dlq-prod`                  |
| `IP_RATE_LIMITER`の`namespace_id`    | `apps/api`は`1001`・`apps/event`は`1002`        | `apps/api`は`2001`・`apps/event`は`2002`            | `apps/api`は`3001`・`apps/event`は`3002`         |

- D1の`database_name`・`database_id`とR2のバケット名は、環境ごとに両アプリで同じ値にする(「[ローカル状態の保存先と共有するアプリ](#ローカル状態の保存先と共有するアプリ)」)。
- デプロイ先の`database_id`は仮の値である。OpenTofuで作成したD1の値に、両アプリ同時に置き換える。
- `namespace_id`は全Worker・全環境で重複させない。`apps/client`・`apps/admin`のIP制限のために、ローカル環境の`1003`・`1004`、デプロイ先検証環境の`2003`・`2004`、本番環境の`3003`・`3004`を予約している。
- `IP_RATE_LIMITER`の上限は、全Worker・全環境で送信元IPアドレスごとに10秒あたり100回(`simple: { limit: 100, period: 10 }`)である。

## 業務時刻

- 業務時刻は、夏時間の無いUTC-08:00である。`apps/backend-lib/core/time/business-time.ts`の`BUSINESS_UTC_OFFSET_MINUTES`(`-480`)が定める。
- 業務日付の境界(業務時刻の0:00)は、UTCの8:00である。
- 例えば、業務時刻の4:21はUTCの12:21(cron式`21 12 * * *`)、業務時刻の23:45はUTCの翌日の7:45(cron式`45 7 * * *`)になる。

## 定期実行と非同期メッセージ

- 定期実行は`apps/api`だけが受け持つ。ジョブと時間の予算は`apps/api/src/composition/scheduled-jobs.ts`の`SCHEDULED_JOBS`・`SCHEDULED_RUN_BUDGETS`に登録し、cron式は`apps/api/wrangler.jsonc`のルート・`env.staging`・`env.prod`の`triggers.crons`に書く。両者の一致は`apps/api/test/config/cron-sync.unit.test.ts`が確かめる。
- メッセージは`apps/api`・`apps/event`のどちらからも送り、`apps/event`だけが受信する。メッセージの処理は`apps/event/src/composition/message-handlers.ts`の`MESSAGE_HANDLERS`に登録する。
- ローカルの`apps/api`は`--test-scheduled`付きで起動し、定期実行を手動で起こす(「[オンボーディングガイド](README.md#定期実行の手動起動)」)。

### 定期実行の時間の予算

| 起動時刻(業務時刻) | cron式(UTC)   | 予算           | 上限            | 各ジョブの目安 |
| ------------------ | ------------- | -------------- | --------------- | -------------- |
| 4:21               | `21 12 * * *` | 300,000ms(5分) | 600,000ms(10分) | 30,000ms(30秒) |

- 4:21には複数のドメインの日次のジョブが順に集まるため、この起動時刻にだけ予算を置く。
- 予算は`SCHEDULED_RUN_BUDGETS`に`{ at: { hour: 4, minute: 21 }, maxTotalDurationMs: 300_000 }`として登録し、合計の所要時間が予算を超えるとエラートラッキングへ警告が送られる。上限と各ジョブの目安は登録せず、要約のログの`totalDurationMs`・`durationMs`で確かめる(「[同じ時刻のジョブ群の時間の予算](../GUIDES/tech/infra/003-async-processing.md#同じ時刻のジョブ群の時間の予算)」)。
