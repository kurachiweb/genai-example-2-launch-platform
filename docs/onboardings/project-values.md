# 本プロジェクト固有の値

## ローカル状態の保存先と共有するアプリ

WranglerのD1・R2ローカルモードの実データは`/workspace/.wrangler/state`に置く。このディレクトリはGit管理に含めない。

- `--persist-to`を持つWranglerのコマンドには`--persist-to /workspace/.wrangler/state`を付け、D1・R2系のコマンドではさらに`--local`を付ける。

```sh
wrangler dev --persist-to /workspace/.wrangler/state
wrangler d1 migrations apply <データベース名> --local --persist-to /workspace/.wrangler/state
```

- 次のアプリが、このローカル状態を共有する。

| アプリ                      | 起動方法                                                  | 保存先の指定                                                                             |
| --------------------------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `apps/api`・`apps/event`    | `wrangler dev`                                            | `--persist-to /workspace/.wrangler/state`                                                |
| `apps/client`・`apps/admin` | `@cloudflare/vite-plugin`による`vite dev`・`vite preview` | `vite.config.ts`の`cloudflare({ persistState: { path: '/workspace/.wrangler/state' } })` |

- `apps/api`と`apps/event`のWrangler設定では、`database_id`・R2のバケット名(`bucket_name`)、及び`wrangler dev`が優先して使う`preview_database_id`・`preview_id`・`preview_bucket_name`を、両アプリで同一の値にする。

## 互換性日付

全アプリのWrangler設定(`@cloudflare/vite-plugin`でビルドする`apps/client`・`apps/admin`を含む)で、`compatibility_date`を`2026-08-04`と定義する。この日付では、互換性フラグ`nodejs_compat`・`nodejs_compat_v2`が自動で有効になる。

## 単体テストの設定ファイル

単体テスト(Bun)の共通設定ファイルは`/workspace/bunfig.toml`である。ルート(`/workspace`)以外のディレクトリで`bun test`を実行する場合は、`--config=/workspace/bunfig.toml`を明示する。

```sh
cd /workspace/apps/api
bun test --config=/workspace/bunfig.toml unit.test
```

- 各アプリの`package.json`の`test:unit`スクリプトでは、アプリのディレクトリからの相対パス`--config=../../bunfig.toml`で指定する([スクリプト契約](../GUIDES/tech/coding/001-javascript-typescript-conventions.md#スクリプト契約))。
- 共有ディレクトリ(`apps/db`・`apps/backend-lib`)の検査担当でない`apps/event`は、ルートの`bunfig.toml`を書き写して`coveragePathIgnorePatterns`に配置先の`lib/**`・`db/**`を加えた`/workspace/apps/event/bunfig.unit.toml`を`--config=bunfig.unit.toml`で指定する([検査担当でないアプリでの共有ディレクトリの除外](../GUIDES/tech/coding/001-javascript-typescript-conventions.md#検査担当でないアプリでの共有ディレクトリの除外))。同じく画面の共通部品(`apps/frontend-lib`)の検査担当でない`apps/client`・`apps/admin`は、配置先の`lib/**`を加えた各アプリの`bunfig.unit.toml`を指定する。`/workspace/bunfig.toml`を変えたときは、これらのファイルも同じく変える。

```sh
cd /workspace/apps/event
bun run test:unit --coverage
```

## シークレット注入の実行接頭辞

ローカル環境でシークレットを使うコマンド(`bun run dev`・`vite build`など)は、先頭に`infisical --telemetry=false run --env dev -- `を付けて実行する。

```sh
infisical --telemetry=false run --env dev -- bun run dev
```

- `--telemetry=false`は、本プロジェクトで`infisical`のすべてのコマンドに付ける共通のオプションである。
- `dev`は、ローカル環境のInfisicalの環境種別である。デプロイ先検証環境は`staging`、本番環境は`prod`を指定する。

APIサーバー(`apps/api`)とイベントサーバー(`apps/event`)の起動だけは例外として、`infisical run`の代わりに配布のスクリプトの`run-with-secrets`を付けて実行する。`dev`の共通のフォルダ(`/`)の値に、そのWorkerのWorkerごとのフォルダ(`/workers/api`・`/workers/event`)の値を重ねて注入する。

```sh
cd /workspace/apps/api
bun /workspace/scripts/delivery/cli.ts run-with-secrets --scope local --worker api -- bun run dev

cd /workspace/apps/event
bun /workspace/scripts/delivery/cli.ts run-with-secrets --scope local --worker event -- bun run dev
```

- 同じキーがあればWorkerごとのフォルダの値を優先し、`WORKER_SCOPED_SECRETS`(`scripts/delivery/core/secret-scope.ts`)に挙げたキーは共通のフォルダの値を使わない。デプロイとCIのE2Eと同じ規則である(「[Workerのシークレットの選別](../GUIDES/tech/infra/007-ci-cd-pipelines.md#workerのシークレットの選別)」・「[Workerのシークレットのキーの一覧](#workerのシークレットのキーの一覧)」)。
- `--scope local`は、開発者自身の`infisical login`の認証で取り出し、`--`の後のコマンドへ環境変数として渡す。値は表示せず、注入した件数とフォルダだけを表示する。
- 利用者側・管理者側のフロントエンドはWorkerごとのフォルダを持たないため、`infisical --telemetry=false run --env dev -- `のままにする。

- `apps/client`・`apps/admin`の`API`の`service`は、`apps/api`の同じ環境のWorker名である。`services`・`ratelimits`はWrangler設定の`env`へ継承されないため、ルートと`env.staging`・`env.prod`のそれぞれに書く。
- `IP_RATE_LIMITER`の上限は、全Worker・全環境で送信元IPアドレスごとに10秒あたり100回(`simple: { limit: 100, period: 10 }`)である。
- メールイベント用Queueは`apps/event`だけがconsumerを持ち、`max_retries`とデッドレターは本体Queueと同じ値にする。デプロイ先のメールイベント用Queueと送信ドメインの登録(送信内容のプレビューの無効化を含む)はIaC定義が資源一覧から作り、配信不能イベントの購読はデプロイのパイプラインがデプロイのたびに確かめて無ければ作る。管理画面では作らない(「[購読とQueueの作成](../GUIDES/tech/external/001-email-sending.md#購読とqueueの作成)」「[送信ドメインの登録](../GUIDES/tech/external/001-email-sending.md#送信ドメインの登録)」)。

| シークレット               | Infisicalの`dev`に登録する値                                                                                                          |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `HASH_PEPPER`              | `openssl rand -hex 64`で生成した128文字の16進数。環境ごとに別の値にし、他の環境の値を流用しない。同じ環境の4アプリが1つの値を共有する |
| `TURNSTILE_SECRET_KEY`     | 常に成功するテスト用の秘密鍵`1x0000000000000000000000000000000AA`                                                                     |
| `SENTRY_DSN`               | 登録しない。ローカル環境の`secrets.required`に無く、未設定ならエラートラッキングへ送信しない(`apps/client`・`apps/admin`も同じ)       |
| `EMAIL_SMOKE_TOKEN`        | `openssl rand -hex 32`で生成した64文字の16進数。環境ごとに別の値にし、他の環境の値を流用しない                                        |
| `EMAIL_SMOKE_RECIPIENT`    | 任意の宛先(例:`smoke@local.example`)。ローカル環境ではMailpitが全ての宛先のメールを受け取り、外部へは送らない                         |
| `EMAIL_ALLOWED_RECIPIENTS` | 登録しない。ローカル環境は宛先を制限しない(`EMAIL_RECIPIENT_POLICY`が`any`)                                                           |

- `HASH_PEPPER`は、`apps/api`・`apps/event`・`apps/client`・`apps/admin`の全環境の`secrets.required`にある。Infisicalには環境ごとに1つだけ登録し、4アプリへ同じ値を注入する。`apps/client`・`apps/admin`はWorker単位のIP制限のキーのハッシュ化だけに使い(「[フロントエンドのキーのハッシュ化](../GUIDES/tech/frontend/003-frontend-server-security.md#キーのハッシュ化)」)、未登録のまま起動するとページと中継のすべての要求が環境の検証で500になる。
- `apps/client`・`apps/admin`のデプロイ先の`secrets.required`は`HASH_PEPPER`と`SENTRY_DSN`で、Infisicalの`staging`・`prod`に登録する。
- `EMAIL_SMOKE_TOKEN`・`EMAIL_SMOKE_RECIPIENT`は疎通確認の経路だけが使う。ローカル環境の`secrets.required`にはあるが、未登録でも`apps/event`は警告を出して起動し、疎通確認の経路が404になる。
- デプロイ先検証環境(Infisicalの`staging`)には、`EMAIL_ALLOWED_RECIPIENTS`(検証済みの宛先のカンマ区切り。`secrets.required`にあり、未設定ではデプロイが失敗する)と、`EMAIL_SMOKE_TOKEN`・`EMAIL_SMOKE_RECIPIENT`(`secrets.required`に無く任意)を登録し、Infisicalの値を正とする。`EMAIL_ALLOWED_RECIPIENTS`は、`secrets.required`へ加える変更を`main`へマージする前に登録する。登録した値は、次のCIのデプロイがWorkerへ反映する(「[stagingのメールのシークレット](README.md#stagingのメールのシークレット)」)。本番環境には疎通確認の2つを設定せず、経路を無効にする。
- 全環境の登録先のフォルダと登録の時期は「[Workerのシークレットのキーの一覧](#workerのシークレットのキーの一覧)」を正とする。

- Workerごとのフォルダ(`/workers/api`・`/workers/event`)の値は、同じキーの`/`の値より優先して、そのWorkerにだけ渡る。`WORKER_SCOPED_SECRETS`に挙げたキーは`/`に置いても使われないため、必ずWorkerごとのフォルダへ登録する。この規則は、デプロイ(`deploy-worker`)・検査のE2E(`e2e-stack`)・ローカルの起動(`run-with-secrets --scope local --worker`)で同じである。
- 現時点の`WORKER_SCOPED_SECRETS`は`STRIPE_API_KEY`(api用とevent用の別々の制限付きキー)だけで、まだどのWrangler設定にも宣言されていない。paymentsが宣言する変更と同じ変更で、`dev`・`staging`の`/workers/api`・`/workers/event`の行を足す。
- 必須のキーを`staging`に登録しないまま、そのキーを`secrets.required`へ加える変更をmainへマージすると、そのWorkerのデプロイが欠けたキーの名前を示して止まり、登録するまで`staging`へのデプロイがすべて止まる。
- 任意のキーは`OPTIONAL_WORKER_SECRETS`のそのWorkerの項目に無ければ、Infisicalに値があってもWorkerへ渡らない。
- `prod`には疎通確認のトークン(`EMAIL_SMOKE_TOKEN`・`EMAIL_SMOKE_RECIPIENT`・`MEDIA_SMOKE_TOKEN`)と`EMAIL_ALLOWED_RECIPIENTS`を登録しない。
- `/ci/tofu`・`/ci/cloudflare`はCIのデプロイの主体だけが使い、ローカルの起動とCIの検査は読まない。

## 業務時刻

- 業務時刻は、夏時間の無いUTC-08:00である。`apps/backend-lib/core/time/business-time.ts`の`BUSINESS_UTC_OFFSET_MINUTES`(`-480`)が定める。
- 業務日付の境界(業務時刻の0:00)は、UTCの8:00である。
- 例えば、業務時刻の4:21はUTCの12:21(cron式`21 12 * * *`)、業務時刻の23:45はUTCの翌日の7:45(cron式`45 7 * * *`)になる。

## 定期実行と非同期メッセージ

- 定期実行は`apps/api`だけが受け持つ。ジョブと時間の予算は`apps/api/src/composition/scheduled-jobs.ts`の`SCHEDULED_JOBS`・`SCHEDULED_RUN_BUDGETS`に登録し、cron式は`apps/api/wrangler.jsonc`のルートの`triggers.crons`だけに書く。`triggers`はWranglerで環境へ継承されるキーのため、`env.staging`・`env.prod`にも同じcron式が適用される。ルートと継承後の`env.staging`・`env.prod`の値がジョブと一致することは`apps/api/test/config/cron-sync.unit.test.ts`が確かめる。
- メッセージは`apps/api`・`apps/event`のどちらからも送り、`apps/event`だけが受信する。メッセージの処理は`apps/event/src/composition/message-handlers.ts`の`MESSAGE_HANDLERS`に登録する。
- ローカルの`apps/api`は`--test-scheduled`付きで起動し、定期実行を手動で起こす(「[オンボーディングガイド](README.md#定期実行の手動起動)」)。

| 起動時刻(業務時刻) | cron式(UTC)   | 予算           | 上限            | 各ジョブの目安 |
| ------------------ | ------------- | -------------- | --------------- | -------------- |
| 4:21               | `21 12 * * *` | 300,000ms(5分) | 600,000ms(10分) | 30,000ms(30秒) |

- 4:21には複数のドメインの日次のジョブが順に集まるため、この起動時刻にだけ予算を置く。
- 予算は`SCHEDULED_RUN_BUDGETS`に`{ at: { hour: 4, minute: 21 }, maxTotalDurationMs: 300_000 }`として登録し、合計の所要時間が予算を超えるとエラートラッキングへ警告が送られる。上限と各ジョブの目安は登録せず、要約のログの`totalDurationMs`・`durationMs`で確かめる(「[同じ時刻のジョブ群の時間の予算](../GUIDES/tech/infra/003-async-processing.md#同じ時刻のジョブ群の時間の予算)」)。

## メール送信

メール送信の仕組みは「[メール送信サービス](../GUIDES/tech/external/001-email-sending.md)」に従う。描画と送信は`apps/event`だけが行い、`apps/api`は送信要求をQueueへ送る。環境ごとの送信ドメイン・送信元・Queueの名前は「[Workerとリソースの名前と識別子](#workerとリソースの名前と識別子)」、変数とシークレットは「[バインディング・変数・シークレット](#バインディング変数シークレット)」を参照する。

| 項目                         | 値                                                                                            | 定義場所                                                                          |
| ---------------------------- | --------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 送信元の表示名               | `Launch Stadium`                                                                              | `apps/event/src/composition/email-module.ts`の`fromName`                          |
| テンプレートの集約点         | `EMAIL_TEMPLATES`(疎通確認のテンプレートだけ)                                                 | `apps/event/src/infrastructure/email/templates/index.ts`                          |
| 送信者情報の提供元           | `UnsetSenderInfoProvider`(未設定として送信者情報の区画を省く)                                 | `apps/event/src/composition/email-registrations.ts`の`EMAIL_SENDER_INFO_PROVIDER` |
| 利用者のアドレスの照会口     | `UnavailableUserAddressDirectory`(照会できないとして、利用者に紐づかない抑止記録を削除しない) | `apps/api/src/composition/email-registrations.ts`の`USER_ADDRESS_DIRECTORY`       |
| 配信不能イベントの処理の登録 | 名前`email-delivery-events`、Queueの名前は`EMAIL_EVENTS_QUEUE_NAME`の値                       | `apps/event/src/composition/raw-queue-handlers.ts`の`RAW_QUEUE_HANDLERS`          |
| 日次の後始末のジョブ         | `email-delivery.cleanup`(業務時刻の4:21、順序`900`)                                           | `apps/api/src/composition/scheduled-jobs.ts`の`SCHEDULED_JOBS`                    |
| 疎通確認の経路               | `POST /internal/email/smoke`                                                                  | `apps/event/src/presentation/email/email-smoke-route.ts`の`EMAIL_SMOKE_PATH`      |

疎通確認の経路のURLは次のとおりである。使い方は「[疎通確認の経路](README.md#疎通確認の経路)」に従う。

| 環境                          | URL                                                                                                                                                        |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ローカル環境                  | `http://localhost:48043/internal/email/smoke`                                                                                                              |

- 送信者情報の提供元と利用者のアドレスの照会口は、送信者情報を管理する機能と利用者のアカウントを管理する機能が、それぞれの登録箇所のクラスを書き換えて差し替える。
