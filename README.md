# ローンチディレクトリ「Launch Stadium」

Launch Stadiumのプログラム一式、及びドキュメント。
サイトURL(予定)：https://genai-example-2-client.shortbook.workers.dev

---

## このサービスについて

数々のユーザーが作ったプロダクト同士の1対1勝負を、日々開催するコミュニティ。ProductHuntやUneedの競合という立ち位置。
サッカーの試合をテーマにしていて、Upvoteしたユーザーはサポーターとして扱う。
勝ったプロダクトのみが製品ディレクトリに掲載される。
勝った製品は、Product of the week/yearを決めるトーナメントに進出できる。

## なぜ作るか

製品を探す人にとって、選ばれる製品だけを掲載するプラットフォームこそ価値があると信じているため。
製品を発表する人や応援する人に、一人でも多く何らかの成果を感じてほしいため。

## 既存サービスの課題点

ProductHuntやTinyLaunch、Uneedなど既存のローンチディレクトリは、数々のプロダクトが投稿される中で日毎に1位を決める仕組み。
尊敬する素晴らしいサービスであるが、以下の課題点があると感じている。

1. ランキング上位が正義という仕組み → 1位〜3位ほどの上位にならない限り注目されにくく、成功したとは見做されにくい。
2. ランキング上位を目指すためのローンチ前準備が多すぎる → 無名の新人は作業量でも集客力でも不利。
3. 特定の日に誰がローンチするのか分からない → 不運にも有名会社と同じ日にローンチしてしまうと勝てない。
4. ランキング内に全く違うカテゴリのプロダクトが混ざっている → AIのような流行りのジャンル以外は不利。
5. 再ローンチが規約で制限されているか、そうでなくてもコミュニティから忌み嫌われかねない → AI時代の高頻度アップデートと相性が悪い。

## 解決する点

1. ~~ランキング上位が正義という仕組み~~ → 1対1勝負なので、必ず半分は勝ちになる。毎日勝ち製品を量産する仕組み。
2. ~~ランキング上位を目指すためのローンチ前準備が多すぎる~~ → 事前に対戦相手を選ぶこともできるので、実力に見合った相手を選べる。
3. ~~特定の日に誰がローンチするのか分からない~~ → 事前に対戦相手を選ぶこともできるので、対策を練って覚悟を持てる。
4. ~~ランキング内に全く違うカテゴリのプロダクトが混ざっている~~ → 事前に対戦相手を選ぶこともできるので、似た製品を選んで真っ向勝負できる。
5. ~~再ローンチが規約で制限されているか、そうでなくてもコミュニティから忌み嫌われる~~ → 勝てるまで毎日投稿OK。勝ったら一定期間は同じ製品を再投稿できない。

## ソフトウェア要件定義書 (IEEE 29148準拠)

### 1. イントロダクション

#### 1.1 目的

本文書は、Launch Stadiumのソフトウェア要件を定義する。本システムは、プロダクト同士の1対1対戦形式によるローンチプラットフォームを提供し、既存ローンチディレクトリの課題を解決することを目的とする。

#### 1.2 スコープ

Launch Stadiumは、以下を提供するWebアプリケーションである:

- プロダクト同士の1対1対戦形式によるローンチ機能
- サポーター(Upvote)によるプロダクト支援機能
- 勝利したプロダクトのみを掲載する製品ディレクトリ
- トーナメント機能(Product of the Week/Year)
- 再ローンチ機能(勝利後一定期間は同じ製品を再投稿できない)

#### 1.3 定義・略語

- **プロダクト**: ユーザーが投稿する製品・サービス
- **マッチ**: 2つのプロダクト間の対戦
- **サポーター**: プロダクトにUpvoteしたユーザー
- **ディレクトリ**: 勝利したプロダクトが掲載されるカタログ
- **FCP**: First Contentful Paint (初回コンテンツ描画)

#### 1.4 文書概要

本文書は、ステークホルダー要件、システム要件、機能要件、非機能要件を定義する。

### 2. 全体的な記述

#### 2.1 製品の展望

Launch Stadiumは、ProductHuntやUneedの競合として位置づけられる新しいローンチプラットフォームである。サッカーの試合をテーマとし、1対1対戦形式により「必ず半分は勝者になる」仕組みを提供する。

#### 2.2 製品の機能

- プロダクト登録・投稿機能
- 対戦相手選択機能
- マッチ・対戦機能
- サポーター機能(Upvote)
- 製品ディレクトリ機能
- トーナメント機能
- 再ローンチ機能
- ユーザー認証・認可機能
- 管理機能

#### 2.3 ユーザークラスと特性

- **プロダクト投稿者**: 自身のプロダクトをローンチし、対戦相手を選択する
- **サポーター**: 気に入ったプロダクトにUpvoteし、応援する
- **製品探索者**: ディレクトリから優れた製品を探す
- **システム管理者**: プラットフォーム全体を管理する

#### 2.4 運用環境

- **クライアント**: モダンWebブラウザ(Chrome, Firefox, Safari, Edge最新版)
- **サーバー**: Cloudflare Workers (NestJS on Hono), Cloudflare D1
- **インフラ**: Cloudflare各種サービス

#### 2.5 設計・実装の制約

- FCPを最優先とした設計
- HTTPS-Only Cookieによる認証
- GraphQL APIによる通信
- マークダウン形式によるプロダクト説明

#### 2.6 前提と依存関係

- Cloudflare各種サービスの利用可能性
- GitHubリポジトリとの連携
- 外部認証サービス(将来的なOAuth対応の可能性)

### 3. ステークホルダー要件

#### 3.1 既存サービスの課題

1. ランキング上位のみが注目され、成功と見做されにくい
2. ローンチ前準備の負担が大きく、新人が不利
3. 対戦相手が不明確で運に左右される
4. カテゴリ混在により特定ジャンルが不利
5. 再ローンチが制限され、高頻度アップデートと相性が悪い

#### 3.2 解決策

1. 1対1勝負により必ず半分が勝者になる仕組み
2. 事前に対戦相手を選択可能
3. 対策を練る時間と覚悟を持てる
4. 類似製品との真っ向勝負が可能
5. 勝利後一定期間を除き、再ローンチ可能

- **LR-004**: システムは、ランキング・投票(Upvote)等の表示について、景品表示法及びステルスマーケティング規制の観点から、やらせ投票や不正な実績操作を防止する対策を講じなければならない
- **LR-005**: システムは、ユーザー投稿コンテンツ(プロダクト説明・コメント)について、著作権の帰属を明確化し、プロバイダ責任制限法相当の侵害コンテンツ削除請求フローを提供しなければならない
- **LR-006**: システムは、通知メールについて、特定電子メール法(日本)及びCAN-SPAM法(米国)に基づく送信者情報の表示及び配信停止(オプトアウト)機能を提供しなければならない
- **LR-007**: システムは、EU消費者権利指令によるクーリングオフ期間(14日間の無条件解約権)等、事業展開する各国の消費者保護法に対応しなければならない
